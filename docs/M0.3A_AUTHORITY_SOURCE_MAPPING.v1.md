# M0.3A authority source mapping v1

## Status and purpose

Contract ID: `M0.3A-AUTHORITY-SOURCE-MAPPING`

Version: `1`

This contract defines the first sealed mapping from repository-authoritative
M0.2 historical evidence to an observed M0.3A runtime subject. It is diagnostic
and DENY-only. It cannot produce `CURRENT`, `PASS`, `generation_match: true`,
`ALLOW`, an authenticated receipt, a scheduler transition, or any paper, live,
execution, STOP-clearance, or capital action.

The public composer accepts exactly a `Scheduler`, a SQLite task ID, and a
capture ID. It accepts no caller-provided path, snapshot, trust root, source
mapping, receipt, generation, result, seal, or policy. The scheduler must be
attached to the canonical repository root from which the composer module is
loaded; an alternate root fails closed.

## Authoritative sources

| Output fact | Sole source | Extraction rule |
|---|---|---|
| mapping contract | this file | exact file-byte SHA-256 plus fixed ID/version above |
| trusted root | `docs/M0.2_STAGE1_TRUST_ROOT.v1.json` | self-verified `root_id`, `root_sha256`, `freeze_commit`, `entrypoint` |
| capture root | `docs/M0.2_HISTORICAL_CAPTURE_ROOT.v1.json` | self-verified `root_id`, `root_sha256`, base-root binding, one exact capture entry |
| capture directory | selected capture-root entry | resolve only its repository-relative `fixture_path`; reject traversal, aliases, or caller paths |
| captured intent/result | capture sidecar at the selected directory | exact sidecar bytes must match the capture-root digest and trusted verifier |
| persisted graph | deterministic generator over the selected directory | graph self digest must equal the selected capture-root entry |
| historical status | `tools.verify_authentic_history.verify_authentic_history` | require `HISTORICALLY_VALID`, completed replay, raw result match, trusted roots, package/module/schema closure, and compatible retained runtime boundary |
| active runtime subject | `read_locked_authority(Scheduler, task_id)` | actual Git, attachment, immutable SQLite, task, attempt, claim, and review read under the scheduler lock; coherent result is still DENY-only |

The mapping, trusted-root, and capture-root files are pinned by exact file-byte
SHA-256 constants in the composer. They must be regular, non-symlink files at
their canonical repository paths. The trusted root also passes a closed JSON
Schema before the existing canonical self-digest and dependency-closure checks.

Repository M0.2 claims and runtime M0.3A claims are distinct namespaces. No
field from the historical capture is treated as proof that the current
repository, STOP set, assignments, handoffs, capabilities, or runtime generation
matches the frozen state.

## Exact binding invariants

A `BOUND_DENY_ONLY` candidate requires all of the following:

1. Both trust roots self-verify before and after composition, and their exact
   bytes plus this mapping contract's bytes remain unchanged.
2. The selected capture ID occurs exactly once in the capture root and resolves
   only to its declared in-repository fixture directory.
3. Sidecar digest, repository inventory, packages, persisted graph digest,
   frozen commit, entrypoint, trusted-root ID, captured result, reconstructed
   replay result, and verifier evidence agree exactly.
4. Captured intent task ID equals captured result task ID, the requested SQLite
   task ID, and the locked runtime task ID.
5. Captured intent attempt is an actual positive integer and equals the locked
   runtime task attempt.
6. The captured result uses `MOCK_ONLY`. `DISPATCH` has a nonempty operation;
   `DENY` has no operation. Decision ID and reason are retained exactly.
7. The locked authority read is coherent and a second locked read has the same
   authority digest. Any unavailable read or observed change fails closed.
8. The resulting historical seal and candidate pass their closed JSON Schemas
   and the semantic verifier's cross-field and self-digest equations.

The historical verifier projection is deliberately stable: status, capture ID,
trusted-root ID, replay completion, raw-result match, frozen commit, replay-root
digest, raw-result digest, and decision ID. Environment paths and other
diagnostics remain verifier evidence but are not copied wholesale into the seal.

`seal_sha256` is SHA-256 over canonical JSON of the seal excluding
`seal_sha256`. `seal_id` is `HS-` plus the first 32 hexadecimal characters of
the source projection digest. `candidate_sha256` is SHA-256 over canonical JSON
of the candidate excluding `candidate_sha256`.

The two JSON Schemas validate closed shape and DENY-only constants. Schema
validity alone is not integrity verification. `verify_binding_integrity`
recomputes the candidate and seal digests, stable and source projections, seal
ID, raw decision digest, and all task, attempt, capture, root, replay, decision,
and evidence-class equalities. It still does not re-observe historical sources
or the runtime. A future consumer must call the composer rather than accept a
stored schema-valid candidate as authority.

## Candidate classification

- A historically valid captured `DISPATCH` becomes
  `R_GATE_CANDIDATE_EVIDENCE` only. This label means it may be considered by a
  future, separately reviewed currentness and R-gate design. It is not a current
  or authorizing receipt.
- A historically valid captured `DENY` becomes `NON_AUTHORIZING_EVIDENCE`.
- Missing, invalid, incompatible, raced, or mismatched evidence becomes
  `UNAVAILABLE` with no seal or authority digest.

Every result embeds a schema-v3-shaped denial. Even a bound historical candidate
is fixed to `historical_status: VALID`, `currentness_status: UNKNOWN`,
`runtime_compatible: true`, `verifier_status: FAIL`,
`generation_match: false`, `authorizing_use: DENY`, and
`reason_code: VERIFIER_FAILURE`.

## Explicit absent claims

This contract does not map or infer authoritative current values for project
state, STOP inventory, task/assignment/handoff heads, dependency or capability
generations, active repository reachability, authenticated receipt identity,
runtime policy generations, or the frozen repository's equality to the active
repository. Absence remains `UNKNOWN`, never zero, equal, current, or approved.

The scheduler bundle currently omits decision-critical sources and the stored
`decision_receipt_digest` is caller supplied. No transition may consume this
candidate. Existing runtimes have no persisted authority-binding field; any
future storage migration must initialize it as unbound/null and must never
backfill a receipt from this diagnostic.

## Fail-closed boundary

The composer performs no database write, scheduler initialization, permission
repair, migration, transition, network access, executor call, or repository
mutation. Unknown capture IDs, task/attempt substitutions, root or graph drift,
decision/result drift, incompatible historical runtime, locked-authority
failure, races, malformed schemas, and internal errors return a schema-valid
`UNAVAILABLE` denial whenever the local schema itself remains readable.

The local process and its loaded code remain inside the trust boundary. These
controls detect caller-selected roots, dirty authoritative-source bytes, and
filesystem aliases; they cannot defend against an actor able to replace the
running composer, its embedded pins, and its verifier together. This diagnostic
therefore remains unusable as a positive authority boundary.
