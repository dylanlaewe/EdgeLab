# M0.3A Closed Transactional Contract v2

**Status:** planning only; implementation is withheld pending focused Skeptic acceptance. This contract supersedes the implementation details proposed in `M0.3A_TRANSACTIONAL_SPEC.md`; that earlier document remains preserved as planning history. Stage 1 M0.2 is frozen at `bc3a40924ca580ca6eddc4c24e32ff99ddd95330`. M0.3A may bind the frozen engine's exact receipt and inputs, but may not reimplement or change its semantics.

M0.3A is a local, SQLite-backed, synthetic scheduler. It has no executor, network/task adapter, Codex invocation, credential, plugin, MCP, external authority, sports-research, paper, live, capital, STOP-clearance, or M1 authority. `STOP-M0-001` stays OPEN; M0 stays blocked; executor state is `MOCK_ONLY`; capital remains USD 50 conceptual and USD 0 deployable/reserved; live stays `LOCKED` and kill `ENGAGED`.

## 1. Authoritative state, identity, and valid tuples

Git is authoritative for immutable task definitions, dependencies, handoffs, project state, STOP inventory, policy/capability inputs, and the frozen M0.2 source. SQLite is authoritative only for local runtime queue state and immutable transition records.

Each task has this complete state tuple:

`(workflow, execution, review, attempt_no, scheduler_generation, dispatch_generation, task_fence, active_claim_id, reviewer_assignment_id, continuation_count, repository_generation, decision_receipt_digest)`.

Domains are:

| Dimension | Values |
| --- | --- |
| workflow | `ACTIVE`, `GOVERNANCE_BLOCKED`, `DIRECTOR_GATE_READY`, `CANCELLED`, `SUPERSEDED`, `CLOSED` |
| execution | `CLAIMABLE`, `CLAIMED`, `IN_PROGRESS`, `EXECUTION_BLOCKED`, `FAILED`, `EXECUTION_COMPLETED` |
| review | `NOT_REQUIRED`, `REVIEW_PENDING`, `REVIEWING`, `REJECTED`, `REMEDIATION_REQUIRED`, `APPROVED` |

`attempt_no` starts at 1 and is never reused. All generations and `continuation_count` start at 0; `task_fence` starts at 0 and increases whenever a claim is issued, fenced, invalidated, recovered, retried, or governance-blocked. `scheduler_generation` advances for every state-mutating transition; `dispatch_generation` advances only when a claim becomes dispatchable or an existing dispatch becomes invalid. A non-null `active_claim_id` requires `execution=CLAIMED` or `IN_PROGRESS`. `reviewer_assignment_id` is non-null only for `REVIEWING`. A non-null receipt is required by rows marked **R** below.

The only valid, non-terminal operational tuples are listed below. All other tuples and every unlisted operation are denied before mutation.

| Alias | Tuple `(workflow, execution, review)` | Terminality |
| --- | --- | --- |
| N0 | `(ACTIVE, CLAIMABLE, NOT_REQUIRED)` | claimable |
| N1 | `(ACTIVE, CLAIMED, NOT_REQUIRED)` | worker-fenced |
| N2 | `(ACTIVE, IN_PROGRESS, NOT_REQUIRED)` | worker-fenced |
| F0 | `(ACTIVE, FAILED, NOT_REQUIRED)` | attempt terminal; retryable only by explicit classification |
| N3 | `(ACTIVE, EXECUTION_COMPLETED, REVIEW_PENDING)` | review assignable |
| N4 | `(ACTIVE, EXECUTION_COMPLETED, REVIEWING)` | reviewer-fenced |
| N5 | `(ACTIVE, EXECUTION_COMPLETED, REJECTED)` | evidence terminal; may create linked remediation task |
| N6 | `(ACTIVE, EXECUTION_COMPLETED, REMEDIATION_REQUIRED)` | evidence terminal; may create linked remediation task |
| N7 | `(ACTIVE, EXECUTION_COMPLETED, APPROVED)` | review terminal; routable once |
| N8 | `(DIRECTOR_GATE_READY, EXECUTION_COMPLETED, APPROVED)` | terminal for M0.3A routing |
| B0 | `(GOVERNANCE_BLOCKED, EXECUTION_BLOCKED, NOT_REQUIRED)` | recoverable only by revalidation |
| B1 | `(GOVERNANCE_BLOCKED, EXECUTION_BLOCKED, REVIEW_PENDING)` | recoverable only by revalidation |
| C0 | `(CLOSED, EXECUTION_COMPLETED, NOT_REQUIRED)` | terminal |
| C1 | `(CANCELLED, EXECUTION_BLOCKED, NOT_REQUIRED)` | terminal |
| C2 | `(CANCELLED, EXECUTION_BLOCKED, REVIEW_PENDING)` | terminal |
| S0 | `(SUPERSEDED, EXECUTION_BLOCKED, NOT_REQUIRED)` | terminal |
| S1 | `(SUPERSEDED, EXECUTION_BLOCKED, REVIEW_PENDING)` | terminal |

`APPROVED` is terminal only in the **review** dimension. `ROUTE_DIRECTOR_GATE` changes N7 to N8; it never changes review `APPROVED`. No terminal complete tuple is a source for a state-mutating transition except the separately created task/attempt explicitly named below. `GOVERNANCE_BLOCKED` is not a generic pause: it always has `EXECUTION_BLOCKED` and no active claim.

## 2. Closed transition matrix

Every row requires an exact current tuple, expected attempt and every listed generation/fence. **W** means the current active worker claim ID and fence; **V** means an active reviewer assignment, its generation, a synthetic reviewer fixture and reviewer role; **R** means a current exact M0.2 receipt/input bundle. `+S`, `+D`, and `+F` mean increment scheduler, dispatch, and task fence. “Close claim” records its close reason and clears it atomically.

| Operation / actor | Source → target | Preconditions and effects | Event / result |
| --- | --- | --- | --- |
| `INITIALIZE` / synthetic director fixture | none → N0 | verify genesis bindings; create task attempt 1; S=0,D=0,F=0 | `TASK_INITIALIZED`; task ID and tuple |
| `IMPORT_REPOSITORY` / synthetic scheduler fixture | N0 → N0 | idle only; exact new Git bundle; +S; no receipt/claim change | `REPOSITORY_IMPORTED`; repository generation |
| `CLAIM` / synthetic worker fixture | N0 → N1 | **R**; exact actor role allowed by immutable assignment; issue unique claim; +S,+D,+F | `CLAIM_ISSUED`; claim ID, F, D |
| `START` / worker | N1 → N2 | **W,R**; lease has not been revoked; +S | `WORK_STARTED`; tuple |
| `CONTINUE` / worker | N2 → N2 | **W,R**; increment `continuation_count`; +S; retain claim and F; policy limit is stored but no M0.3A policy is invented | `WORK_CONTINUED`; counter |
| `YIELD` / worker | N1 or N2 → N0 | **W**; close claim `YIELDED`; +S,+D,+F; receipt cleared | `CLAIM_YIELDED`; next claimable tuple |
| `COMPLETE_NO_REVIEW` / worker | N2 → C0 | **W,R**; immutable output/evidence bundle; close claim; +S,+D,+F | `WORK_COMPLETED`; final evidence digest |
| `COMPLETE_FOR_REVIEW` / worker | N2 → N3 | **W,R**; immutable output/evidence bundle; close claim; +S,+D,+F | `WORK_COMPLETED`; review-required tuple |
| `FAIL` / worker | N1 or N2 → `(ACTIVE,FAILED,NOT_REQUIRED)` | **W**; close claim; +S,+D,+F; failure classification immutable | `WORK_FAILED`; failure digest |
| `RETRY_NEW_ATTEMPT` / synthetic director fixture | `(ACTIVE,FAILED,NOT_REQUIRED)` → N0 on new attempt | failure is explicitly retryable; old attempt terminal; create attempt `n+1`, link predecessor; +S,+D,+F; receipt cleared | `ATTEMPT_RETRIED`; new attempt ID |
| `RECOVER_FENCED` / synthetic recovery fixture | N1 → N0 | documented lease/liveness evidence; old claim is not proof of completed work; close `RECOVERED`; +S,+D,+F; receipt cleared | `CLAIM_RECOVERED`; old/new fence |
| `BLOCK_GOVERNANCE` / synthetic scheduler fixture | N0,N1,N2,N3,N4 → B0,B0,B0,B1,B1 respectively | changed/dirty/missing Git bundle or stale receipt; if claim exists close `GOVERNANCE_INVALIDATED`; if N4 revoke reviewer assignment and return review to pending; +S,+D,+F; record invalidation tuple | `GOVERNANCE_BLOCKED`; changed binding bundle |
| `REVALIDATE_GOVERNANCE` / synthetic director fixture | B0 → N0; B1 → N3 | exact newly imported Git and **R** where claiming/decision requires it; B1 always needs later fresh review assignment; +S; receipt set only to verified current value | `GOVERNANCE_REVALIDATED`; new repository generation |
| `CANCEL` / synthetic director fixture | N0,N1,N2,N3 → C1,C1,C1,C2 | immutable cancellation authority input; close/revoke claim or reviewer if present; +S,+D,+F | `TASK_CANCELLED`; reason digest |
| `SUPERSEDE` / synthetic director fixture | N0,N1,N2,N3 → S0,S0,S0,S1 | new immutable task definition ID; close/revoke claim/review; +S,+D,+F; bidirectional link | `TASK_SUPERSEDED`; successor ID |
| `ASSIGN_REVIEW` / synthetic scheduler fixture | N3 → N4 | reviewer role differs from immutable owner role and reviewer fixture ID differs from owner fixture ID; create assignment generation; +S | `REVIEW_ASSIGNED`; assignment ID |
| `APPROVE_REVIEW` / reviewer | N4 → N7 | **V,R**; exact output/evidence bundle; close assignment; +S | `REVIEW_APPROVED`; decision digest |
| `REJECT_REVIEW` / reviewer | N4 → N5 | **V**; close assignment; +S | `REVIEW_REJECTED`; decision digest |
| `REQUIRE_REMEDIATION` / reviewer | N4 → N6 | **V**; close assignment; +S | `REMEDIATION_REQUIRED`; requirement digest |
| `CREATE_REMEDIATION_TASK` / synthetic director fixture | N5 or N6 → unchanged source plus new task N0 | source remains immutable; new task links `remediates_task_id` and source links successor; +S on new task only | `REMEDIATION_TASK_CREATED`; new task ID |
| `ROUTE_DIRECTOR_GATE` / synthetic director fixture | N7 → N8 | exact approved review and immutable gate-routing input; +S | `DIRECTOR_GATE_READY`; evidence digest |

`COMPLETE_*`, `FAIL`, `YIELD`, and `CONTINUE` reject stale worker fences before evidence or state mutation. Recovery never acts on N2 because M0.3A cannot determine or cancel external effects; a governance block from N2 fences and clears the claim, records the uncertainty, and permits no later worker-effect transition. Review result and remediation races serialize: whichever committed event first changes N4 wins; the other sees a tuple mismatch and is denied. There is no retry of a completed/reviewed attempt and no resurrection of a cancelled, superseded, closed, or director-gated tuple.

## 3. Request, idempotency, and transaction protocol

Canonical request bytes are UTF-8 canonical JSON: recursively lexicographic keys, no insignificant whitespace, integers only where fields are integers, RFC3339 UTC timestamps, lowercase hex digests, sorted sets by their canonical member bytes, and explicit `null` fields. The canonical request binds runtime ID, attachment ID, operation key, operation, task/attempt IDs, synthetic actor fixture and role, expected full tuple, every expected generation/fence/claim/review assignment, immutable task-definition and resolved assignment/head IDs, evidence references and digests, transition arguments, repository generation and Git bundle, and exact frozen M0.2 receipt/input bundle when required. `operation_key` is caller-supplied uniqueness scope; `request_digest=sha256(canonical_request_bytes)` is distinct.

For every mutating request, the sole cooperative scheduler performs this exact ordering:

1. acquire owner-only runtime lock `scheduler.lock` using `O_CREAT|O_EXCL`, record runtime ID, attachment ID, PID, nonce and creation time; reject another live holder; a suspected stale lock requires liveness evidence and a separately recorded takeover,
2. outside the SQLite writer transaction, resolve a candidate Git bundle and frozen M0.2 receipt; dirty worktree, changed/missing immutable input, unsupported ref, or invalid receipt is a candidate denial,
3. open a new SQLite connection, verify required PRAGMAs, and `BEGIN IMMEDIATE`,
4. verify immutable local runtime and attachment identity,
5. look up `idempotency_results` by `(runtime_id, operation_key)` **before any mutable tuple/CAS/fence check**: same `request_digest` returns its stored committed result exactly; different digest rejects key reuse,
6. for a new key, load current task/attempt/claim/review rows and validate the matrix, CAS tuple, generations, fence, roles, evidence, and receipt,
7. re-resolve the Git head and hash the precise authoritative files while the cooperative lock remains held; compare this final bundle to the candidate bundle and to the request's bound bundle. A mismatch atomically applies `BLOCK_GOVERNANCE` if that row is permitted, otherwise denies without authorization,
8. allocate logical event sequences, append exactly one event, mutate every materialization, and store one immutable idempotency result in the same transaction,
9. commit; only then release the lock and return the stored result.

Any exception before commit rolls back event, state, generations, claim/review rows and idempotency record together. A post-commit/pre-response failure is recovered by the exact idempotent retry at step 5 even though CAS values have advanced. Reusing a key with changed evidence or arguments is never a retry. A host process that ignores the lock or rewrites Git/SQLite remains outside M0.3A's local trust boundary.

## 4. Schema, events, replay, and genesis

Schema v1 tables are `runtime_meta`, `tasks`, `attempts`, `claims`, `review_assignments`, `events`, `evidence_refs`, `idempotency_results`, `snapshots`, `migration_ledger`, and `runtime_anchors`. Foreign keys are enabled per connection; unique constraints cover task IDs, `(task_id,attempt_no)`, active claim, active review assignment, `(runtime_id,operation_key)`, global sequence, and `(task_id,task_sequence)`. Normal runtime SQL denies `UPDATE`/`DELETE` on events and immutable evidence/idempotency records through triggers and restricted connection usage. These are detection controls, not defense against a hostile local administrator.

An event has: logical `event_id`; runtime/attachment IDs; global and task sequences; global and task predecessor IDs/digests; task and attempt IDs; operation and operation key/request digest; actor fixture and structural role; complete previous/next tuple; previous/next scheduler, dispatch, and fence values; claim ID/fence/lease facts; reviewer assignment ID/generation; task-definition digest and resolved assignment/head identity; repository generation and complete Git/policy/STOP/project/capability bundle; exact M0.2 receipt and authoritative input bundle digests; immutable evidence IDs/digests; canonical arguments/result digests; timestamp; and `event_digest` over all preceding immutable fields.

Genesis is logical global sequence 0 with fixed predecessor ID `GENESIS` and digest of canonical `GENESIS`; it stores schema version, runtime ID, attachment-manifest digest, repository identity, origin remote, source commit, frozen M0.2 commit, root constitution/AGENTS digests, full project-state digest, complete STOP-set digest, task/dependency/handoff/assignment digests, policy/capability bundle, and creation timestamp. The first normal event is global sequence 1 with the genesis event as predecessor; each task's first event has task sequence 1 and predecessor `TASK_GENESIS:<task_id>`. SQLite rowids are storage details only. Logical sequences are allocated from committed metadata inside the transaction, so committed chains are contiguous and rollbacks leave no logical gap.

Replay starts at genesis and derives/compares: imported task definition/version, all tuple dimensions, current and historical attempts, active/closed claims and fences, reviewer assignments, every generation/counter, repository generation/receipt, supersession/remediation links, evidence references, idempotency results (including canonical committed response), task/global heads, and snapshot roots. Startup and export run integrity, foreign-key, sequence, predecessor, tuple, chain and full replay/materialization equality checks; any duplicate, gap, reordering, wrong task/attempt substitution, impossible tuple, extra materialized row, or missing result makes the runtime unavailable. No automatic repair exists.

## 5. Git binding, checkout attachment, migrations, backups, snapshots

The runtime directory is owner-only. Its owner-only external `attachment.json` contains a random attachment ID/nonce, runtime ID, canonical real checkout path, Git common-dir identity, origin remote, repository root marker digest, frozen M0.2 commit, and genesis digest. Genesis binds the attachment manifest digest. Startup compares both directions. A copied database in another checkout, even at the same commit, fails because its external attachment/path/nonce binding differs. A coordinated copy of database, attachment, Git checkout and all local anchors remains outside local-only assurance.

Git/SQLite serialization is the lock protocol in section 3. Git input changes while idle are imported only through `IMPORT_REPOSITORY`; changes after a claim and before start block N1 to B0; during N2 they block to B0 and prohibit later effect-authorizing worker transitions; during N3/N4 they block to B1 and revoke any reviewer assignment. Revalidation never restores a claim and B1 returns to N3 for a fresh reviewer assignment. Every decision-bearing row marked **R** requires an exact current receipt plus resolved task/assignment/head binding.

Migrations refuse unknown newer versions and downgrades. Before a migration, create a WAL-safe backup with the SQLite backup API from a consistent read connection into a temporary destination; verify integrity and atomic-rename it with owner-only permissions. Raw `.db` copying while WAL exists is forbidden. Execute schema change, migration ledger metadata, and a representable `SCHEMA_MIGRATED` event in one exclusive transaction. A failed migration rolls back to the prior usable schema; if that cannot be proven, runtime availability is denied. Snapshot export is distinct: after replay verification, hold one SQLite read transaction, read its coherent database view and exact Git bundle, canonicalize selected non-secret state/events, hash it, and write the snapshot atomically. Snapshots exclude credentials, attachment nonce, WAL bytes, and live database files.

## 6. Required acceptance and failure-injection cases

Every case asserts initial tuple, canonical request, intervening action, final tuple, event count/head, generations/fence, and exact idempotency outcome. Tests must cover each matrix row and at least these named cases:

| Case | Initial / request / intervening condition | Required result |
| --- | --- | --- |
| genesis/import | no DB; initialize, then valid import | genesis 0 then one event; N0; exact bound digests |
| each allowed edge | source row; valid request | exactly listed target, one event, stated counter changes |
| default deny | unlisted tuple/operation or invalid source | no event/state/result mutation |
| lost response | valid claim commits; inject failure after commit before response; resend same key/request | same stored claim result, no second event despite stale CAS |
| altered idempotency | committed key; resend changed evidence/argument | key-reuse denial, no mutation |
| stale worker | recover/yield/retry then old worker start/progress/fail/complete/evidence | stale-fence denial before evidence/state mutation |
| recovery | N1 with liveness evidence | old claim closed, N0, +S/+D/+F, one recovery event |
| continuation | N2 valid continuation | N2, same claim/fence, counter +1, S +1 |
| retry | retryable failed attempt | predecessor immutable; new attempt  n+1 at N0; old output unusable |
| remediation | N5/N6 create linked task | source unchanged; linked new task N0; no history mutation |
| review fencing | N3 assign then N4 approve/reject/require remediation | owner/reviewer role and fixtures differ; stale/revoked reviewer denied |
| approval routing | N7 route gate twice | first N8; second terminal denial; review remains APPROVED |
| governance races | N1/N2/N3/N4 then task/dependency/assignment/handoff/STOP/project/Git change | B0/B0/B1/B1; claim/review fenced; subsequent authorization denied until revalidated |
| serialization | mutate Git between candidate and final check | no decision commit; permitted block or denial; no TOCTOU authorization |
| chain/replay attacks | alter/reorder/delete/duplicate/gap/wrong predecessor/task/attempt/materialization | startup/export unavailable |
| attachment copy | attach copied DB to other checkout, stale nonce, wrong freeze | startup unavailable |
| atomic writes | inject failure after each event/state/claim/result write point | no partial event/state/generation/idempotency residue |
| migration/backup | WAL frames committed; backup/restore, failed migration, downgrade, unknown newer | consistent restore; atomic rollback or unavailable; no raw-copy path |
| coherent snapshot | concurrent attempted writer while read snapshot is open | one coherent root, no mixed state/Git bundle |
| M0.2 binding | stale/missing/altered receipt or assignment head | denial/block with no duplicate decision semantics |
