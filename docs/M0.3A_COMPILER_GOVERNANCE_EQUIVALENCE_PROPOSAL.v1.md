# M0.3A compiler governance-equivalence proposal v1

Proposal ID: `GOV-M0-3A-COMPILER-EQUIVALENCE-001`

Status: `PROPOSED / PENDING OWNER DECISION AND FORMAL 05 SKEPTIC REVIEW`

Effect while pending: none
Authorizing use: `DENY`

## 1. Scope of the proposed equivalence

If accepted through the process below, a compiler-generated per-site witness
may replace the *manual construction* of the same witness. The compiler does
not replace semantic review, independent acceptance, predecessor preservation,
classification-manifest publication, repository validation, or any safety or
release gate.

Equivalence is restricted to an exact registered rule-family version. It never
applies to a similar keyword, sibling constraint, different census, changed
schema dialect, changed compiler, changed registry, ambiguous site, or
unregistered family. Compiler output remains `CANDIDATE_ONLY / DENY` until an
accepted successor classification manifest incorporates exact reviewed witness
identities through the promotion procedure in §7.

The first proposed calibration family is only:

- family ID: `DRAFT_2020_12_EXACT_LOCATION_MINLENGTH_V1`;
- census namespace: `SCHEMA`;
- dialect: `https://json-schema.org/draft/2020-12/schema`;
- keyword: `minLength` with a non-Boolean, nonnegative integer bound;
- instance domain: string;
- metric and equation: `UNICODE_CODE_POINT_COUNT >= bound`;
- unit: Unicode code points;
- applicability: exact pinned schema document and JSON Pointer only;
- non-domain behavior: no assertion from this keyword; and
- ambiguity exclusions: unsupported/root-mismatched dialect or ID, nested
  dialect or ID, dynamic/recursive reference, external/encoded reference, or
  unresolved local reference.

No other family is implicitly registered.

## 2. Closed rule-family contract

Every acceptable registry entry MUST bind all of the following:

1. stable family ID and version;
2. exact census namespace and frozen census profile/hash;
3. eligibility predicate over frozen site records and pinned source bytes;
4. exact observed-syntax shape and type rules;
5. semantic subject, instance domain, metric, operator, unit and bound mapping;
6. exact-location, ancestor, containing-subschema and source-digest bindings;
7. non-domain behavior and explicit nonclaims;
8. complete ambiguity predicates and required `AMBIGUOUS` reason codes;
9. deterministic witness shape and canonical ordering;
10. accepted calibration site IDs and their expected semantic projections;
11. disallowed overlaps with other registered families; and
12. rule-entry digest using a versioned domain separator.

Eligibility is closed-world. A site either matches exactly, is explicitly
ambiguous, or is nonmatching. Unknown/malformed inputs invalidate compilation;
they are not silently omitted or coerced into a family.

## 3. Compiler and registry identity

An acceptance package MUST identify the complete compiler source closure,
entrypoint, rule registry, interpreter/runtime profile, canonical JSON profile,
test manifest and exact Git commit. At minimum it MUST contain:

- raw SHA-256 for every compiler-closure file;
- domain-separated aggregate compiler-closure digest;
- raw SHA-256 and domain-separated self-digest for the versioned rule registry;
- exact frozen discovery and accepted-classification raw hashes;
- exact compiler command and supported interpreter profile;
- a declaration that no network, clock, environment secret, writable cache,
  random value or caller-selected census participates in output; and
- two isolated-run output hashes proving deterministic reproduction.

## 4. Exhaustive witness and census requirements

The candidate ledger MUST contain exactly one record for every site in the
frozen census, including sites outside the family. Each record MUST bind:

- namespace and stable site ID;
- exact path/module or schema ID and JSON Pointer;
- source byte length and raw SHA-256;
- observed syntax and syntax/AST identity where applicable;
- one disposition: `ACCEPTED_REFERENCE_MATCH`, `CANDIDATE_ONLY`, `AMBIGUOUS`,
  or `NONMATCHING`;
- deterministic reason codes for ambiguity/nonmatch;
- derived semantics only for exact eligible sites;
- accepted-reference identity where applicable; and
- `authorizing_use: DENY`.

Verification MUST independently reconstruct the census and prove:

1. expected and observed `(namespace, site_id)` sets are equal in both
   directions;
2. every identity occurs exactly once;
3. canonical ordering is exact;
4. source-site, schema-site, source-input and schema-input aggregate digests
   equal the frozen manifest;
5. all disposition counts recompute from witnesses;
6. every accepted calibration projection matches field-for-field; and
7. separate domain-digests bind the witness ledger and complete output.

Duplicate, missing, unexpected, reordered, stale, mismatched or colliding
records invalidate the whole package. Partial success is not evidence.

## 5. Required adversarial and preservation evidence

The minimum regression package MUST demonstrate rejection of:

- forged semantic subject, metric, operator, bound, unit or domain;
- positive authorization or governance-equivalence substitution;
- stale/changed discovery, classification, input or source digest;
- site-ID, namespace, coordinate, source, ancestor or containing-context
  mismatch;
- duplicate, omission, unexpected site, ordering change or identity collision;
- accepted-reference substitution or accepted semantic mismatch;
- unsupported dialect, nested dialect/ID, dynamic/external/unresolved
  references and invented/removal of ambiguity;
- noncanonical/duplicate-key JSON and malformed host types;
- compiler, registry, interpreter-profile or command substitution; and
- nondeterministic output across two clean isolated runs.

The package MUST also prove:

- V55 and every predecessor are byte-for-byte unchanged;
- H-M0-179 and H-M0-180 preservation tests pass;
- accepted counts do not change during compilation or review;
- production repository validation, compilation and diff checks pass; and
- failures cannot emit partial accepted evidence.

An accepted historical artifact is never rewritten or rebased. Corrections use
versioned successors with explicit lineage.

## 6. Owner decision versus independent reviewer decision

### Owner may authorize

The owner may:

- adopt this contract as the permitted process for a named exact family;
- establish the external trust root and reviewer-appointment mechanism;
- name the policy ID, scope, validity, revocation and required evidence;
- authorize creation of the registry and a bounded acceptance package; and
- after all conditions are satisfied, authorize the Director to publish a
  successor classification manifest.

Owner authorization alone MUST NOT accept a witness, authenticate a reviewer,
declare semantic correctness, change V55 counts, clear a STOP, or authorize
release.

### Independently authenticated 05 Skeptic must approve

The independent reviewer must:

- be a distinct canonical actor, not an author or conflicted actor;
- hold a current externally authenticated `05 Skeptic` role and exact
  `M0_3A_COMPILER_GOVERNANCE_REVIEW` scope;
- claim the exact review subject and disclose conflicts;
- independently reconstruct the census and reproduce deterministic output;
- review compiler closure, rule semantics, ambiguity policy, manual
  calibration, exhaustive coverage and all adversarial tests;
- issue `APPROVE` or `DENY` bound to exact proposal, compiler, registry,
  census, accepted predecessor, ledger and evidence hashes; and
- publish, commit and push the formal review and attestation.

The reviewer cannot create or expand the rule while approving it. A requested
change creates a new proposal/registry version and invalidates the prior
approval subject.

## 7. Promotion criteria

A `CANDIDATE_ONLY` witness may enter accepted classification evidence only when
all of these are true:

1. the owner has approved this exact proposal version and exact family scope;
2. a versioned registry and compiler-closure manifest satisfying §§2–3 exist;
3. an externally authenticated, unexpired authority policy maps a distinct
   canonical actor to the required role and scope with conflicts/revocation;
4. that actor issues a valid subject-bound approval attestation after
   independently reproducing §§4–5;
5. the candidate package is regenerated from the exact current frozen inputs
   and matches the formally approved hashes;
6. a proposed successor classification manifest preserves the exact V55
   constraint prefix and appends only complete reviewed constraint records
   whose site-ID sets and semantic projections exactly match the formally
   approved candidate witnesses, with no historical evidence rebase;
7. the authenticated reviewer separately verifies the final successor diff
   and its production validation; and
8. the Director publishes the accepted successor only after steps 1–7, with
   complete audit/handoff lineage.

Compiler status, a green test, engineering review, owner approval, or a signed
Git commit alone satisfies none of these promotion steps. Counts change only
through the final accepted successor manifest. STOP and release decisions
remain separate.

## 8. Formal reviewer mechanism gap

The repository does not currently provide an operationally supported method to
appoint or authenticate a formal 05 Skeptic reviewer. `docs/OPERATIONS.md`
requires distinct accountable actors and explicitly says authentication and
enforcement are pending M0. The existing `authority-policy` and
`approval-attestation` schemas and `risk_controls` verifier provide useful
local shapes and conflict checks, but they assume a verifier-controlled policy
already authenticated by an external source. No external source, trust-root
fingerprint, signature verifier, reviewer appointment registry, revocation
channel, or binding from those records into the Skeptic review workflow is
provisioned.

The smallest sufficient setup is:

1. owner selects an external identity/trust controller separate from the
   compiler author and records its out-of-band root fingerprint/source;
2. the controller issues a signed, versioned policy mapping one distinct actor
   to role `05 Skeptic`, the exact review scope, aliases, conflicts, validity,
   authority generation and revocation channel;
3. a verifier adapter authenticates policy source/signature against the
   configured root rather than trusting the literal `VERIFIED_EXTERNAL` field;
4. the reviewer claims the review with canonical actor ID, policy generation,
   exact subject hashes and conflict disclosure;
5. the reviewer issues a signed approval/denial attestation binding the exact
   proposal, compiler, registry, census, predecessor, ledger and evidence
   digests; and
6. repository validation verifies the policy, attestation, non-self-review,
   validity/revocation and exact subject before treating the review as formal.

Because the current v1 policy and attestation schemas use
`additionalProperties: false` and cannot carry authenticated signature
material, the setup also requires versioned signed-policy and
signed-attestation successors, or typed detached-signature envelopes, binding
the complete canonical record bytes, signer/key identity, algorithm, external
credential or certificate chain, and revocation/current-generation evidence.
Repository validation must verify those artifacts against the out-of-band
root; a self-digest or `VERIFIED_EXTERNAL` literal is insufficient.

Until that setup exists and is independently tested, every native/subagent
review remains engineering feedback only and this proposal remains pending.

## 9. Safety state

This proposal does not implement V56, a new proof family, a registry, an
appointment mechanism, a release closure, public-verifier attachment, STOP
resolution, execution or capital capability. Data remains BLOCKED; all STOPs
remain OPEN; M0 remains blocked; M1 remains unreleased; authorization remains
`DENY`; executor remains `MOCK_ONLY`; live remains `LOCKED`; kill remains
`ENGAGED`; deployable capital remains USD 0.
