# M0.3A successor runtime format v1

## Status and authority boundary

This document specifies **runtime format 2**. It does not change the active
runtime, reinterpret format-1 rows, accept M0.3A, clear a STOP, establish
positive currentness, authenticate an M0.2 receipt, create an R-gate, attach an
executor, or authorize paper/live/capital activity.

Every artifact defined here is locally integrity-checkable but initially
`UNANCHORED / UNKNOWN / DENY`. A hash chain whose database, heads, verifier, and
checkpoints can all be rewritten by the same hostile local actor is not an
authentic history. External anchoring is a separate authority milestone.

## Why a successor is required

Format 1 remains preserved evidence. Its bounded replay reconstructs task
tuples, owners and remediation lineage, attempts, claims, reviews, and links,
but does not replay-derive idempotency rows, complete runtime metadata, seals,
migrations, or snapshots. Task-event hashes omit the global predecessor ID and
other semantic coordinates. The current migration path is v1-to-v1 bookkeeping,
and coordinated complete-chain rewrites cannot be detected from mutable local
heads alone.

Runtime format 2 must close those representation gaps without claiming that
local integrity is external authenticity.

## Version vocabulary and negotiation

- `runtime_format_version` describes tables, replay closure, and persistence.
- `event_format_version` describes the canonical event envelope and digest.
- The first supported pair is exactly `(2, 2)`.
- Readers and writers must require an exact supported pair before reading any
  mutable state. Missing, boolean, fractional, lower, higher, or mixed versions
  deny. There is no best-effort downgrade or unknown-field tolerance.
- Format-1 storage is never parsed through a format-2 reader. A dedicated
  migration reader verifies format 1 using its frozen implementation and emits
  a new side-by-side format-2 runtime.

Negotiation is format-dispatched. First acquire the common runtime lock, parse
and semantically verify the selector without opening a database, and use only
descriptor-relative/no-follow file access for identity preflight. A generation-
zero `V1_ACTIVE` selector invokes only the frozen format-1 read-only diagnostic
verifier and migration builder; `EDG2` metadata is neither expected nor read by
that path. Unknown selector formats deny.

For `V2_ACTIVE`, preflight verifies that the selected main database has an
SQLite header, the fixed filename and descriptor identity, owner-only mode, and
only the permitted WAL/SHM names. The lock-held SQLite open may then perform
normal crash recovery; this is the sole mutation allowed before full semantic
verification. After recovery, verify `application_id = 1162102578`
(`0x45444732`, `EDG2`), `user_version = 2`, the closed manifest and runtime/file
identity, the exact storage descriptor and live structural inventory against
`storage_schema_sha256`, the schema
registry, genesis, complete replay, and materializations. Recovery that cannot
complete cleanly, or any post-recovery mismatch, quarantines the runtime and
denies further mutation. No command writer or migration begins before all of
those checks pass.

## Canonical encoding and digest domains

Canonical JSON is `EDGELAB_CANONICAL_JSON_V1`: UTF-8; object keys sorted by
Unicode code point; no insignificant whitespace; ASCII escapes; integers only;
no floats, NaN, infinities, duplicate keys, or Unicode normalization performed
after validation. Strings are hashed exactly as validated.

All digests are lowercase SHA-256 and domain separated:

```text
blob = SHA256("EDGELAB\0BLOB\0V2\0" || canonical_json)
event = SHA256("EDGELAB\0EVENT\0V2\0" || canonical(envelope_without_event_sha256))
table_root = SHA256("EDGELAB\0TABLE\0V2\0" || table_name || "\0" || canonical(ordered_rows))
checkpoint = SHA256("EDGELAB\0CHECKPOINT\0V2\0" || canonical(checkpoint_without_checkpoint_sha256))
manifest = SHA256("EDGELAB\0MANIFEST\0V2\0" || canonical(runtime_manifest))
selector = SHA256("EDGELAB\0SELECTOR\0V1\0" || canonical(selector_without_selector_sha256))
legacy_archive = SHA256("EDGELAB\0LEGACY_ROWS\0V1\0" || canonical(exact_legacy_rows))
legacy_projection = SHA256("EDGELAB\0LEGACY_PROJECTION\0V1\0" || canonical(projection_without_projection_sha256))
legacy_columns = SHA256("EDGELAB\0LEGACY_COLUMNS\0V1\0" || table_name || "\0" || canonical(column_names))
legacy_table_rows = SHA256("EDGELAB\0LEGACY_TABLE_ROWS\0V1\0" || table_name || "\0" || canonical(ordered_rows))
legacy_storage = SHA256("EDGELAB\0LEGACY_STORAGE\0V1\0" || canonical(storage_inventory))
schema_registry = SHA256("EDGELAB\0SCHEMA_REGISTRY\0V2\0" || canonical(schema_registry))
schema_document = SHA256("EDGELAB\0SCHEMA_DOCUMENT\0V2\0" || canonical(schema_document))
storage_schema = SHA256("EDGELAB\0STORAGE_SCHEMA\0V2\0" || canonical(storage_descriptor))
selector_history = SHA256("EDGELAB\0SELECTOR_HISTORY\0V1\0" || canonical(selectors_in_generation_order))
sqlite_structure = SHA256("EDGELAB\0SQLITE_STRUCTURE\0V2\0" || canonical(full_pragma_observation))
sqlite_compile_options = SHA256("EDGELAB\0SQLITE_COMPILE_OPTIONS\0V2\0" || canonical(sorted_compile_options))
```

The implementation must use one shared encoder. Re-serialization by SQLite,
language defaults, or a caller is not authoritative. JSON Schema validates
shape; a pure semantic verifier must recompute every equation above.

## Storage-schema prerequisite

There is no DDL whitespace normalization. `storage_schema_sha256` uses the
`storage_schema` equation over canonical JSON for a closed
`schemas/m0-3a-runtime-storage.v2.json` descriptor. That descriptor must fix an
ordered inventory of every table, index, column, SQLite affinity, nullability,
default, primary-key position, foreign key, uniqueness rule, and exact creation
statement, plus the expected canonical results of `table_xinfo`,
`foreign_key_list`, and `index_xinfo`. Object order is `type,name`; subordinate
records use the ordinal returned by the named PRAGMA. Implicit/unlisted schema
objects deny.

The descriptor, its JSON Schema, compiled-in verifier digest, and positive and
negative live-database fixtures are an implementation prerequisite. Until they
exist, no format-2 database, manifest, migration, selector cutover, or verifier
result is constructible or valid. An implementation may not substitute
normalized `sqlite_schema.sql`, because its rendering is not the canonical
contract.

The descriptor pins the reported SQLite `3.50.0` version, exact
`sqlite_source_id()`, and the domain-separated digest of the sorted full
`PRAGMA compile_options` result. A different reported version, source ID, or
compile-options digest is `UNSUPPORTED / DENY`; changing any of them requires a
new descriptor version. These values define the supported compatibility tuple;
they are not proof of binary or distribution provenance. Its
`structural_observation_sha256` is the `sqlite_structure` digest of one closed
object containing: the reported engine version and source ID;
the exact application ID, user version, encoding, foreign-keys, journal-mode,
and synchronous PRAGMAs; every `(type,name,tbl_name,sql)` row from
both `sqlite_schema` and `sqlite_temp_schema`, schema-tagged and ordered by
`schema,type,name`, except `sqlite_stat%`; the complete raw `PRAGMA table_list`
result; and, for each descriptor table in name order,
the complete raw `table_xinfo`, `foreign_key_list`, `index_list`, and every
listed index's `index_xinfo` rows in SQLite-returned order. This includes
implicit primary-key indexes. Any object, field, row, order, SQL text, or
PRAGMA-result difference denies.

The descriptor's `tables`, `foreign_keys`, `indexes`, and `root_projections`
are closed semantic projections and human review aids. They must agree with the
executable DDL, but they do not replace the full structural observation hash.
Likewise, `STRICT` tables and foreign keys do not establish runtime meaning by
themselves. The descriptor's closed `semantic_predicates` list is verifier-
enforced: singleton/cardinality rules, format and authority values, digest and
timestamp forms, checkpoint/export sequencing, canonical-JSON equality, and
total ascending-BINARY root order must all hold before a future verifier can
report consistency. The currently published pure verifier intentionally has
no consistency-success state and accepts no runtime image content beyond the
exact descriptor.

SQLite integers are signed 64-bit. Every nonnegative persisted integer is
therefore bounded above by `9223372036854775807`; booleans never satisfy an
integer field. Canonical table-root rows are JSON arrays in descriptor column
order, with strict JSON null/string/integer cell values and rows sorted by the
descriptor's explicit key. Canonical-JSON database columns contain the exact
ASCII canonical text, not a caller serialization or base64 wrapper.

## Content-addressed blobs

Variable event content is stored once in a `blobs` table with exact columns
`sha256`, `schema_id`, and `canonical_json`. The digest is recomputed from the
canonical bytes. `schema_id` must resolve in the closed registry digest named by
the runtime manifest; unknown schemas deny. Payload, request, response, and
before/after state are event references to these blobs, never untyped JSON
accepted directly by replay.

Before a writer for an event type can exist, that type's payload and state
schemas must be closed, versioned, registered, and covered by negative tests.

`schemas/m0-3a-schema-registry.v2.schema.json` binds schema documents and an
exact event-to-payload/state/request/response mapping. Documents are sorted by
`schema_id`; event bindings are sorted by `event_type`; each ID and event type
appears exactly once, all referenced IDs exist with the required content role,
and the full set equals the event-envelope vocabulary. The manifest's registry
digest uses the `schema_registry` equation. A nonempty but unregistered or
wrong-role `schema_id` denies semantic verification.

Runtime schema bytes live in a closed `schema_documents` table with exact
`schema_id,document_sha256,canonical_json` columns. Replay rehashes retained
bytes, requires JSON Schema validity and `$id == schema_id`, rejects duplicate
IDs and network/file resolution, and compares the exact inventory to registry
documents. References resolve only inside this retained table. Bootstrap uses
the verifier release's compiled-in SHA-256 pins for the manifest and registry
schemas before mutable runtime data is trusted; the verifier's dependency-
closure digest is bound by genesis/bridge. The current checkout and network are
never schema authorities. This is still local code trust, not an external
witness.

`document_sha256` uses the `schema_document` equation over the parsed canonical
schema document. Checkpoints include a separate `schema_documents` table root;
the registry digest and that root must independently agree with the same exact
document inventory.

## Event envelope 2

The machine contract is
`schemas/m0-3a-event-envelope.v2.schema.json`. Every event binds:

- runtime and chain IDs;
- event ID, exact event type, UTC timestamp, and contiguous global sequence;
- global predecessor event ID **and** digest;
- stream kind and, for task events, task ID, attempt, task sequence, and task
  predecessor event ID **and** digest;
- transaction ID, position/count, operation key, request digest, and response
  digest;
- schema-tagged content-addressed payload and before/after state references;
- repository generation and exact repository bundle digest; and
- an authority-binding digest fixed to null until the separate
  currentness/R-gate milestone exists.

`event_sha256` covers every field above. Task sequences start at one. A task
event therefore participates in
both the task-local and global chains without relying on an unhashed column.
Event IDs, task IDs, attempts, sequences, stream kind, and predecessor IDs can
no longer be substituted while retaining the old digest.

Global sequence zero is a runtime-stream `RUNTIME_GENESIS` or
`LEGACY_V1_BRIDGE`. Its predecessor ID is exactly
`FORMAT2_GENESIS_PREDECESSOR`; its predecessor digest is
`228a5eca65d6da5649229c520a9c922c7de239b821e362beddadacdf278f5a99`,
the SHA-256 of the exact bytes
`EDGELAB\0EVENT\0V2\0GENESIS_PREDECESSOR`. Later events bind the exact
immediately preceding event ID and digest.

For a task attempt's first event (`task_sequence = 1`), let `C` be canonical
JSON for `{"attempt":<integer>,"chain_id":<string>,"task_id":<string>}`. Its
task-root digest is
`SHA256("EDGELAB\0EVENT\0V2\0TASK_PREDECESSOR\0" || C)`. Both the task
predecessor digest and the lowercase-hex suffix of predecessor ID
`FORMAT2_TASK_PREDECESSOR:<digest>` must equal that value. Later task events
bind the immediately preceding event ID and digest for the same task and
attempt. Any arbitrary sentinel, cross-task predecessor, gap, or reuse denies
semantic verification.

Format 2 corrects future wire names to `TASK_YIELDED`, `TASK_FAILED`, and
`REVIEW_REJECTED`. Migration preserves the exact format-1 strings and bytes in
the legacy projection; normalization is an explicit bridge mapping, never a
rewrite of retained history.

## Command transactions and idempotency

Each mutating command is one SQLite transaction and one contiguous event group:

1. All events share `transaction_id`, `operation_key`, request digest, response
   digest, repository binding, and group count.
2. Positions start at zero, are contiguous, and occupy a contiguous range of
   global sequence numbers.
3. `event_count` includes all semantic events plus the final commit event.
   Exactly one final `COMMAND_COMMITTED` lists the ordered semantic event IDs
   (not itself), pre-command global head, post-command semantic head, operation,
   request reference, response projection reference, and result.
4. Materialized changes, blobs, semantic events, the commit event, idempotency
   row, and new heads commit atomically. Any exception rolls back all of them.
5. Replay derives the idempotency table solely from committed command groups.
   The same key and request returns the exact recorded response; a different
   request denies. Orphan, overlapping, reordered, duplicate, or partially
   committed groups deny.

The response projection is computed before event hashes and excludes the commit
event ID/digest and final global head; the returned response may add those
self-derived fields, but they are not part of `response_sha256`. This order is
acyclic: request/response blobs, semantic events, commit payload, commit event,
final head, then materialized idempotency row.

Genesis and the legacy bridge are the only single-event system-transaction
exceptions to `COMMAND_COMMITTED`. Their operation keys are exactly
`system:v2:genesis` and `system:v2:legacy-bridge`; callers cannot supply them.
Caller keys are stored as `v2:<chain_id>:<caller_key>`.

Format-1 idempotency rows are archive-only. They cannot seed active format-2
idempotency, synthesize a committed response, or authorize a retry. The active
format-2 table starts empty, and all format-1 protocol retries after cutover
deny without mutation.

## Genesis, manifest, and replay closure

The closed manifest contract is
`schemas/m0-3a-runtime-manifest.v2.schema.json`. A new runtime begins with one
`RUNTIME_GENESIS`; a migrated runtime begins with one `LEGACY_V1_BRIDGE` that is
also its format-2 genesis. Sequence zero uses the fixed predecessor above.

The manifest has no self-digest field. Its canonical bytes are digested by the
`manifest` equation only after the genesis/bridge event digest is known, and
that full manifest digest is pinned by the selector and later checkpoints. The
genesis/bridge payload instead binds the runtime ID, chain ID, attachment,
format versions, schema-registry digest, storage-schema digest, and—when
applicable—the complete legacy-source coordinates directly. It MUST NOT bind
the full manifest digest, because the manifest contains the genesis event ID and
digest. A mismatch denies.

## Active-runtime selector and recovery states

`schemas/m0-3a-active-runtime-selector.v2.schema.json` is the only active
runtime selector. Its filename is exactly `active-runtime.json`; its temporary
name is `.active-runtime.next`. The only active storage names are:

- format 1: `runtime.sqlite` plus `attachment.json`; or
- format 2: `runtime.v2.sqlite`, `attachment.v2.json`,
  `runtime.v2.manifest.json`, and the transient SQLite sidecars
  `runtime.v2.sqlite-wal` and `runtime.v2.sqlite-shm` when present.

All names are single path components under one descriptor-pinned runtime root;
aliases, links, traversal, alternate names, and multiple selectors deny. The
selector binds its generation, prior-selector digest, exact active filenames,
runtime ID, manifest digest, latest local checkpoint when any, and
`UNKNOWN / DENY`. Generation zero has no predecessor; every later selector
binds the prior selector digest. The selector digest uses the equation above.
This local chain is not an external rollback witness.

The two format-2 sidecars are permitted only when the active selector names the
matching format-2 main database. They must be regular, owner-only,
descriptor-verified files in the pinned runtime root; links, alternate names,
or sidecars while format 1 is active deny as `CUTOVER_UNCERTAIN`.

Before replacing the active copy, write the exact selector bytes once with
exclusive creation to `selectors/<generation-as-20-digits>.json`, fsync the
file and `selectors/`, and verify the complete contiguous retained selector
chain. `selector_history_path` must equal the current generation path and
`prior_selector_path` the immediately previous path. Generation zero is exactly
v1; every later generation is exactly v2. The runtime-root inventory is closed
to the selector files, fixed active files, lock, checkpoints/backups, and the
single declared pending directory. Unexpected entries deny. Joint rollback of
the whole local selector history remains undetectable without an external
anchor and therefore remains `UNKNOWN/DENY`.

`selector_history_sha256` uses the equation above over the complete canonical
selector objects, including each selector's own digest, in contiguous
generation order beginning at zero. An empty history is invalid.

The only recovery classifications are:

- `ABSENT_SELECTOR`: allowed only for a structurally exact legacy-v1 directory;
  diagnostics may read it, but mutation and migration deny until a generation-0
  `V1_ACTIVE` selector is durably bootstrapped.
- `V1_ACTIVE`: selector and exact v1 files agree; no v2 file is active.
- `V2_BUILD_PENDING`: selector remains `V1_ACTIVE`; the only permitted staging
  path is `runtime.v2.pending/` containing a closed `migration-state.json` in
  phase `BUILDING`, `VERIFIED`, or `READY_TO_CUTOVER`. Pending state is never
  selected for ordinary reads or writes.
- `CUTOVER_UNCERTAIN`: selector temp/active state, rename durability, file
  identity, or migration phase cannot be proved. Authority-bearing reads and
  all mutations deny; no automatic deletion, rollback, or completion occurs.
- `V2_ACTIVE`: selector, v2 manifest, attachment, database, and replayed
  identity agree. Legacy files remain immutable archive inputs only.

The migration-state record binds migration ID, phase, v1 selector digest, v1
storage/backup/projection/archive digests, pending manifest/database/attachment
digests, expected v2 selector digest, and timestamps. Its exact closed schema
is an implementation prerequisite before migration code; the three pending
phases above are exhaustive.

Selector bootstrap is the sole mutation allowed from `ABSENT_SELECTOR`: acquire
the common lock; perform complete read-only v1 verification and closed directory
inventory; exclusively create/fsync the generation-zero history record; write
and fsync `.active-runtime.next`; rename it to `active-runtime.json`; fsync the
root; reopen and verify. It never changes the database or attachment. An
interruption yields either still-absent state or `CUTOVER_UNCERTAIN`, never
inferred success.

Replay starts from the manifest and genesis/bridge, processes the complete
global chain, validates each blob and registered schema, reconstructs every
task chain and command group, and derives all materialized rows. It must exactly
compare, with strict scalar types and a closed column set:

- runtime metadata and both chain heads;
- tasks, attempts, claims, reviews, and remediation links;
- idempotency requests and responses;
- exactly one deterministic `RUNTIME_GENESIS_IDENTITY` attachment/genesis seal
  and no mutable-head seal;
- migration records, the runtime manifest, the active selector coordinates,
  and one digest of the complete verified external selector history (selector
  files are not duplicated row-by-row in SQLite);
- snapshot/checkpoint records and roots, with checkpoints and exports sharing
  the single `snapshots` materialization distinguished by a closed kind; and
- the content-addressed blob inventory and schema-registry digest.

Extra rows, columns, tables, triggers, views, indexes outside the exact schema,
missing rows, or differing derived values deny startup, read, backup, export,
snapshot, migration, and mutation. SQLite integrity and foreign-key checks are
necessary but not sufficient.

Repository-import events must reconstruct repository-global generation,
bundle history, affected-task fencing, and every task-local generation. No
materialized metadata value is accepted merely because it is self-consistent.

## Checkpoints, snapshots, and external anchors

The local checkpoint contract is
`schemas/m0-3a-runtime-checkpoint.v2.schema.json`. It binds the manifest, chain
head, prior checkpoint, and ordered roots for events, metadata, tasks, attempts,
claims, reviews, remediation links, idempotency, seals, migrations, snapshots,
blobs, schema documents, the schema registry, and the legacy-archive root.
Every root is a digest. A NEW runtime hashes the empty ordered
`legacy_archive` row array; it never substitutes null. Checkpoint
rows are replay-derived from checkpoint events; exported snapshots contain the
complete replay closure, not only tasks and event tables.

Construction is acyclic. Under the lock, take a stable **pre-registration cut**
at head `H` and compute roots excluding the candidate checkpoint document, its
payload blob, checkpoint row, `RUNTIME_CHECKPOINTED`, and that command's
`COMMAND_COMMITTED`. `through_global_sequence` and `head_event_*` identify `H`.
The canonical checkpoint document is inserted as a content-addressed DB blob in
the same transaction that appends the two registration events and materializes
the row. Checkpoint `K+1` covers registration artifacts for `K`. An external
checkpoint file is a regenerable export of a registered blob; its absence or a
partial `.pending` export does not invalidate the runtime and it is never part
of the active directory inventory. Sequence zero requires a null prior
checkpoint; later checkpoints bind the immediately preceding checkpoint digest.

Local checkpoints are always `LOCAL_UNANCHORED / UNKNOWN / DENY`. They detect
accidental or partial mutation relative to a separately retained copy, but not
a hostile rewrite of the database, checkpoints, and mutable heads together.

A future external-anchor contract must pin an exact checkpoint digest outside
the runtime, identify an independently trusted key/service and generation,
support revocation, and be verified before any stronger claim. That contract is
not defined here and cannot be inferred from a local signature or Git commit.

## Canonical format-1 archive and projection

The closed projection and raw archive contracts are
`schemas/m0-3a-legacy-v1-projection.v1.schema.json` and
`schemas/m0-3a-legacy-v1-row-archive.v1.schema.json`. The logical archive
covers exactly these tables and column orders:

| Table | Column order | Row order |
|---|---|---|
| `meta` | `k,v` | `k` |
| `seals` | `runtime_id,attachment_id,attachment_digest,genesis_digest,created_at,seal_digest` | `runtime_id` |
| `tasks` | `task_id,attempt,workflow,execution,review,scheduler_generation,dispatch_generation,task_fence,claim_id,reviewer_id,continuations,repository_generation,receipt_digest,owner,reviewer,predecessor_task,successor_task` | `task_id` |
| `attempts` | `task_id,attempt,predecessor_attempt` | `task_id,attempt` |
| `claims` | `claim_id,task_id,attempt,fence,status,actor` | `claim_id` |
| `reviews` | `assignment_id,task_id,actor,role,status` | `assignment_id` |
| `idempotency` | `operation_key,request_digest,response` | `operation_key` |
| `runtime_events` | `event_id,global_seq,event_type,payload,event_digest,prev_id,prev_digest` | `global_seq,event_id` |
| `task_events` | `event_id,task_id,attempt,task_seq,global_seq,event_type,before_json,after_json,payload,event_digest,prev_task_digest,prev_global_digest` | `global_seq,event_id` |
| `remediation_links` | `link_id,source_task,child_task,source_event,child_event,decision_digest,link_digest` | `link_id` |
| `migration_ledger` | `migration_id,from_version,to_version,artifact_digest,backup_ref,backup_digest,result,created_at` | `migration_id` |
| `snapshots` | `snapshot_id,digest,generation,global_head,created_at` | `snapshot_id` |

The exact meta-key inventory is the schema's fixed list. SQLite values are
archived as tagged cells: `NULL` with null, `INTEGER` with a JSON integer,
`TEXT` with the exact decoded UTF-8 string, and `BLOB` with canonical base64.
`REAL` and unknown storage classes deny. JSON stored in `TEXT` is archived
exactly as text; a separate semantic projection may parse it with duplicate-key
denial, but may not replace the raw cell. Each row is a canonical array in the
column order above. The archive schema fixes every table name, row width,
tagged-cell representation, attachment encoding, and physical storage entry;
the frozen semantic verifier additionally enforces each column's expected
SQLite storage class and the exact row ordering shown above.
Base64 is RFC 4648 standard alphabet with required padding and zero unused pad
bits. The verifier decodes with strict validation, re-encodes with padding, and
requires byte-for-byte equality; encodings such as `AB==` and `AAB=` deny.

The archive is a canonical object keyed by the table order above and digested
with `legacy_archive`. Each table projection records its exact column-inventory
digest, versioned row-schema ID, row count, and ordered-row digest. The
projection also binds attachment bytes, the sidecar-free main-DB storage
inventory (physical evidence, not logical state), SQLite backup, global head, repository
generation/bundle, closed legacy-name mapping, and archive digest.
`source_projection_sha256` uses the `legacy_projection` equation.

For each table, `columns_sha256` and `ordered_rows_sha256` use the
`legacy_columns` and `legacy_table_rows` equations. Row schema IDs are fixed by
the projection schema as JSON Pointer references into the raw archive schema.
The physical storage inventory contains exactly one owner-only regular file
named `runtime.sqlite`, with closed `name,type,mode,size,sha256` fields, and is
digested by `legacy_storage`. Any format-1 WAL/SHM sidecar makes the source
ineligible for migration because the frozen format-1 verifier rejects it. Such
files may be hashed into a separate nonconforming diagnostic record, but never
into this canonical archive or projection and never recovered, checkpointed,
or mutated by the migration builder. The state remains `CUTOVER_UNCERTAIN`
pending an explicit future recovery contract. Storage inventory never
substitutes for the logical archive.

Exact legacy event strings remain in the archive. Only the closed mapping
`TASK_YIELDD→TASK_YIELDED`, `TASK_FAILD→TASK_FAILED`, and
`REVIEW_REJECTD→REVIEW_REJECTED` may appear in a normalized bridge view.

## Non-destructive v1-to-v2 migration

Migration is side-by-side and one-way:

1. Acquire one exclusive runtime lock and hold it through verification, backup,
   projection, format-2 build, verification, and cutover. The current v1 method,
   which releases the common lock between backup and bookkeeping, is not this
   migration path.
2. Verify format 1 with the frozen v1 verifier and verify that no WAL/SHM
   sidecar exists. Produce a consistent SQLite backup, exact attachment bytes,
   an exact sidecar-free main-DB storage inventory, exact row archive,
   canonical full-state projection, and their SHA-256 digests. Do not modify,
   vacuum, normalize, or add rows to the v1 database.
3. Build a new temporary format-2 directory and database. The
   `LEGACY_V1_BRIDGE` binds source runtime/attachment IDs, storage-inventory and
   backup hashes, source global head ID/digest, exact row archive and projection
   digests, migration-plan digest, immutable verifier commit and dependency-
   closure digest, explicit `V16_BOUNDED_REPLAY_ONLY` assurance class, and
   source repository bundle.
4. Preserve caller-supplied v1 receipt strings only as explicitly untrusted
   legacy content. Set `authority_binding` to null and all authorizing use to
   `DENY`; migration must never manufacture or backfill a receipt.
   Format-1 `meta` fields outside v16's checked projection, seals, idempotency,
   migration ledger, and snapshots are likewise raw archive-only evidence. They
   must not seed active v2 metadata, seals, retries, migrations, snapshots, or
   runtime authority. The only normalized legacy projection is v16's verified
   global sequence/head consistency plus task tuples, owners/lineage, attempts,
   claims, reviews, remediation links, and exact task-event semantics. Even
   those remain a `V16_BOUNDED_REPLAY_ONLY` diagnostic projection, not active
   v2 scheduler rows. A migrated v2 scheduler begins with no active tasks.
5. Replay and compare the pending runtime. Require a successful locked
   `wal_checkpoint(TRUNCATE)`, close every SQLite connection, verify the pending
   WAL/SHM files are absent, then fsync the sidecar-free database, attachment,
   manifest, and staging directory. Rename pending files
   to fixed final names while the selector still says v1, then fsync the runtime
   root. Write and fsync `.active-runtime.next`, atomically rename it over
   `active-runtime.json`, fsync the runtime root again, reopen through the
   selector, and complete read-only replay before reporting success.
6. Keep the original v1 database and attachment immutable. There is no dual
   writer. Before the first pending-to-final rename, rollback means
   quarantining or removing only the unselected pending build while v1 remains
   active. Once the selector has cut over to v2 and any active format-2 write
   commits, falling back to v1 would discard history and must deny pending
   explicit recovery from a verified checkpoint.

Before the first pending-to-final file rename, failure leaves the proven v1
selector active and quarantines pending output for diagnosis. From that first
file rename—including each file rename, root fsync, selector-history creation,
active-selector rename, final fsync, and verified reopen—an interruption is
`CUTOVER_UNCERTAIN`, never assumed rollback or success and never silently
deleted. A selector swap is local
availability state, not an external history anchor or authorization.

## Crash and concurrency requirements

- One descriptor-pinned runtime root and one cooperative exclusive lock cover
  every writer, backup, snapshot, migration, and cutover operation.
- SQLite runs with foreign keys, WAL, `synchronous=FULL`, and explicit
  transaction modes; the implementation verifies the effective profile.
- On format-2 startup, while holding the runtime lock, the implementation opens
  the selected database normally so SQLite can recover a valid WAL, then checks
  database identity, `integrity_check`, replay closure, and all manifest roots.
  It does not open an active WAL database as immutable. Malformed, linked,
  wrong-mode, mismatched, or format-1-selected sidecars deny. Checkpoint or WAL
  truncation occurs only through an explicit locked maintenance operation.
  Backups and exports use SQLite's backup API, never a raw copy of the main
  database or sidecars.
- Startup denies leftover ambiguous cutover state, multiple active manifests,
  unknown side databases, stale temporary manifests, or a manifest/database
  identity mismatch.
- Durable rename order and directory fsync behavior must be tested with
  injected failure at every boundary. No test may claim power-loss safety from
  transaction rollback alone.

## Acceptance matrix

At minimum, implementation tests must prove denial of:

| Threat | Required falsification |
|---|---|
| Unknown/mutated versions | Change one manifest, genesis, event, selector, DDL, or schema-registry version without coherently rewriting every retained descendant; startup denies. |
| Event-coordinate substitution | Rehash after changing task, attempt, stream, predecessor, generation, transaction, or key while retaining a descendant/checkpoint; replay denies. |
| Idempotency forgery | Change a request/response/row, omit its commit event, or reuse a key without a coordinated complete rewrite; replay denies. |
| Metadata/genesis/seal forgery | Change any value or add a row while retaining a derived descendant/root; replay comparison denies. |
| Migration forgery | Change source backup/head/archive/projection/plan, reorder mapping, or reinterpret a v1 typo while retaining bridge descendants; verification denies. |
| Snapshot forgery | Add, delete, reorder, or rewrite checkpoint/root/snapshot data while retaining a later root or external copy; replay denies. |
| Partial command/crash | Inject failure before and after every event, materialization, idempotency, manifest, fsync, and rename boundary; pre-state or complete post-state is the only result. |
| Repository drift | Change authoritative bundle during a command/migration; transaction and cutover deny. |
| Complete local rewrite | Rehash every local record and head; local consistency may pass, but anchor status remains `UNANCHORED`, currentness `UNKNOWN`, and authorizing use `DENY`. No stronger result is permitted. |
| Rollback after v2 activity | Replace the selector with v1 while retained v2 selector/checkpoint evidence remains; startup denies. Joint rollback of all local evidence remains `UNKNOWN/DENY` without an external anchor. |

Positive tests must cover new runtime initialization, multi-event commands,
lost-response retry, repository import with unaffected/stale tasks, remediation,
review, snapshot/export, backup/restore, pre-cutover migration failure, atomic
cutover, empty-active-state legacy archival migration, and read-only restart.
All examples remain synthetic. Failure injection covers each individual final-
file rename, root fsync, history-selector creation/fsync, active-selector
rename, final root fsync, and reopen.

2. Publish and freeze the exact storage-schema descriptor prerequisite; then
   implement the canonical encoder, digest domains, schema registry, and pure
