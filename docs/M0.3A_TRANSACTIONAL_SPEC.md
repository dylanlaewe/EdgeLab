# M0.3A transactional scheduler specification

This is an implementation contract only. It consumes frozen M0.2 evidence at
`bc3a40924ca580ca6eddc4c24e32ff99ddd95330`; it does not modify M0.2, attach an
executor, authenticate workers, clear STOP, or authorize M1.

## State and attempts

`workflow_state`: `READY`, `BLOCKED`, `CANCELLED`, `SUPERSEDED`, `COMPLETED`.
The last three are terminal. `execution_state`: `CLAIMABLE`, `CLAIMED`,
`IN_PROGRESS`, `BLOCKED`, `FAILED`, `COMPLETED`; terminal execution states are
`BLOCKED`, `FAILED`, `COMPLETED`. `review_state`: `NOT_REQUIRED`,
`REVIEW_PENDING`, `REVIEWING`, `REJECTED`, `REMEDIATION_REQUIRED`, `APPROVED`,
`READY_FOR_DIRECTOR_GATE`; the last four except remediation are terminal for an
attempt. All newly created attempts begin READY/CLAIMABLE/NOT_REQUIRED.

Allowed transitions only: READY→CLAIMED→IN_PROGRESS; IN_PROGRESS→COMPLETED,
FAILED, BLOCKED, REVIEW_PENDING; REVIEW_PENDING→REVIEWING→APPROVED, REJECTED,
REMEDIATION_REQUIRED; APPROVED→READY_FOR_DIRECTOR_GATE; any nonterminal may
become BLOCKED or CANCELLED by policy; workflow may become SUPERSEDED only by a
new linked task. No terminal resurrection. Claim increments task generation and
returns fencing generation. Continuation preserves task/attempt/assignment and
increments dispatch generation. Retry after retryable FAILED creates a new
attempt and fences all earlier attempts. Remediation creates a new linked task.

Every matrix row specifies expected generation, permitted synthetic actor role,
evidence digest requirements, event type, idempotency outcome and claim effect:
claim requires Director synthetic role and no active claim; progress requires
matching fencing generation; complete requires completion evidence; review
assignment/result requires distinct structural reviewer role; recovery requires
expired liveness plus a fencing event. Other rows deny.

## Atomic algorithm and idempotency

Each operation uses `BEGIN IMMEDIATE`: load immutable runtime identity and task;
verify expected CAS generation, transition matrix, claim fence, Git binding and
receipt; compute a canonical semantic fingerprint of operation, task, attempt,
actor fixture ID, expected generation, evidence digest, receipt and arguments;
look up existing fingerprint; if present return its committed result; otherwise
insert event, update materialized state/generation, record fingerprint and
commit. Any failure rolls back the whole transaction. Lost responses repeat the
same fingerprint and return the original committed transition without creating a
second event. Random request IDs are correlation metadata only.

Lease expiry is only liveness suspicion. Recovery is an explicit transaction
that verifies expiry, advances fencing generation, marks the old claim fenced,
emits `RECOVERED`, and returns CLAIMABLE. A stale worker can never write after
its fencing generation changes. M0.3A actors are explicitly synthetic and
unauthenticated fixtures.

## SQLite, events, replay, and snapshots

Use local SQLite outside Git: `journal_mode=WAL`, `synchronous=FULL`,
`foreign_keys=ON`, busy timeout 5 seconds, single-process local locking,
per-operation connections, owner-only directory/database permissions, and
`PRAGMA integrity_check` at startup/export. Corruption, foreign-key failure,
duplicate sequence, malformed row, chain mismatch, or replay mismatch makes the
runtime unavailable; no automatic repair. Backup before migration; migrations
are monotonic, transactional, evented, downgrade-refusing, and unknown future
schema versions refuse startup.

Event fields: runtime ID, schema version, global and per-task sequence, event
ID/type, task/attempt, previous/next states, actor fixture ID, claim fence,
scheduler generation, semantic request digest, M0.2 receipt, evidence digests,
previous global/task event digests, Git/policy digests, timestamp, canonical
event digest. Global sequence is unique; `(task_id, task_sequence)` is unique.
State update and event insert share one transaction. Replay from genesis in
sequence order must exactly reproduce materialized state.

Genesis binds immutable runtime ID, canonical repository identity, source Git
commit, M0.2 freeze, project ID, schema version, creation timestamp, initial
generation and genesis digest. Startup preflights repository, freeze, project
and STOP; applies/verifies migration; verifies identity/genesis; runs integrity
and replay; then becomes available. Incompatible Git binds fail closed.

Snapshots contain runtime ID/schema/generation, global head/count, per-task
heads, materialized summary, source Git commit/freeze, policy/project/STOP
digests, timestamp and canonical snapshot digest—never private keys. Hash chains,
sequence continuity, replay and surviving snapshot anchors detect ordinary
mutation/deletion/reordering/partial rollback. Coordinated rollback of DB and
every newer anchor is outside local proof.

## Git binding and governance changes

Git is authoritative for project/STOP/task/policy/capability definitions and
M0.2 eligibility; SQLite is authoritative for current runtime state. Before
claim/dispatch/review transitions, revalidate Git bindings and M0.2 receipt.
Changed bound Git content invalidates READY/CLAIMABLE work. During IN_PROGRESS,
STOP/project change emits a synthetic pause/block event and prevents new future
effects; M0.3A has no executor semantics. A stale M0.2 receipt is invalid when
any bound digest changes and requires a new decision.

## Acceptance matrix

Data must prove: double claim; stale generation; fenced old worker; duplicate
semantic transition; lost-response retry; invalid transition; terminal
resurrection; atomic event/state behavior; replay equality; mutation/deletion
detection where anchored; restart after commit and uncommitted work; wrong-repo
DB; stale Git/receipt; STOP/project changes before and during work; dependency
version change; fingerprint collision resistance; schema mismatch; snapshot
correctness; corruption fail-closed. Skeptic independently reviews each
security-significant boundary.
