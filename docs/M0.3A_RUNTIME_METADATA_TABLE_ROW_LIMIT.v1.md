# Runtime-v2 metadata table row limit

Status: **CLASSIFIED RESOURCE MAXIMUM / INCOMPLETE / DENY**

This evidence classifies one previously discovered resource site only: the
Discovery V4 positional `metadata` table-row ceiling in
`src/edgelab/runtime_v2_image.py:inspect_runtime_image_host`.

## Accepted equation

For an exact `RuntimeImage` whose `table_snapshots` field is an exact built-in
tuple with exactly `len(_TABLE_SPECS)` members, the snapshot paired by strict
zip with `_TABLE_SPECS[6]` must have an exact built-in tuple `rows` field and:

```text
len(captured['table_snapshots'][6].rows) <= 1
```

The maximum is inclusive. Zero rows is admitted by this resource check and one
row satisfies it; two or more rows adds `TABLE_ROW_LIMIT` at `/6/rows`, marks
accounting incomplete, skips row inspection, and prevents a sanitized image
from being returned. This is not a minimum, exactly-one, singleton-validity,
metadata-validity, or completeness claim.

## Positional binding

The cap is selected by position 6 in
`enumerate(zip(captured['table_snapshots'], _TABLE_SPECS, strict=True))`, not
by the supplied `snapshot.table` label. A hostile label cannot select another
cap or bypass the inclusive maximum. The outer exact-cardinality gate must
pass before the strict zip is entered. Exact snapshot type and field-presence
guards, the non-blocking table-identity diagnostic regardless of supplied
label match, and the exact rows-tuple guard precede `len(rows)`.
