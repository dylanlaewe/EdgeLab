# M0.3A transition semantic-event construction limit v1

## Status and scope

This additive evidence contract freezes the exact narrow source-level claim
required to classify `MAX_GROUP_EVENTS`. Despite the constant name, this is
only the private `TransitionIntent.semantic_event_ids` construction ceiling.
It is not the valid semantic-event count of an operation, a transaction-group
limit, an envelope `event_count` limit, or a schema acceptance claim.

The classification is valid only while the definition, direct comparison,
exact joint tuple guard, preceding argument bound, later UUID traversal,
rejection result, enclosing method/class/module, evidence, predecessor,
schema, manifest, and self-digest bindings remain exact. Missing, stale,
aliased, inconsistent, or partially refreshed evidence fails closed.

## Preconditions and enforcement order

1. `operation` must have exact built-in `str` type.
2. `arguments` and `semantic_event_ids` must both have exact built-in `tuple`
   type. Lists and tuple subclasses reject before caller-controlled length or
   iteration behavior can run.
3. The independent `MAX_ARGUMENTS` predicate runs first.
4. Built-in `len(self.semantic_event_ids)` applies the inclusive 10,002-item
   equation and overflow raises exact `TRANSITION_RESOURCE_EVENTS` at
   `/semantic_event_ids`.
5. Argument member shape and ordering checks run later.
6. Every admitted semantic-event item is then checked as a UUID4 string.
7. Operation-specific counts and duplicate rejection occur only in later
   transition logic, not in construction.

The constructor stores the exact admitted tuple object without copying,
truncation, slicing, deduplication, sorting, or substitution.

## Relational reconciliation and known slack

The same and adjacent numeric values elsewhere do not express this subject.
For a valid `IMPORT_REPOSITORY` group:

```text
affected task IDs                     <= 10000
semantic events / semantic IDs        = affected + 1 <= 10001
complete envelope events with commit  = semantic + 1 <= 10002
maximum zero-based position            = total - 1 <= 10001
constructor semantic-event allowance                  <= 10002
```

Thus the constructor ceiling has one item of slack relative to the largest
semantically realizable import transition. A tuple of 10,002 valid semantic
IDs can construct, but no current operation can validly consume it. This is a
documented limitation, not valid-group evidence.

The following remain explicitly unclassified by this slice: import affected
task limits, import semantic-event tuple limits, commit-payload
`semantic_event_ids.maxItems`, envelope `event_count` and `position`, response
cardinalities, `_expect_events` count and duplicate checks, and the source
assignments that preserve the relationships above. A future group-wide claim
requires Discovery V3 relational-flow and schema-site bindings first.
