# M0.3A runtime top-level blob cardinality limit v1

## Status and scope

This additive evidence contract defines the exact semantic claim required to
classify `MAX_BLOBS` in the private runtime-image host preflight. It does not
change runtime behavior, complete the resource inventory, authorize release
generation, establish reducer or public-verifier acceptance, clear a STOP, or
authorize execution or capital.

The classification remains valid only while its source, Discovery V3 census,
schema, manifest, evidence, predecessor, and self-digest bindings remain
exact. Any missing, stale, aliased, inconsistent, or incompletely reproduced
binding fails closed.

## Exact semantic claim

```text
constraint_id: MAX_BLOBS
classification: RESOURCE_MAXIMUM
semantic_subject:
  EXACT_BUILTIN_TUPLE_ITEM_COUNT_OF_CAPTURED_RUNTIME_IMAGE_BLOBS
unit: ITEMS
maximum: 300,000
```

For an exact `RuntimeImage` whose required slots were completely captured and
whose top-level `blobs` value was admitted as an exact built-in tuple, the
accepted equation is:

```text
0 <= len(captured top-level blobs tuple) <= 300,000
```

The literal lower bound is tautological for an exact tuple. This classification
is only the inclusive upper bound on supplied top-level blob records. It counts
every tuple item before record type, record fields, UTF-8 size, body byte size,
digest, schema, uniqueness, reachability, table cross-equality, or canonicality
validation. An item need not be a valid `BlobRecord` to count.

## Preconditions and enforcement order

The governing function is
`src/edgelab/runtime_v2_image.py:inspect_runtime_image_host`. The exact order
is:

1. require exact built-in `RuntimeImage` input;
2. capture every required top-level slot, returning early if capture is
   incomplete;
3. bind the literal `blobs` subject to its captured value;
4. require the value to have exact built-in type `tuple`;
5. skip cardinality length inspection when that type guard fails;
6. load the same captured branch through the literal V3 cardinality row;
7. evaluate `0 <= len(value) <= MAX_BLOBS`;
8. write the result to `cardinality_valid["blobs"]`;
9. on failure, add `IMAGE_CARDINALITY_LIMIT` for artifact `blobs` at `/`
   and mark accounting incomplete;
10. only a cardinality-valid branch reaches blob-record type, field type,
    UTF-8 accounting, body accounting, per-body byte-size, and clean-record
    reconstruction work; and
11. any finding withholds the sanitized image, while the report remains
    non-authorizing.

The complete normalized function and module ASTs are mandatory. The scalar
assignment and derived row alone are insufficient evidence for capture,
type-guard precedence, diagnostic emission, member-loop suppression, image
withholding, or authority.

## Boundary and separation matrix

Let `M = 300,000`. Dedicated evidence must use an otherwise valid host image.

| Case | Supplied branch | Required result |
| --- | --- | --- |
| empty | exact tuple of length `0` | no blob-cardinality finding |
| maximum minus one | exact tuple of length `M - 1` | no blob-cardinality finding; sanitized records preserve count and order |
| maximum | exact tuple of length `M` | no blob-cardinality finding; sanitized records preserve count and order |
| maximum plus one | exact tuple of length `M + 1` | exact `IMAGE_CARDINALITY_LIMIT`, artifact `blobs`, coordinate `/`; no image or accounted totals |
| hostile collection | non-tuple length-bomb object | `IMAGE_FIELD_TYPE` before length inspection |
| hostile subclass | tuple subclass | `IMAGE_FIELD_TYPE`; no cardinality attribution |
| over-count plus hostile member | `M + 1` items with a callback-bomb member | cardinality finding only; blob-record loop skipped |
| valid-count invalid member | one non-`BlobRecord` item | no cardinality finding; separate exact `IMAGE_RECORD_TYPE` |
| over-count plus oversized body | `M + 1` records with one over-byte body | cardinality finding only; member-size loop skipped |
| at-count plus oversized body | `M` records with one over-byte body | no cardinality finding; separate exact `IMAGE_ITEM_BYTE_LIMIT`; oversized bytes are accounted |
| independent table over-count | empty top-level blobs tuple and `M + 1` minimally valid rows in the `blobs` `TableSnapshot` | no top-level cardinality finding; separate exact `TABLE_ROW_LIMIT` at `/1/rows` |

The evidence must also prove input immutability, stable item order at admitted
boundaries, table-row-limit separation, per-member-size separation,
sibling-cardinality independence, fixed `DENY`, and non-Boolean report
behavior.

  comparing record/body length instead of tuple length;
- removing the invalid-branch continuation, result write, diagnostic,
  accounting failure, member-loop guard, or image withholding;
- changing the diagnostic code, artifact, or coordinate;

  cardinality;

- changing fixed deny-only or non-Boolean result behavior;
- changing evidence, schema, predecessor, ancestry, or self-digest bytes; or
- refreshing attacker-controlled ordinary census and manifest digests around
  semantic source drift.

## Explicit exclusions

  canonicality, uniqueness, ordering, or fixed-point reachability;
- the separately classified `MAX_BLOB_BYTES` body ceiling or its definition
  and enforcement sites;
- total accounted input, root work, memory, storage, or database size;
- events, schema-document, table-snapshot, checkpoint-copy, or
  selector-history cardinality;
- any reducer requirement that `set(blobs)` equal the exact reachable digest
  set, or any group-specific reachable-blob calculation;
- successful reducer or public-verifier acceptance of a boundary fixture; or
- runtime release, STOP clearance, scheduling, execution, wagering, or
  capital authority.

In particular, passing this private host-preflight count does not prove that
any supplied blob is referenced, valid, unique, canonical, or equal to the
`blobs` table. The reducer may reject a tuple with even one supplied record.
