# M0.3 — Runtime Foundation

## Boundary

M0.2 at `bc3a40924ca580ca6eddc4c24e32ff99ddd95330` is the frozen pure
eligibility decision engine. M0.3 adds a local scheduler runtime; it does not
execute tasks. A later executor receives only a runtime-authorized typed request.
`STOP-M0-001` remains OPEN, M0 remains blocked, M1 remains unreleased, and all
capital remains locked.

## Storage and transaction model

Use one local SQLite database outside Git, in WAL mode with foreign keys enabled.
SQLite supplies atomic claim/transition transactions, uniqueness constraints,
durable queue state, and crash recovery without a distributed service. JSON in
Git remains schemas, policy, immutable reports, and milestone snapshots.

Tables: `tasks`, `attempts`, `claims`, `events`, `evidence`, `receipts`,
`identities`, `revocations`, `usage_ledgers`, and `continuations`. Every mutable
row has a generation. A transition uses `BEGIN IMMEDIATE`, checks expected
generation/state, appends one event, updates current state, and commits. A stale
compare-and-swap, duplicate idempotency key, duplicate active claim, or invalid
transition rolls back. Startup replays verified events against materialized
state; incomplete transactions are rolled back by SQLite.

Allowed state vocabulary: `READY`, `CLAIMED`, `IN_PROGRESS`, `BLOCKED`,
`COMPLETED`, `REVIEW_PENDING`, `REVIEWING`, `REJECTED`,
`REMEDIATION_REQUIRED`, and `READY_FOR_DIRECTOR_GATE`. Only a valid transition
table may move between them. Writer-slot ownership is an exclusive claim row,
not a Git convention.

## Evidence, identity, and receipts

Events are append-only database rows with sequence, task/attempt, previous and
next state, actor key ID, evidence references/digests, decision receipt, and a
hash of the prior event. Exported signed evidence snapshots go to Git; local
database integrity detects mutation/deletion relative to the latest snapshot but
does not claim hostile-host immutability.

Each local workload identity has an encrypted private key outside Git, a public
key ID, role, allowed task assignment, expiry, rotation and revocation state.
Workers sign start/progress/complete assertions; independently assigned
reviewers sign review assertions. This proves local workload identity only. It
does not replace external KMS/human authority required for STOP clearance or
capital decisions.

Receipts bind the accepted M0.2 receipt, resolved assignment-head identity,
runtime transaction/version, event sequence, actor key ID, evidence digests and
policy digest. They become authenticated when signed with the runtime identity.
Replay is denied by unique event IDs, sequence, task/attempt binding and nonce.

## Continuation and budgets

`IN_PROGRESS` workers submit signed progress with a bounded continuation count,
deadline and usage. A valid continuation reclaims the same task/attempt; a
timeout moves to `BLOCKED` or `REMEDIATION_REQUIRED` according to policy.
Continuation and attempt budgets prevent loops. External-authority blockers
escalate to a human; ordinary retryable failures do not require a human prompt.

## Model, capability, and executor contracts

A machine-readable policy maps role/action to `MECHANICAL`, `STANDARD`,
`DEEP_REASONING`, or `ADVERSARIAL`, with defaults, escalation preconditions,
per-task/milestone/continuation budgets and usage ledger requirements. Unknown
tiers or exhausted budgets deny. Runtime configuration maps tiers to available
models later; no silent escalation is allowed.

Capability registry entries remain reviewed metadata. Runtime binds only pinned,
approved, unrevoked capability IDs to a task request; it does not install or
activate them. Future executor request fields are closed and typed: task,
attempt, role, repository/assignment identity, allowed operation/capabilities,
model tier, resource limits, input evidence, expected outputs, STOP/project and
decision receipts, and runtime authorization. Responses are likewise closed:
started, progress, blocked, failed, completed, evidence, usage, outputs and
commit references. Unknown fields deny.

## Synthetic executor gate

Before any Codex invocation: transaction/event store accepted by Skeptic;
workload identity and signed evidence accepted; policy and usage enforcement
accepted; typed executor request/response accepted; STOP/project recheck at
transaction; capability allowlist empty except local fixture read/write; isolated
temporary sandbox; network, credentials, plugins, MCP, sports data, paper/live
and capital paths prohibited. The first invocation may only read a synthetic
fixture and write a bounded temporary artifact.

## Threats and separation

Controls address stale tasks/receipts, replay, duplicate workers/reviewers,
self-review, concurrent claims, rollback, event mutation/deletion, stale policy,
budget exhaustion, continuation loops, forged executor responses, wrong
repository, prohibited capabilities, and STOP/project changes during work.
External KMS identity remains a parallel STOP-clearance track; convergence is
only at an evidence-linked human/Risk authority gate.

Due diligence, without installation or cloning, will inventory official OpenAI
plugin/skill material, sports-data skills, research/data-analysis skills, and
orchestration patterns. Each candidate enters the registry with source, pinned
version, provenance, permissions, network/credential/executable flags, review,
approval and revocation fields.
