# M0.3A transition task-record resource limit v1

## Status and scope

This additive evidence contract freezes the exact narrow source-level claims
required to classify `MAX_TASKS`. The constant governs two related private
task-record cardinality predicates: the exact built-in task tuple supplied to
`ReducerState` construction, and the current transition-workspace task-key
count plus validated writes that introduce previously absent task keys.

It is not a global task-table, task-history, workload, event, group, import,
operation, strategy, or execution limit. It creates no permission to allocate
100,000 tasks. It does not establish a memory bound, database bound, whole-
image bound, or public-verifier acceptance claim.

The classification is valid only while both definitions/comparisons, the
container guard, prospective-cardinality derivation, write-shape and CAS
checks, rejection results, enclosing methods/classes/module, evidence,
predecessor, schema, manifest, and self-digest bindings remain exact. Missing,
stale, aliased, inconsistent, or partially refreshed evidence fails closed.

## Exact semantic claims

```text
constraint_id: MAX_TASKS
classification: RESOURCE_MAXIMUM
unit: ITEMS
maximum: 100000

binding 1 subject:
  EXACT_BUILTIN_TUPLE_TASK_ITEMS_SUPPLIED_TO_REDUCER_STATE_CONSTRUCTION

binding 2 subject:
  CURRENT_TRANSITION_WORKSPACE_TASK_KEYS_PLUS_VALIDATED_ABSENT_KEY_TASK_WRITES
```

The accepted equations are:

```text
for ReducerState.tasks having exact built-in type tuple:
    len(tasks) <= 100000

after exact delta/write shape and task-write CAS validation:
    len(workspace task keys)
      + count(task writes whose validated current value is absent)
      <= 100000
```

The maximum is inclusive. The first equation proves only passage through the
constructor resource predicate; later member, ordering, uniqueness, and
cross-record checks can still reject. The second equation is prospective and
read-only: replacement of an existing key contributes zero, while each
validated absent-key write contributes one. It neither commits nor reserves a
task record.

## Preconditions and enforcement order

### ReducerState construction

1. Repository generation and bundle digest validate first.
2. `tasks`, `claims`, `reviews`, `decisions`, and `remediation_links` must each
   have exact built-in `tuple` type. A list or tuple subclass rejects before
   caller-controlled task length or iteration behavior can run.
3. `len(self.tasks)` applies the inclusive 100,000-item equation and overflow
   raises exact `TRANSITION_RESOURCE_TASKS` at `/tasks`.
4. Other record-family resource predicates run independently.
5. Task member type, key order/uniqueness, and cross-record invariants run
   later. Passing this cardinality check does not imply full state validity.

### Transition-workspace precheck

1. The delta must have exact private `_TransitionDelta` type.
2. Task-write keys must be nonempty, sorted, and unique; all auxiliary key
   families must be sorted and unique.
3. Every task write must have exact private `_TaskWrite` type and a key equal
   to its `after.task_id`.
4. The current workspace value must equal `write.before`; a stale write fails
   CAS before prospective resource evaluation.
5. `added_tasks` increments by exactly `int(current is None)`. Replacements
   contribute zero and validated absent-key writes contribute one.
6. The prospective equation applies and overflow raises exact
   `TRANSITION_RESOURCE_TASKS` at `/tasks` before auxiliary-family maxima,
   retained-event reuse checks, and final after-task containment.
7. `_precheck` performs no write. Mutation occurs only through a separately
   issued staged object and later `commit` checks.

## Required boundary and adversarial evidence

Dedicated evidence must prove 99,999-, 100,000-, and 100,001-item constructor
outcomes; exact-tuple rejection before hostile length/iteration; overflow
before task-member validation; deterministic code and coordinate; replacement
versus absent-key accounting at the prospective boundary; exact write-shape,
key-set, and CAS failures before resource evaluation; no workspace mutation;
and no authority effect.

The classification must fail closed under changed or same-valued definition
expressions, `>=`, subject or symbol substitution, arithmetic changes,
`added_tasks` initialization or increment changes, replacement/absence test
changes, extra loads/stores, guard deletion/duplication/movement/bypass,
weakened exact-type checks, altered diagnostics, source-level `len` or `int`
shadowing, or changes to `_deny`. Adversarial tests must refresh ordinary
source and census identities around semantic mutations.

## Explicit exclusions and authority boundary

This contract does not establish a global task-table, task-history, event,
group, import-width, operation, queue, concurrency, database, storage, memory,
or workload limit. It does not establish task-member validity, uniqueness,
whole-state consistency, transition correctness, public-verifier acceptance,
closure correctness, release readiness, scientific evidence, strategy
approval, execution, or capital authority.

The cumulative manifest remains `INCOMPLETE`; generation and authorizing use
remain `DENY`; the resource-inventory blocker remains unconditional; live
remains `LOCKED`; deployable capital remains USD 0; the kill switch remains
engaged; and every OPEN STOP remains OPEN. Any unreproduced identity,
boundary, ordering, prospective-accounting, adversarial, or authority fact
leaves `MAX_TASKS` unclassified.
