# M0.3A event-byte resource limit v1

## Status and scope

This additive evidence contract defines the exact semantic claim required to
classify `MAX_EVENT_BYTES`. It does not itself classify the constraint, change
runtime behavior, complete the resource inventory, authorize release
generation, establish public-verifier acceptance, clear a STOP, or authorize
capital or execution.

The classification remains valid only while its source, census, schema,
manifest, test-evidence, predecessor, and self-digest bindings remain exact.
Any missing, stale, aliased, inconsistent, or incompletely reproduced binding
fails closed.

## Exact semantic claim

The constraint is:

```text
constraint_id: MAX_EVENT_BYTES
classification: RESOURCE_MAXIMUM
semantic_subject: EXACT_BUILTIN_BYTES_MEMBERS_OF_CAPTURED_RUNTIME_IMAGE_EVENTS
unit: BYTES
maximum: 1,048,576
```

Its accepted equation is:

```text
for each exact built-in bytes member reached after events tuple and
cardinality validation:

    len(supplied event member bytes) <= 1,048,576
```

The subject is the exact supplied built-in `bytes` object at one indexed
position of the captured `RuntimeImage.events` tuple. The word `bytes` means
Python byte length as measured by `len()` at this source layer. It does not
mean decoded characters, canonical JSON length, event payload length, parsed
event size, retained storage size, or any estimated memory footprint.

This is an inclusive per-member maximum. It is not a limit over the number of
events and is not a sum over two or more event members.

## Preconditions and enforcement order

The governing function is
`src/edgelab/runtime_v2_image.py:inspect_runtime_image_host`.

The event-member comparison is reached only through this order:

1. The candidate's required top-level fields are captured without invoking a
   caller-selected fallback.
2. `events` is required to have exact built-in type `tuple`.
3. The separate event-cardinality rule establishes
   `0 <= len(events) <= MAX_EVENTS`.
4. Only when that cardinality rule is valid does the byte-collection loop
   iterate the supplied tuple.
5. Each iterated member is required to have exact built-in type `bytes`.
6. The exact byte length is added to the separate bounded aggregate-accounting
   calculation.
7. The member is compared with `MAX_EVENT_BYTES` using the inclusive equation
   above.
8. An over-limit member adds `IMAGE_ITEM_BYTE_LIMIT` for artifact `events` at
   its exact `/<index>` coordinate.
9. Any resulting violation prevents construction of the sanitized image.

The classification must bind the complete normalized AST of the governing
function and source module. The scalar definition and comparison alone are
not sufficient evidence for field capture, precondition ordering, diagnostic
emission, exact-byte retention, image withholding, or deny-only authority.

## Boundary acceptance matrix

Dedicated evidence must exercise an otherwise valid host-preflight fixture
with one exact built-in `bytes` event member. `M` below is 1,048,576.

| Case | Exact member length | Required event-byte result |
| --- | ---: | --- |
| maximum minus one | `M - 1` | no `IMAGE_ITEM_BYTE_LIMIT` for `events`; retain the exact supplied member when no unrelated violation exists |
| maximum | `M` | no `IMAGE_ITEM_BYTE_LIMIT` for `events`; retain the exact supplied member when no unrelated violation exists |
| maximum plus one | `M + 1` | exact `IMAGE_ITEM_BYTE_LIMIT`, artifact `events`, coordinate `/0`; withhold the sanitized image |

The evidence must additionally prove:

- an oversized member at a nonzero index reports that exact index;
- accepted members are neither truncated, sampled, replaced, nor reordered;
- a non-`bytes` member is rejected by the member-type rule before this size
  rule is attributed to it;
- invalid event cardinality does not get relabeled as a per-member size
  failure;
- multiple members are each evaluated against the same per-member maximum,
  not against a shared remaining allowance; and
- normal and optimized (`-O`) execution produce the same results.

The matrix concerns this one finding and the sanitized-image consequence. It
does not claim that a boundary fixture is a semantically valid runtime event
or that another independent rule cannot also reject a deliberately hostile
fixture.

## Required adversarial evidence

The classification must fail closed when any attack changes or bypasses its
semantic dependency closure, including:

- changing the maximum or replacing its definition with an alias or literal;
- substituting `MAX_BOOTSTRAP_DOCUMENT_BYTES` for `MAX_EVENT_BYTES`, even
  though both currently have the same numeric value;
- adding another load or store of `MAX_EVENT_BYTES`;
- changing, deleting, duplicating, reordering, slicing, filtering, or
  dynamically constructing the `events` table row;
- changing the branch key, captured subject, row index, loop target, loop
  iterable, or shared comparator;
- changing `>` to `>=`, measuring the collection rather than its member,
  clearing or replacing the iterated values, adding a branch-specific bypass,
  or moving the comparison outside its guarded loop;
- removing, suppressing, renaming, or redirecting the violation;
- changing its artifact or coordinate;
- retaining, truncating, or substituting an over-limit member in the
  sanitized image;
- allowing an image to survive after the violation;
- shadowing or replacing `len` within the bound source closure;
- changing the result's fixed deny-only authority; or
- refreshing only ordinary source, census, schema, manifest, predecessor, or
  self-digests around a semantic mutation.

Adversarial tests must refresh all attacker-controlled ordinary bindings when
that is necessary to demonstrate that the hard-pinned row, loop, function,
module, evidence, predecessor, and exact-manifest checks remain independently
effective.

## Explicit exclusions

This contract does not establish or classify:

- whether an event member contains JSON;
- canonical JSON syntax or canonicality;
- event schema validity, event digest validity, chain validity, task identity,
  timestamp validity, authorization, replay validity, or reducer semantics;
- public-verifier acceptance or support for nonempty events;
- event count or `MAX_EVENTS`;
- `MAX_BOOTSTRAP_DOCUMENT_BYTES` or either sibling table binding;
- total accounted input, root work, stored bytes, database size, or any other
  aggregate or relational limit;
- successful construction of an image when an unrelated field is invalid;
- release-generation readiness or completeness of the broader resource
  inventory; or
- behavior of an unpinned interpreter or externally monkeypatched runtime.

In particular, the current public verifier separately requires unsupported
event inputs to be empty and always remains non-authorizing. This private
host-preflight maximum does not broaden that boundary.
