# M0.3A Transactional Contract v3 — implementation authority

**Planning only.** This is the sole implementation-authoritative M0.3A contract and supersedes v2 and earlier M0.3A planning documents for semantics. They remain immutable review evidence. Data is not released pending independent Skeptic acceptance.

M0.3A is a local SQLite synthetic scheduler. It does not implement authentication, Goal, model policy, executor/Codex, network, plugin/MCP, credentials, external authority, sports research, paper/live work, STOP clearance, M1, or capital capability. Stage 1 M0.2 remains frozen at `bc3a40924ca580ca6eddc4c24e32ff99ddd95330`; M0.3A only binds its exact receipt and inputs. `STOP-M0-001` is OPEN; M0 blocked; executor `MOCK_ONLY`; capital USD 50 conceptual and USD 0 deployable/reserved; live `LOCKED`; kill `ENGAGED`.

## 1. Authority, identities, and state

Git is authoritative for immutable task definitions, dependencies, handoffs, project/STOP/policy/capability state, and frozen M0.2 inputs. SQLite is authoritative only for local runtime state and append-only records. A task tuple is:

`(workflow, execution, review, attempt_no, scheduler_generation, dispatch_generation, task_fence, active_claim_id, reviewer_assignment_id, continuation_count, repository_generation, decision_receipt_digest)`.

`workflow ∈ {ACTIVE,GOVERNANCE_BLOCKED,DIRECTOR_GATE_READY,CANCELLED,SUPERSEDED,CLOSED}`; `execution ∈ {CLAIMABLE,CLAIMED,IN_PROGRESS,EXECUTION_BLOCKED,FAILED,EXECUTION_COMPLETED}`; `review ∈ {NOT_REQUIRED,REVIEW_PENDING,REVIEWING,REJECTED,REMEDIATION_REQUIRED,APPROVED}`. Attempts start at 1 and never reuse; all generations/counters start at 0. A claim is non-null only in `CLAIMED`/`IN_PROGRESS`; a reviewer assignment only in `REVIEWING`. Every unlisted tuple or operation denies before mutation.

Valid tuples are `N0=(ACTIVE,CLAIMABLE,NOT_REQUIRED)`, `N1=(ACTIVE,CLAIMED,NOT_REQUIRED)`, `N2=(ACTIVE,IN_PROGRESS,NOT_REQUIRED)`, `F0=(ACTIVE,FAILED,NOT_REQUIRED)`, `N3=(ACTIVE,EXECUTION_COMPLETED,REVIEW_PENDING)`, `N4=(ACTIVE,EXECUTION_COMPLETED,REVIEWING)`, `N5=(ACTIVE,EXECUTION_COMPLETED,REJECTED)`, `N6=(ACTIVE,EXECUTION_COMPLETED,REMEDIATION_REQUIRED)`, `N7=(ACTIVE,EXECUTION_COMPLETED,APPROVED)`, `N8=(DIRECTOR_GATE_READY,EXECUTION_COMPLETED,APPROVED)`, `B0=(GOVERNANCE_BLOCKED,EXECUTION_BLOCKED,NOT_REQUIRED)`, `B1=(GOVERNANCE_BLOCKED,EXECUTION_BLOCKED,REVIEW_PENDING)`, `C0=(CLOSED,EXECUTION_COMPLETED,NOT_REQUIRED)`, `C1=(CANCELLED,EXECUTION_BLOCKED,NOT_REQUIRED)`, `C2=(CANCELLED,EXECUTION_BLOCKED,REVIEW_PENDING)`, `S0=(SUPERSEDED,EXECUTION_BLOCKED,NOT_REQUIRED)`, and `S1=(SUPERSEDED,EXECUTION_BLOCKED,REVIEW_PENDING)`.

`F0`, N5, N6, N8 and C*/S* are terminal for the stated attempt/task except the explicitly linked new attempt/task below. `APPROVED` is terminal only in review: N7→N8 changes workflow, never review. `task_fence` increases on claim, fencing, recovery, retry, or governance block. `scheduler_generation` increases on every task mutation; `dispatch_generation` increases whenever dispatchability is issued or invalidated.

## 2. Closed task transition matrix

Each row requires the exact source tuple, expected attempt and all expected generation/fence values. **W** requires current claim ID/fence; **V** requires current reviewer assignment/generation, different immutable owner/reviewer roles and different synthetic fixture IDs; **R** requires current exact M0.2 receipt/input bundle. `+S/+D/+F` increment scheduler/dispatch/fence.

| Operation | Source → target and atomic effect |
| --- | --- |
| initialize | none→N0; create attempt 1, task event sequence 1, S/D/F=0 |
| import repository | N0→N0; authoritative bundle differs; advance runtime repository generation; +S |
| claim/start/continue | N0→N1 (**R**, issue claim,+S+D+F); N1→N2 (**W,R**,+S); N2→N2 (**W,R**, continuation+1,+S) |
| yield/fail | N1/N2→N0 (**W**, close claim,+S+D+F); N1/N2→F0 (**W**, immutable failure, close claim,+S+D+F) |
| complete | N2→C0 or N3 (**W,R**, immutable output, close claim,+S+D+F) |
| retry/recovery | F0→new attempt N0 only if retryable (link predecessor,+S+D+F); N1→N0 only with liveness evidence (close recovered claim,+S+D+F) |
| governance/revalidate | N0/N1/N2→B0; N3/N4→B1 (close claim/revoke reviewer,+S+D+F); B0→N0 and B1→N3 only after current bundle/receipt revalidation (+S) |
| cancel/supersede | N0/N1/N2/N3→C1/C1/C1/C2 or S0/S0/S0/S1; close/revoke,+S+D+F; supersede links immutable successor |
| review | N3→N4 (assign **V**,+S); N4→N7/N5/N6 on approve/reject/remediation (**V**, +S) |
| director route | N7→N8 with immutable routing evidence,+S |

Stale W/V denies before evidence or state mutation. Recovery never acts on N2; a governance block there closes/fences the claim, records uncertainty, and permits no later effect transition. Revalidation never restores a prior claim/reviewer assignment. All review/remediation/cancel/supersede races serialize on the source tuple.

## 3. Repository generation and governance invalidation

`repository_generation` is runtime-global, monotonically starts at 0 in genesis, and is copied into every task tuple/receipt binding. It advances exactly once in a committed `REPOSITORY_GENERATION_ADVANCED` runtime event when the canonical **authoritative scheduling bundle** changes: source Git commit/head, project state, complete STOP set, task/dependency/assignment/handoff definitions, policy/capability records, or other frozen M0.2 decision input. Its digest is SHA-256 of canonical ordered path→content-digest pairs plus resolved source commit. Untracked/ignored noise and commits that leave this bundle byte-identical do not advance it.

The runtime event records old/new generation and bundle digest, source commit, project/STOP/policy/capability digests, reason (`IMPORT`, `FINAL_RECHECK`, or `REVALIDATION`), and affected task IDs. At N0, a changed bundle is imported and any old receipt is stale; at N1 it fences to B0; at N2 it fences to B0; at N3/N4 it moves to B1 and revokes review. A stale generation, receipt, or assignment may not proceed. `IMPORT_REPOSITORY` and `REVALIDATE_GOVERNANCE` set each affected task's tuple generation to the new runtime value in the same transaction; the event carries old/new values.

## 4. Request, idempotency, and common serialization

Canonical requests are UTF-8 canonical JSON with lexicographic keys, explicit nulls, RFC3339 UTC timestamps, lowercase hex digests, and sets sorted by canonical bytes. They bind runtime/attachment IDs, operation key and digest, task/attempt, actor fixture/role, expected tuple/generations/fence/claim/reviewer, definition/assignment/head, evidence, arguments, repository generation/bundle, and M0.2 receipt/inputs. `operation_key` and `request_digest=sha256(bytes)` are distinct.

All operations acquire the same OS advisory lock first, then SQLite, then release SQLite before the lock. The lock is an owner-only `scheduler.lock` file held with a non-blocking exclusive advisory lock for the process lifetime; its diagnostic record has lock ID, runtime/attachment ID, PID/start identity where locally available, acquisition time, repository generation, purpose and nonce. It is not an `O_EXCL` deletion protocol. A second cooperative holder denies. Process death releases the advisory lock; stale text/elapsed time alone never authorizes takeover. A new holder verifies matching runtime/checkout attachment, takes the OS lock, records a `LOCK_RECOVERED` runtime event with liveness evidence and old record digest, then proceeds. Wrong-runtime/check-out metadata is never deleted silently. Malicious/noncooperative local processes remain outside proof.

Normal transitions: acquire lock → resolve candidate Git/M0.2 bundle → `BEGIN IMMEDIATE` → verify runtime/attachment/config → idempotency lookup **before** mutable CAS → validate new operation → final Git/bundle check → append events/materializations/result → commit. Exact same idempotency digest returns the stored committed response; reused key with different digest denies. Failure rolls back all changes; post-commit/pre-response retry returns the committed result.

Initialization: lock → configure/verify SQLite → `BEGIN EXCLUSIVE` → attachment/genesis/runtime records → commit. Migration: lock → bind Git/runtime head → WAL-safe backup outside write transaction → `BEGIN EXCLUSIVE` → schema/ledger/runtime event → commit. Export: lock → bind Git/generation → integrity/replay checks → begin SQLite read snapshot → collect and verify heads → canonicalize/hash output → close snapshot → release lock. Backup: lock → record starting generation/heads → SQLite backup API from consistent read connection → verify backup integrity/digest → emit backup runtime event in a short `BEGIN IMMEDIATE` transaction. Slow backup/export never holds a write transaction, but retains the common advisory lock through the coherent read and identity pin.

## 5. SQLite mandatory operational profile

The owner-only runtime directory is mode `0700`; database, `-wal`, `-shm`, attachment, lock, backup and export files are mode `0600` (POSIX expectation). Creation or startup diagnoses and denies if these protections cannot be established or verified on the platform. Every new connection sets and verifies `PRAGMA foreign_keys=ON`, `PRAGMA busy_timeout=5000`, `PRAGMA journal_mode=WAL` (initialization connection verifies returned `wal`), and `PRAGMA synchronous=FULL`; writer connections use short `BEGIN IMMEDIATE`, migrations `BEGIN EXCLUSIVE`, exports a read transaction. Connections are process-owned, never shared concurrently, and closed after the operation.

Startup performs `PRAGMA integrity_check` requiring `ok`, `PRAGMA foreign_key_check` requiring no rows, PRAGMA effective-value checks, permissions checks for directory/database/WAL/SHM, event-chain/replay checks, and attachment/genesis checks. Export repeats integrity, FK, chain/replay and binding checks before its read snapshot. Backup verifies the backup database with integrity/FK checks and recorded digest. Failure, malformed rows, sequence/chain/tuple mismatch, unavailable required PRAGMA, permission violation, corruption, or failed verification makes runtime unavailable with no destructive repair. Raw copying of only the main DB in WAL mode is forbidden.

## 6. Acyclic checkout attachment and runtime genesis

The attachment lives at `${runtime_dir}/attachment.json`, outside the database and owner-only. **Phase A:** create immutable canonical attachment fields `{attachment_schema_version, attachment_id, canonical_project_id, repository_identity, expected_remote, repository_marker_digest, m0_2_freeze_commit, checkout_realpath, git_common_dir_identity, checkout_local_nonce, created_at}`. It excludes runtime ID and every genesis field/digest. Hash its canonical bytes as `attachment_digest`.

**Phase B:** create immutable genesis fields `{runtime_schema_version, runtime_id, attachment_id, attachment_digest, source_git_commit, m0_2_freeze_commit, project_state_digest, complete_stop_set_digest, policy_capability_bundle_digest, task_dependency_assignment_handoff_digest, initial_repository_generation:0, initial_scheduler_generation:0, global_sequence:0, predecessor_id:"GENESIS", predecessor_digest:sha256("GENESIS"), created_at}`. Hash canonical bytes as `genesis_digest`. Genesis never changes attachment bytes.

**Phase C:** write a separate immutable `runtime_attachment_seal` inside SQLite and exportable runtime events with `{runtime_id, attachment_id, attachment_digest, genesis_digest, created_at, seal_digest}`. It is created in the initialization transaction and binds both prior immutable hashes; neither attachment nor genesis contains the other’s future digest.

Startup reads attachment first, recomputes attachment digest, then validates genesis attachment ID/digest, recomputes genesis digest, and validates the seal. DB without attachment denies. Attachment without matching DB denies startup (a new runtime requires explicit initialization). DB+attachment copied to another checkout denies when realpath/common-dir/repository marker/remote binding differs. Coordinated malicious copying of DB, attachment, checkout and every local anchor remains outside local proof.

## 7. Task events, runtime events, and remediation

`task_events` are task-scoped; `runtime_events` are separate and have no task/attempt/task-sequence fields. Both have immutable logical IDs, global sequence, global predecessor ID/digest, runtime/attachment IDs, operation/request digest, actor fields, timestamp, canonical content digest, and event digest. Task events additionally have task/attempt, task sequence, task predecessor, complete tuple/generation/fence before/after, claim/reviewer facts, evidence, definition/head, repository/M0.2 bindings and argument/result digests. Runtime events carry runtime generation/head before/after and their typed payload. SQLite rowids are never semantic.

Genesis is runtime event global sequence 0, predecessor `GENESIS`, then the next committed event is sequence 1. Each task starts its own sequence at 1 with predecessor `TASK_GENESIS:<task_id>`. Global sequences are allocated from committed metadata in transaction and are contiguous across both tables.

`CREATE_REMEDIATION_TASK` is one transaction with two deterministic task events and one immutable relationship: (1) source `REMEDIATION_CREATED` receives global N and source task sequence next, binding source attempt, source rejection/remediation decision, new task ID and relationship ID; (2) child `TASK_CREATED_FROM_REMEDIATION` receives global N+1 and task sequence 1, binding parent task/attempt/review and the same relationship ID; (3) `remediation_links` has one relationship ID, source/new task IDs, source event ID, child event ID, source decision digest and link digest. Both events, link, child N0 materialization, source successor link and idempotency result commit or roll back together. Replay requires reciprocal IDs/digests and both heads; deletion/mutation/substitution of either locally observable side denies startup/export.

Replay derives and compares all task tuples, attempts, claims/fences, reviewer assignments, generations/counters, repository receipt/binding, links, evidence, idempotency responses, task/global/runtime heads, seals, snapshots and migration ledger. Duplicates, gaps, reordering, wrong predecessor/task/attempt, irreconcilable link, or extra/unreplayable materialization makes runtime unavailable.

## 8. Migrations, backup, export, and runtime failures

`migration_ledger` is schema-stable and append-only: runtime ID, migration ID, from/to schema versions, migration artifact digest, backup reference/digest, started/committed timestamps, result, pre/post runtime/global heads, and canonical migration digest. A success commits schema change, ledger success row and `SCHEMA_MIGRATED` runtime event atomically. A failed migration rolls back where possible; it writes no success event/row, retains prior schema only if integrity/replay prove it usable, otherwise marks runtime unavailable. A separately safe stable-ledger failure entry may record classification/evidence but never a successful version. Unknown newer schema and downgrade both deny.

Backups use SQLite backup API into a temporary owner-only target, verify integrity/FKs and digest, then atomic rename; no raw main-file copy. Exports contain canonical non-secret material only, bind exact Git bundle/repository generation/runtime/global heads, and exclude credentials, nonce, WAL/SHM/database bytes. `BACKUP_COMPLETED`, `SNAPSHOT_EXPORTED`, `CORRUPTION_DETECTED`, `RUNTIME_UNAVAILABLE`, `LOCK_RECOVERED`, repository advancement and migration are typed runtime events; a failed attempt may record a safe failure runtime event only when the stable preexisting schema can commit it.

## 9. Required acceptance cases

Every case asserts request, initial/intervening/final tuple, global/task/runtime heads, generations/fence, event count/order and idempotency result. Cover every matrix edge/default deny; stale worker/reviewer; lost response/key alteration; recovery/continuation/retry; approval terminality; governance races/final Git TOCTOU; M0.2 stale inputs; replay tampering; and atomic-write injection. Additionally require:

- attachment valid/mutated/missing/wrong-repo/wrong-genesis-digest/no-cycle/seal cases;
- effective WAL/FULL/foreign-key/busy-timeout/permission/integrity/FK checks and startup failure;
- remediation two-event atomicity, N/N+1 ordering, both task heads, reciprocal link/replay, and either-side mutation/deletion detection;
- relevant bundle advance versus irrelevant noise, stale READY/CLAIMED/IN_PROGRESS/REVIEW state behavior, and repository event fields;
- second-holder denial, process-death advisory-lock release, stale-text denial, wrong attachment lock denial, auditable takeover;
- successful/injected-failed migration, unknown-newer/downgrade, ledger/head correctness, backup verification and post-failure availability;
- lock coverage and coherent exact-head export/backup during attempted concurrent activity, no-secret export, and snapshot-digest change on bound-state change.

Optional future `goal_id`/`milestone_id` fields may be immutable non-authorizing task/event lineage metadata. They cannot override STOP, constitution, capabilities, runtime policy, or scheduler safety and are not implemented in M0.3A.
