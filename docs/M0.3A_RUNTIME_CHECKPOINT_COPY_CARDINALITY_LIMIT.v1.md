# M0.3A runtime checkpoint-copy cardinality limit v1

## Status and scope

This additive evidence contract defines the exact semantic claim required to
classify `MAX_CHECKPOINT_COPIES` in the private runtime-image host preflight.
It does not change runtime behavior, complete the resource inventory,
authorize release generation, establish public-verifier acceptance, clear a
STOP, or authorize execution or capital.

The classification remains valid only while its source, Discovery V3 census,
schema, manifest, evidence, predecessor, and self-digest bindings remain
exact. Any missing, stale, aliased, inconsistent, or incompletely reproduced
binding fails closed.

## Exact semantic claim

```text
constraint_id: MAX_CHECKPOINT_COPIES
classification: RESOURCE_MAXIMUM
semantic_subject:
  EXACT_BUILTIN_TUPLE_ITEM_COUNT_OF_CAPTURED_RUNTIME_IMAGE_CHECKPOINT_COPIES
unit: ITEMS
maximum: 49,999
```

For an exact `RuntimeImage` whose required slots were completely captured and
whose `checkpoint_copies` value was admitted as an exact built-in tuple, the
accepted equation is:

```text
0 <= len(captured checkpoint_copies tuple) <= 49,999
```

The literal lower bound is tautological for an exact tuple. This classification
is about the inclusive upper bound. It counts every supplied tuple item before
member-type, byte-size, canonicality, registration, order, uniqueness, or
cross-equality validation. An item need not be valid checkpoint bytes to count.

## Preconditions and enforcement order

The governing function is
`src/edgelab/runtime_v2_image.py:inspect_runtime_image_host`. The exact order
is:

1. require exact built-in `RuntimeImage` input;
2. capture every required top-level slot, returning early if capture is
   incomplete;
3. bind the literal `checkpoint_copies` subject to its captured value;
4. require the value to have exact built-in type `tuple`;
5. skip cardinality length inspection when that type guard fails;
6. load the same captured branch through the literal V3 cardinality row;
7. evaluate `0 <= len(value) <= MAX_CHECKPOINT_COPIES`;
8. write the result to `cardinality_valid["checkpoint_copies"]`;
9. on failure, add `IMAGE_CARDINALITY_LIMIT` for artifact
   `checkpoint_copies` at `/` and mark accounting incomplete;
10. only a cardinality-valid branch reaches member-type, per-member byte-size,
    and aggregate-accounting work; and
11. any finding withholds the sanitized image, while the report remains
    non-authorizing.

The complete normalized function and module ASTs are mandatory. The scalar
assignment and derived row alone are insufficient evidence for capture,
type-guard precedence, diagnostic emission, image withholding, or authority.

## Boundary and separation matrix

Let `M = 49,999`. Dedicated evidence must use an otherwise valid host image.

| Case | Supplied branch | Required result |
| --- | --- | --- |
| empty | exact tuple of length `0` | no checkpoint-copy cardinality finding |
| maximum minus one | exact tuple of length `M - 1` | no checkpoint-copy cardinality finding; exact items retained |
| maximum | exact tuple of length `M` | no checkpoint-copy cardinality finding; exact items retained |
| maximum plus one | exact tuple of length `M + 1` | exact `IMAGE_CARDINALITY_LIMIT`, artifact `checkpoint_copies`, coordinate `/`; no image or accounted totals |
| hostile collection | non-tuple length-bomb object | `IMAGE_FIELD_TYPE` before length inspection |
| hostile subclass | tuple subclass | `IMAGE_FIELD_TYPE`; no cardinality attribution |
| over-count plus oversized member | `M + 1` items with one over-byte member | cardinality finding only; member-byte loop skipped |
| at-count plus oversized member | `M` items with one over-byte member | no cardinality finding; separate `IMAGE_ITEM_BYTE_LIMIT` for that member |

The evidence must also prove input immutability, stable item ordering and
identity at admitted boundaries, sibling-cardinality independence, fixed
`DENY`, and non-Boolean report behavior.
