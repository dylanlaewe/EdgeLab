# M0.3A Runtime Foundation planning review v1

**Verdict: `M0_3A_PLAN_REQUIRES_REVISION`.** SQLite is an appropriate bounded choice for one local scheduler, and the frozen decision-engine → runtime → future executor layering is sound. The current plan is not implementation-ready because it does not yet define the authoritative state machine, semantic idempotency contract, event/state replay invariant, repository/database initialization binding, or stale-decision/STOP invalidation protocol precisely enough to produce one auditable implementation. These are M0.3A requirements rather than demands for distributed infrastructure, authenticated identity, or an executor.

## SQLite and transaction profile

One local SQLite database can provide serialized writers, atomic state/event changes, uniqueness, foreign-key integrity, restart recovery and deterministic local replay. M0.3A should specify and verify on every connection: `journal_mode=WAL`, `foreign_keys=ON`, a bounded `busy_timeout`, an explicit durability setting (`synchronous=FULL` unless the plan documents and accepts a weaker crash-loss boundary), and write operations beginning with `BEGIN IMMEDIATE`. Busy/locked results must be retryable without bypassing CAS or idempotency. Runtime code should use short transactions, one controlled write path, read transactions for coherent snapshots, restrictive database/WAL/SHM file permissions, SQLite's online backup mechanism rather than copying a live database, and fail-closed startup integrity/replay checks. WAL files are part of live durability and must be included by a correct backup/checkpoint procedure.

SQLite does not authenticate actors, protect a hostile host, prevent an administrator from replacing all local files, provide distributed consensus, or prove rollback after the database and Git anchors are rolled back together. M0.3A must state those limits. Corruption, an unreadable WAL, failed migration, integrity failure, or replay mismatch must prevent transitions and produce diagnostic evidence; automated destructive repair is out of scope.

`BEGIN IMMEDIATE` plus generation/CAS is sufficient only if every material transition follows one transaction shape: acquire the writer transaction; resolve the exact current task/attempt/claim and imported repository generation; verify expected state/generation, transition validity, decision freshness, STOP/project binding and idempotency; append exactly one immutable transition event; update materialized rows and generation; record the operation result; commit. Constraint/CAS failure rolls back. No transition may update state first and append evidence later.

## Minimal state and claim model

The current vocabulary mixes execution state, review workflow and Director-gate outcomes, and omits `FAILED` and `CANCELLED` despite requiring their semantics. M0.3A should use the smallest execution-attempt machine:

`READY → CLAIMED → IN_PROGRESS → COMPLETED | FAILED | BLOCKED | CANCELLED`

with explicit safe edges for yield/cancel/block before start. `COMPLETED`, `FAILED`, and `CANCELLED` are terminal for an attempt. `BLOCKED` resumes only through an explicit event and generation advance. A retry creates a new attempt under policy; a continuation remains the same attempt and advances its continuation counter. Remediation and review should be separate linked tasks/attempts, not mutations that resurrect a completed attempt. `READY_FOR_DIRECTOR_GATE` is derived governance evidence outside the execution machine. If review routing is retained in M0.3A, the schema must enforce reviewer/worker separation; omitting review routing from A is simpler.

Claims should be task-attempt scoped and generation-fenced. A unique active-claim constraint prevents double claim. Every subsequent write supplies the claim generation/fencing token. A disappeared claimant is not automatically replaced merely because time passed. Recovery explicitly expires/revokes/abandons the old claim, records an event, advances generation, and only then permits a new claim. Lease timestamps may be stored now for future policy, but expiry alone must not authorize concurrent work. This avoids permanent deadlock without pretending M0.3A can safely reclaim external effects.

The required race outcomes are: one winner for two claims; claim-versus-cancel and completion-versus-supersession produce one serialized valid outcome; STOP/project import advances the repository/runtime generation and invalidates unstarted authorization; a stale worker cannot write after claim generation advances; and a crash/retry returns the committed result or safely performs the still-uncommitted transition once.

## Semantic idempotency

A random request ID alone is insufficient. Store an operation key plus a canonical request fingerprint binding database/repository identity, task-definition digest, task, attempt, actor label, transition, expected state and generations, claim token, evidence digests, and decision receipt where required. The same key and fingerprint returns the stored outcome without a second event. The same key with different content rejects. A different key cannot repeat the same semantic transition because CAS, transition constraints and an appropriate semantic uniqueness key prevent it. This gives deterministic recovery after a commit whose response was lost.

## Event log and materialized state

M0.3A should define a global monotonically increasing event sequence and chain head, serialized by the single SQLite writer, plus a per-task-attempt sequence/previous-event reference for local history. Each immutable event binds event ID, database/repository identity, task definition, task/attempt, unauthenticated local actor label and role, operation/idempotency fingerprint, global and task sequences, both prior heads, previous/next state, previous/next generation, claim token when applicable, evidence digests, M0.2 decision receipt and imported repository generation when applicable, timestamp, and an event-content digest over every immutable field. Database constraints and triggers should reject event update/delete and invalid sequence linkage through normal runtime access.

The initialization event is replay genesis. Replay from genesis must reproduce materialized task, attempt, claim and generation state exactly. Startup and pre-export checks compare replayed state and event heads to materialized state. A state row without its event, a transition event without the corresponding state result, a gap, fork, deletion, mutation, or digest mismatch fails closed. Local hashes and triggers detect accidental or non-recomputed mutation; they are not tamper-proof against a hostile database administrator before an authenticated external anchor exists.

## Git, decision and runtime authority

Git owns immutable task definitions, policy/schema versions, handoffs, accepted M0.2 evidence and exported milestone snapshots. SQLite owns queue membership, imported-definition identity, attempts, claims, runtime transitions, continuations, idempotency outcomes and later usage. The same mutable fact must not be independently editable in both places.

An explicit import transaction should pin each task to its exact Git reference, blob/content digest and source commit. Updating a Git definition creates a new imported version/event; it never silently rewrites an existing attempt. Runtime initialization requires a schema version/migration ledger, random database ID, normalized repository identity, accepted M0.2 freeze commit, initial clean source Git commit and relevant policy/project/STOP digests, runtime generation, and a genesis event. Startup refuses a wrong repository, mismatched freeze, unsupported migration, newer mandatory Git state not explicitly imported, or a database/snapshot identity conflict.

An M0.2 eligibility result is an input, never runtime-created governance logic. Before claim/start authorization, the adapter runs the frozen M0.2 interface against the exact pinned authoritative inputs and records its receipt, resolved assignment head, project/STOP digests and repository/runtime generation. The transition rechecks those bindings in the same serialized runtime operation. A newer imported repository generation, changed STOP/project digest, changed task/assignment head, or changed runtime generation makes the receipt stale and requires reevaluation. Any necessary M0.2 semantic change is a separate escalation; the adapter may normalize transport but must not reproduce eligibility rules.

Because Git and SQLite do not share a transaction, the plan must define a single runtime synchronization lock/protocol covering repository-state verification/import and the SQLite authorization transition. Noncooperating host mutation remains outside local proof, but a detected dirty/moved/ref-changed repository fails closed.

If STOP/project state changes before work starts, no new claim/start is allowed and existing unstarted authorization is invalidated. If a task is already `IN_PROGRESS`, record the change and move it to a no-new-effect blocked/cancellation-requested condition according to policy; evidence-only progress needed to preserve what happened may be accepted, but no new prohibited effect may be authorized. M0.3A has no executor, so tests exercise state primitives only.

## Restart, rollback and export

A clean restart verifies configuration, schema, database/repository binding, event chain and replay equality. SQLite rolls back an uncommitted transaction. A committed transition remains authoritative even if the response was lost, and its idempotency record returns the same result. A stale `CLAIMED`/`IN_PROGRESS` row is never silently reset; explicit fenced recovery records the disposition before reassignment. Incomplete continuations fail closed.

Local rollback detection should compare the database ID, runtime generation, last global sequence/head and source Git binding with the latest compatible snapshot known in Git. A database behind that snapshot refuses service; a database ahead requires a new export rather than rewriting history. A copied database bound to a different repository refuses. Rollback of both DB and every local Git anchor, or hostile recomputation, cannot be proven locally and remains a future authenticated-anchor boundary.

An atomic read-transaction export should contain database ID, schema/migration version, runtime generation, last global sequence and hash-chain head, per-task state summary/root, relevant policy/project/STOP and accepted-M0.2 bindings, source Git commit, export timestamp, and a canonical snapshot digest. It contains no private keys, credentials, WAL bytes or live queue database. Git receives milestone evidence snapshots, not queue churn.

## Deferred identity, policy and external authority

M0.3A actor fields must be explicitly `SYNTHETIC_LOCAL_UNAUTHENTICATED` fixture identities. They must not say or imply that Director, Data, Skeptic or Risk signed an event. M0.3B owns keys and authentication. M0.3A may reserve typed references/counters for future model-tier, budget, usage and continuation bindings, but must not implement or default model policy.

Nothing here clears `STOP-M0-001`, changes capital, authenticates STOP clearance, or replaces the external KMS/human/Risk authority gate. Local scheduler consistency remains distinct from external governance authority.

## Required M0.3A acceptance matrix

Implementation review must demonstrate:

1. two concurrent claims yield exactly one active claim and one event;
2. stale state, attempt, claim token, repository generation and row generation reject;
3. claim/cancel, claim/STOP-import, completion/supersession and review/remediation races serialize to one valid result;
4. identical idempotent retry returns the recorded result and creates no second event;
5. reused key with changed request rejects, while a distinct valid request is not incorrectly deduplicated;
6. invalid transitions and every terminal-state resurrection reject;
7. state update and transition event commit or roll back together under injected failures;
8. state-without-event and transition-event-without-state cannot arise through the runtime API;
9. replay rebuild equals materialized state, and mismatch fails closed;
10. event gap, fork, deletion, mutation, digest change and sequence error are detected within the stated local threat model;
11. crash before commit leaves no transition, while crash after commit plus retry returns the prior result;
12. clean restart preserves state; stale/disappeared claims require explicit fenced recovery;
13. wrong-repository/copied database, freeze mismatch and unsupported schema migration reject;
14. Git definition changes require explicit immutable import and invalidate stale definition bindings;
15. stale M0.2 receipt, assignment head, STOP digest, project-state digest or runtime generation rejects and reevaluation can produce a new receipt;
16. STOP/project change prevents a new start and places already-started work into the defined no-new-effect state without deleting evidence;
17. owner/reviewer overlap rejects if review routing is represented; otherwise review is demonstrably out of A;
18. online backup/snapshot during activity is coherent, canonical export digest verifies, and secrets are absent;
19. database/WAL corruption, failed integrity check and materialized/event mismatch fail closed;
20. all M0.2 semantic tests remain unchanged and green, with the integration adapter tested separately and no executor path present.

## Required plan revisions before H-M0-041 release

Director must revise the plan and queued implementation handoff to include: the exact minimal transition table and terminal/retry/continuation rules; the connection/durability/backup/corruption profile; one atomic transition algorithm; semantic idempotency; global plus task-attempt event sequencing and replay equality; append-only enforcement limits; generation-fenced claim recovery; explicit Git/SQLite ownership and import synchronization; database genesis/repository binding and migration rules; stale M0.2/STOP/project invalidation; rollback limits; snapshot format; unauthenticated M0.3A actor labeling; and the acceptance matrix above.

No distributed database, real identity keys, model policy, executor, network, sports research, capital action, or external authority system is required in M0.3A. `H-M0-041.v1` remains queued and is not implementation-ready until the revisions receive focused Skeptic disposition.
