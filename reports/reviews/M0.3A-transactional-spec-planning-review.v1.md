# M0.3A transactional specification planning review v1

**Verdict: `M0_3A_PLAN_REQUIRES_REVISION`.** The revision makes SQLite configuration, synthetic identity, migration, corruption, snapshots, local rollback limits, and the frozen M0.2 boundary substantially clearer. It still does not let Data implement the security-critical transition engine without invention. The named transition matrix is absent, the prose crosses three state dimensions inconsistently, and the stated CAS-before-idempotency order makes a retry after a committed/lost response fail instead of returning the committed result. `H-M0-041.v2` remains queued and is not implementation-ready.

## State model and transition contract

Separating workflow, execution, and review state is the right direction, but the allowed-transition prose does not define transitions over their tuple. `READY→CLAIMED→IN_PROGRESS` crosses workflow `READY` into execution-only states. `IN_PROGRESS→REVIEW_PENDING` crosses execution into review without saying the resulting workflow and execution values. `BLOCKED` exists in workflow and execution, while `CANCELLED` exists only in workflow, so “any nonterminal may become BLOCKED or CANCELLED” has no unique implementation. The document calls `APPROVED` terminal and then permits `APPROVED→READY_FOR_DIRECTOR_GATE`. It calls execution `BLOCKED` terminal while also requiring recovery/continuation semantics. These contradictions are HIGH because different reasonable implementations produce different authorization behavior.

The specification says “Every matrix row specifies” its requirements, but contains no matrix. Data therefore cannot determine the full source tuple, target tuple, actor role, required evidence, expected generations, fence, attempt/writer effects, event, and idempotency result for each operation. The revision must include the actual closed/default-deny table. It must cover at least initialize/import, claim, start, progress/continuation, complete, fail, block, cancel, yield, recovery, retry/new attempt, supersede, assign review, begin review, approve, reject, require remediation, and Director-gate readiness. Every unlisted tuple/operation must deny. Terminality must be stated per complete tuple, and no terminal tuple may be used as the source of a state-mutating transition except creation of a separately identified attempt/task where specified.

Retry and remediation are directionally correct: retry creates a fenced new attempt and remediation creates a linked new task. Continuation remains the same attempt. The table still needs to specify whether continuation retains or rotates the claim fence, which counter advances, how a continuation limit is represented for future policy, and why old-attempt output fails after retry/remediation.

Review separation is stated structurally but not implementably while the matrix is missing. Review rows must require a reviewer role distinct from the owner role and a reviewer fixture ID distinct from the owner fixture ID. This is local structural separation only; it does not authenticate either fixture.

## Atomic algorithm and semantic idempotency

The transaction outline is atomic in principle: event, state, generation, and idempotency outcome can commit together under `BEGIN IMMEDIATE`. Its ordering is wrong for lost-response recovery. It validates current CAS generation, state and fence before looking up the fingerprint. After the first request commits, those values have advanced, so the identical retry can fail stale-CAS before discovering and returning its committed result.

The corrected order must be explicit: after opening the transaction and validating immutable runtime/repository identity, canonicalize the complete request and compute its semantic request digest; look up the idempotency operation key/fingerprint; if an exact stored request digest exists, return the stored committed result without reapplying current-state preconditions; if the key/fingerprint exists with different canonical content, reject; only a new operation proceeds to current state/CAS/fence/receipt checks, event allocation, state mutation, generation advances, stored result, and commit. Any failure rolls back all of those writes. The schema must distinguish the operation key from the canonical request digest even if a digest is also used as the key.

The canonical request must bind operation, runtime/repository identity, task definition and resolved assignment/head identity, task, attempt, actor fixture and structural role, complete expected state tuple, every relevant generation/fence, evidence set and digests, exact M0.2 receipt/input bundle where required, and all transition arguments. Canonical property ordering must be defined. Tests should cover exact retry, changed evidence/arguments under a reused key, semantically distinct requests, and retry after an injected post-commit/pre-response failure. “Fingerprint collision resistance” alone is not a useful behavioral test for these cases.

## Claim fencing, lease recovery, and governance change

Generation fencing is the correct primitive, and expiry is correctly treated only as liveness suspicion. The missing matrix leaves unsafe details open. Every worker-originated start, progress, continuation, failure, completion, block, yield, and evidence submission must require the current task-attempt claim ID and fence. Recovery must name the allowed source tuples, actor role and evidence; atomically close the old claim; advance the fence and relevant generations; emit `RECOVERED`; and create the exact claimable target tuple. A stale fence must fail before any state or evidence mutation.

The STOP/project prose is insufficient after a claim. A bound change before claim denies. A change after claim but before start must atomically invalidate the decision receipt, close/fence the claim, advance generations, and enter an explicit blocked tuple. During `IN_PROGRESS`, the scheduler can only record a governance block and reject later effect-authorizing transitions; M0.3A has no executor cancellation. The plan currently says “pause/block” but defines no `PAUSED` state and calls execution `BLOCKED` terminal. Director must choose one exact representation and its recovery rule.

## Events, sequences, replay, and state consistency

Global plus per-task sequencing is appropriate for one serialized writer. The specification must define genesis sequence/head values, require the next committed global sequence to be exactly prior+1, and define the first task-event predecessor. Rolled-back sequence allocation need not be gapless if it uses an SQLite rowid mechanism; the logical committed sequence used by the hash chain must be contiguous. `(task_id, task_sequence)` is a valid task-wide sequence even across attempts, provided replay enforces attempt identity and the per-task predecessor. Reordering, duplicate sequence, committed logical gaps, wrong predecessor and task/attempt substitution must fail.

The event schema needs the actor structural role as well as fixture ID, complete previous/next workflow-execution-review tuples, task-definition and resolved assignment/head bindings, previous/next scheduler/task/attempt/dispatch/fence generations, claim identity and lease/recovery facts where relevant, the exact authoritative decision-input digest bundle, and operation arguments/result digests. Generic “previous/next states,” “Git/policy digests,” and “scheduler generation” are not enough to reconstruct the planned materialized rows or prove that the accepted M0.2 assignment-head identity is carried into M0.3.

“Replay exactly reproduces materialized state” must enumerate replay-derived fields/tables: task import/version binding, workflow state, attempts and current attempt, complete execution/review tuples, active/closed claims and fences, all generations/counters, reviewer assignment, supersession/remediation links, and event heads. It must say whether receipts/evidence/idempotency results are immutable referenced facts verified by replay or replay-derived materializations. A state row, claim, generation or reviewer assignment not derivable or verified from events violates the invariant. Startup and export compare reconstructed values to stored materialization and fail closed on any mismatch.

Normal SQL access should deny event update/delete, while startup chain/replay checks detect accidental or locally anchored mutation. These controls remain non-authenticated and cannot defeat a hostile administrator who rewrites the database and every surviving anchor.

## SQLite, initialization, Git synchronization, and migration

WAL, `synchronous=FULL`, per-connection foreign keys, five-second busy handling, short `BEGIN IMMEDIATE` writes, owner-only permissions, and fail-closed integrity checks are coherent. Initialization should verify the returned WAL mode and all connection PRAGMAs; directory, database, WAL and SHM files must remain owner-only.

The specification says “backup before migration” but does not define a WAL-safe method. It must require the SQLite backup API, `VACUUM INTO` under the documented restrictions, or another explicitly consistent SQLite mechanism. A raw `.db` copy is forbidden while committed frames may remain in WAL. Snapshot evidence export and database backup are distinct operations.

Genesis must additionally bind the initial project-state digest, complete STOP-set digest, relevant policy/capability digest bundle, and checkout/runtime attachment identity. Canonical repository identity plus source commit detects a different repository or revision but does not by itself prevent a copied database from attaching to another checkout of the same repository at the same commit. A separate owner-only attachment manifest/nonce outside the copied DB, or another precisely defined local binding, is required; its local-only limitation must be stated.

Git and SQLite cannot commit atomically. Before decision-bearing transitions, one cooperative runtime lock/protocol must cover authoritative Git verification/import, frozen M0.2 evaluation or receipt validation, and the SQLite authorization transaction, with a final bound-state check before commit. Dirty worktrees, changed refs/heads, changed task/dependency/assignment/handoff/STOP/project content, or an imported repository generation mismatch deny. Noncooperating host mutation remains outside the local threat model. The current phrase “revalidate Git bindings” leaves this security-critical TOCTOU behavior to Data.

Git remains authoritative for immutable definitions and governance inputs; SQLite remains authoritative for runtime queue and transitions. An explicit import event must pin exact refs/digests and never rewrite an existing attempt. Git changes while idle import a new generation; while READY invalidate eligibility; while CLAIMED fence/block before start; while IN_PROGRESS record the chosen governance-block tuple; while review is pending/reviewing invalidate the bound review decision and require revalidation. The revised table must identify which transitions require a newly evaluated M0.2 receipt.

Schema v1, monotonic transactional migrations, backups, downgrade refusal and unknown-version refusal are suitable. The plan should specify that migration metadata and its event commit atomically, that a failed migration leaves the previous schema usable or the runtime unavailable without partial acceptance, and that migration events are representable across the schema boundary. A v2 migration need not be implemented now.

Corruption behavior is appropriate: integrity, foreign-key, malformed-row, sequence, chain, impossible-tuple, and replay failures make the runtime unavailable, with no destructive automatic repair.

## Snapshots, rollback, identity, scope, and frozen Stage 1

The evidence snapshot fields are suitable once the complete event/state roots and exact decision-input bindings above are added. Export must run from a coherent SQLite read transaction after integrity/replay verification and produce a canonical digest. It contains no credentials, keys, attachment nonce, WAL bytes, or live database. A separate database backup uses the WAL-safe mechanism.

The rollback claim is correctly limited to surviving local anchors. Coordinated rollback of database, attachment state, snapshots and Git/local anchors remains undetectable until authenticated external anchoring exists.

`synthetic_actor_fixture` is an unauthenticated local test identity. It cannot satisfy STOP clearance, capital authority, or future worker authentication. M0.3B remains responsible for authentication. Structural role separation in A is a data invariant, not proof of real-world identity.

The frozen Stage 1 boundary at `bc3a40924ca580ca6eddc4c24e32ff99ddd95330` remains unchanged. An integration adapter may call and bind the frozen decision engine; it may not reproduce or alter eligibility semantics. The event/receipt contract must carry the exact M0.2 receipt and resolved authoritative input/head identities, including the assignment head that M0.2 acceptance left as M0.3 hardening.

`H-M0-041.v2` correctly excludes identity keys, model policy, executors, Codex invocation, network, plugins/MCP, external authority, sports research, paper/live activity and capital. Those exclusions remain mandatory.

## Acceptance-matrix revisions

The current list is a useful index but is not an implementation-grade test matrix. Each case must name setup, operation, injected race/failure, expected tuple/generations/event count/head and denial/result. In addition to the listed cases, it must explicitly cover:

1. every allowed row and representative unlisted tuple/operation denial;
2. `APPROVED`/Director-gate terminality after the contradiction is resolved;
3. claim-versus-cancel, claim-versus-STOP import, completion-versus-supersession, and review-result-versus-remediation races;
4. every worker-affecting transition with a stale fence after recovery/retry;
5. identical retry after post-commit/pre-response failure, with CAS already advanced;
6. reused idempotency key/fingerprint with changed canonical content;
7. state/event/generation/idempotency-result atomicity under failure injection at every write boundary;
8. genesis, global/task sequence predecessor, gap, reordering, wrong-attempt and wrong-task-chain attacks;
9. exact replay of every enumerated materialized field and extra/unreplayable-row rejection;
10. STOP/project/task/dependency/assignment/handoff changes after claim but before start and during review;
11. cooperative Git/SQLite lock and final-check TOCTOU mutation tests;
12. same-repository copied database attached to another checkout, stale attachment nonce and wrong freeze;
13. migration commit/failure/downgrade/unknown-newer cases and WAL-safe backup restoration;
14. SQLite-consistent backup with committed WAL frames and coherent snapshot export during activity;
15. reviewer-role and reviewer-fixture separation;
16. exact M0.2 receipt plus resolved assignment/head binding and stale-input reevaluation;
17. frozen M0.2 regression tests and proof that no runtime path or executor exists.

## Required revision and disposition

There is no project-wide BLOCKER, but five HIGH planning gaps remain: contradictory tuple transitions and missing matrix; broken lost-response idempotency ordering; incomplete fence/governance-change transition semantics; incomplete event/replay and exact decision-input bindings; and unspecified Git/SQLite serialization plus copied-checkout binding. Medium items are the WAL-safe backup contract, explicit genesis policy/STOP digests, cross-schema migration event detail, and turning the acceptance list into expected-result cases.

Director must revise the specification and supersede `H-M0-041.v2`, then request another focused Skeptic planning review. Data must remain unreleased. No runtime implementation, production change, executor, M1, operational activity or capital action is authorized.
