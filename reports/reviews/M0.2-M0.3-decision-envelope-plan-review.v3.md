# M0.2 → M0.3A decision-evidence adapter planning review v3

**Verdict: `M0_2_M0_3_ADAPTER_PLAN_REQUIRES_REVISION`.** V3 closes unrestricted nested objects and substantially improves handoff closure, raw-output terminology, clock/Git isolation, historical/current separation and wrong-runtime reporting. It remains non-implementable because v6 contradicts the frozen scheduler state machine, the schema cannot represent the named frozen commit, and the purported authoritative schema does not encode several security-critical relationships required by the prose.

## BLOCKER: v6 contradicts the accepted state machine

V6 says it preserves v3 scheduler invariants, but its operational rows do not use the v3 states:

- v3 defines claim as `N0→N1`; v6 defines `N0→C0`, where v3 defines `C0=(CLOSED,EXECUTION_COMPLETED,NOT_REQUIRED)` and treats C* as terminal.
- v6 introduces `R0`, which v3 never defines, then uses it for START, CONTINUE, COMPLETE and REVALIDATE.
- v3 claim advances S, D and F; v6 lists only F and S.
- v3 COMPLETE permits `N2→C0` or `N2→N3`; v6 provides only undefined `R0→N3`.
- v3 governance revalidation is `B0→N0` or `B1→N3`; v6 instead gives `R0→R0`, leaving the stated governance-block path without the accepted revalidation transition.

Data cannot infer whether these are renames, policy changes or typographical errors. Implementing the literal table could turn CLAIM into terminal successful closure. This is a planning BLOCKER independent of adapter implementation.

## BLOCKER: the schema rejects the authoritative freeze identity

The engine manifest defines `freeze_commit` using the generic 64-hex SHA-256 shape. The implementation-authoritative contract names the accepted Git commit `bc3a40924ca580ca6eddc4c24e32ff99ddd95330`, a 40-hex object ID. The v3 schema rejects that exact value. It does not define a separate SHA-256 commit-object digest or mapping. Data therefore cannot construct a schema-valid envelope that truthfully names the accepted Stage 1 freeze without inventing a new identity interpretation.

The B0 evidence-only direction is safer: rows remain B0, advance only S, do not recreate claims, dispatch or completion, and bind a historical claim/fence and block ledger. `REPORT_BLOCKED` is an acknowledgement after the normal block transition rather than a duplicate route into B0. However, each operation still refers only to a “typed payload” without defining its fields/digest, and the table does not state whether a referenced envelope must first pass historical verification. Those details are HIGH because they define what append-only evidence Data may accept.

## Stage 1 neutrality and complete reads

Frozen M0.2 and its accepted tests remain byte-identical at `bc3a40924ca580ca6eddc4c24e32ff99ddd95330`. V3 is observational in intent and explicitly prohibits scheduler or operational authority. The complete handoff issue is corrected in prose: every `docs/handoffs/*.json` parsed before selection and the directory inventory must be retained. DISPATCH and DENY source categories now cover the frozen reads. Adapter equivalence remains an implementation acceptance requirement; no adapter exists in this review.

Directory and absence evidence are improved but not mechanically closed. A DIRECTORY entry carries path and kind, not a member raw digest or source reference. An ABSENT item can name an `inventory_id` that does not exist. Arrays allow duplicate source IDs, and `input.source_ids` can omit, duplicate or introduce IDs because neither the schema nor a defined validation algorithm enforces the prose’s exact-set relationship. A successor must require unique IDs and specify exact cross-reference, root containment, lexical ordering, inventory digest and file-artifact linkage checks.

## Schema, subject and outputs

Nested extra-property injection now rejects. The schema nevertheless accepts:

- DENY with `operation:"CAPITAL_MUTATION"`;
- DISPATCH with null operation;
- different top-level and input subjects;
- duplicate source IDs and duplicate manifest entries;
- ABSENT evidence referencing no DIRECTORY evidence;
- invalid base64, an arbitrary freeze commit and a non-Z evaluation timestamp while `timezone` says UTC.

The prose says verifier checks will reject several of these, but it also says “Only the v3 schema is authoritative.” Data therefore has no single mechanically authoritative contract. Cross-field checks that JSON Schema cannot express may live in a named verifier algorithm, but that algorithm and its exact failure conditions must then be implementation-authoritative rather than left implicit.

Subject consistency contains an internal impossibility. The authoritative subject has task, attempt, assignment head and handoff head. The document requires the same tuple to be derived from normalized output, including attempt, but normalized output contains only task ID and no attempt or head fields; frozen raw output likewise contains none of those three values. The verifier can compare raw/normalized task ID and separately compare the reconstructed input subject, but it cannot derive the four-field tuple from output. The requirement must be corrected rather than invented by Data.

Raw output is now correctly defined as canonical JSON bytes of the exact returned mapping, avoiding impossible Python-memory-byte claims. Digest/length/decoding and fail-closed unknown keys are clear in prose. The schema itself treats base64 as an arbitrary string and does not encode DENY/DISPATCH conditionals; a mandatory verifier can close these only after the authority conflict above is resolved. Normalized values must remain purely derived and must never authorize independently.

## Engine, replay and verification

The replay design is materially stronger: isolated tree, fresh subprocess, controlled module path/environment, sealed clock and Git shims, captured instant/ref observations and fail-closed environment mismatch. Repeated clock reads are defined to return one captured instant, and current Git is excluded from historical verification. These choices preserve Stage 1 code while making boundary equivalence testable.

The engine evidence graph still lacks a mechanical link from each `engine_manifest.entries` digest to retained bytes. The prose says replay writes manifest blobs and refers to a “sealed import/validation manifest,” but the schema has no dependency-manifest field and does not require engine entries, launcher or shims to reference FILE artifacts in `source_manifest`. It also records only the top-level `jsonschema` version, not the transitive installed dependency/environment closure that may affect validation. Data would have to invent the required-closure calculation and byte lookup. The successor must define a closed dependency manifest and exact artifact references, including package initialization and required third-party distributions.

Clock and Git observation semantics are otherwise implementation-bounded. The successor should specify the exact clock installation point because “before import” and patching a frozen module call site admit different mechanisms; acceptance must demonstrate direct-versus-replay equality at timestamp boundaries. The Git shim covers the only two subprocess observations frozen M0.2 makes.

Historical/current separation is sound in concept. Historical verification uses only retained evidence and yields HISTORICALLY_VALID or INVALID. Currentness then resolves the target under the common lock. Changed current authority is stale; corrupt or unreproducible history is invalid; wrong runtime preserves the historical-valid sub-result and denies authorization. Generation’s common-lock/final-resolve/atomic-store sequence closes the earlier A→B race if the complete evidence graph is fixed.

## Retention, reuse and disposition

SQLite, backup and export correctly require the transitive immutable evidence closure and restore rehashing. This becomes implementable only after engine/source cross-references are closed. Every R-gated use must recheck VALID_CURRENT for the exact task, attempt, claim/fence and runtime/repository generations; revalidation needs a new envelope. Legacy receipt digests, arbitrary IDs and caller verification flags remain non-authorizing.

5. **HIGH:** directory member/file linkage, unique source IDs, exact-set coverage and absence-to-inventory binding are not mechanically defined.
6. **HIGH:** engine entry/shim/dependency bytes are not linked to preserved artifacts and the required import/validation manifest is absent.
7. **HIGH:** evidence-only payload shapes and referenced-envelope historical-validation rules remain undefined.

MEDIUM residuals are exact clock-shim installation timing, RFC3339 `Z` enforcement/base64 schema constraints, and explicit repository/runtime generation names in each corrected transition row. No LOW item needs a separate cycle.

Director must correct v6 using the exact v3 N0/N1/N2/B0/B1/C0 state vocabulary and effects; give `freeze_commit` the exact accepted Git-object identity shape; resolve schema-versus-verifier authority; correct subject comparison; close evidence/engine cross-references and uniqueness; and define the four evidence payloads.
