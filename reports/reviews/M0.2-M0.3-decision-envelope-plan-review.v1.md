# M0.2 → M0.3A decision-evidence adapter planning review v1

**Verdict: `M0_2_M0_3_ADAPTER_PLAN_REQUIRES_REVISION`.** The envelope is the right architectural response to `STOP-M0-3A-001`: it wraps rather than edits Stage 1, rejects caller receipt assertions, distinguishes historical evidence from current authorization, and keeps all security claims local. The current contract is not implementation-ready because its source set is not the full dependency set consumed by frozen M0.2, its engine identity covers only one file, it does not preserve the raw historical source bytes needed for later recomputation, its generation path lacks the accepted Git/SQLite cooperative serialization boundary, and its verifier orders current-source comparison in a way that conflicts with `VALID_STALE`. The nominally typed schema also leaves the input and output bundles open and omits required subject fields.

## Stage 1 neutrality and actual dependency closure

The proposed adapter is semantically neutral in intent. Resolving evidence, invoking the frozen function, preserving its result, hashing evidence and rerunning it do not alter M0.2. The contract correctly forbids changing eligibility, STOP/capability behavior, action classification, permissions, `decision_id`, DENY/DISPATCH meaning or stale authority. No frozen Stage 1 file changed from `bc3a40924ca580ca6eddc4c24e32ff99ddd95330`.

The documented input set is incomplete when compared with `src/edgelab/orchestration.py`:

- `_load_scheduler_state` reads `schemas/scheduler-state.schema.json`.
- `validate_record` reads the project-state, STOP, task, handoff and capability schemas and executes helper logic in `src/edgelab/validate.py` and `src/edgelab/data_integrity.py`.
- `clock_checks` consumes the evaluation wall clock. A future completed timestamp can deny at generation time and later cease to deny, so historical recomputation is not deterministic unless the evaluation instant/environment is captured and replayed.
- repository identity consumes the resolved checkout identity, origin URL, `HEAD`, and the resolved `origin/main` ancestry relation. The proposed repository object does not explicitly bind the `origin/main` commit used by that check.
- `_versioned_head` consumes directory filename inventories, not only the selected record. Added malformed or newer task/assignment names change the result.
- `_current_handoff` attempts to parse every handoff JSON before selecting the claimed handoff and separately consumes the complete version inventory for the handoff ID.
- capability and STOP checks consume their complete matching directory inventories.
- the dispatch decision ID consumes the fixed v1 assignment and handoff-binding reads in the output context as well as the numeric assignment head used for validation.
- a DENY decision ID consumes the broad denial context: project JSON files, all handoffs, STOPs, assignments, handoff bindings, tasks, completions, capabilities, scheduler state, intent and exact error reason. A branch-independent bundle that captures only the successful dispatch inputs cannot reproduce arbitrary DENY output.

The revised contract must define a complete resolver manifest for both DISPATCH and DENY branches. It must bind every raw file, every relevant directory inventory/absence assertion, the resolved Git refs and repository identity, evaluation clock, intent, and deterministic ordering actually consumed. A consumed validation schema or helper cannot remain outside the evidence closure.

## Canonical source and input bundle

The stated JSON encoding is a useful base, and raw source digests intentionally make a same-path byte change detectable. It is not yet enough for implementation:

- `input_bundle` is an unconstrained object in the schema, despite the prose naming a closed structure.
- `assignment_head` is optional in the schema even though currentness requires it.
- the schema does not type or require `source_refs`, directory inventories, Git-ref identities, evaluation instant, resolved records, absence assertions or the engine dependency manifest.
- only `source_refs` ordering is specified. The exact ordering for STOPs, capabilities, dependency traversal, completion records, inventories and denial-context collections must match frozen M0.2.
- envelope parsing must reject duplicate JSON keys before object construction, reject all floats/nonfinite numbers for this integer-only interface, and state that Unicode code points are preserved without normalization (or name a normalization form). Merely using `json.dumps` does not define hostile-input parsing.

Path and content have different meanings and both must be bound. Same path with changed bytes is historically valid only if the old bytes can be reconstructed, but it is stale for current authorization. A moved path with byte-identical content is also stale where path/inventory is an M0.2 input. Semantically equal JSON with changed property order should follow an explicit rule: source raw-byte identity changes, while parsed canonical content may remain equal. This matters because M0.2 directly hashes some source files and only parses others.

The envelope currently stores `{path,sha256}` plus parsed `resolved` values, not the exact historical raw bytes. A digest cannot reconstruct deleted or changed content, and parsed JSON cannot recreate whitespace/property ordering required by raw hashes in scheduler state, handoff binding and completion evidence. Either require a clean committed source tree and bind retrievable Git blob IDs for every input, or persist each exact raw source byte string (for example base64 plus digest/media type) inside immutable envelope evidence. Because frozen M0.2 accepts working-tree bytes, the robust minimum is to persist raw bytes and directory inventories.

## Output and envelope binding

Frozen M0.2 returns five fields for DENY and six for DISPATCH; it does not return `schema_version`, and DENY omits `operation`. The prose calls the bundle the “exact returned mapping” while adding `schema_version` and `operation:null`. Data must not invent whether those are raw output or adapter normalization. Define a closed wrapper with `raw_output` exactly equal to the returned mapping and separately versioned normalized fields, or define one explicit normalization transform and compare both its input and output. Any unexpected frozen output field must be preserved and make the typed normalization fail closed rather than being silently dropped.

`output_bundle` is currently an unconstrained object. The schema must require the complete closed result shape, conditional DENY/DISPATCH operation behavior, exact task subject and `decision_id`. It must likewise close `input_bundle`, require `assignment_head`, and type the engine/source manifests.

The envelope content digest itself is acyclic: canonicalize every envelope field except `content_sha256`, then hash. Mutation of freeze, engine, subject, sources, input/output digests, repository binding, generation or timestamp therefore invalidates it. The revision should retain this construction and make clear that `envelope_id` is independent metadata rather than a digest derived circularly from `content_sha256`.

## Frozen engine identity and deterministic recomputation

Hashing only `src/edgelab/orchestration.py` does not prove which engine ran. That file imports `ROOT`, `read` and `validate_record`, which invoke `data_integrity.clock_checks`, JSON Schema, schemas and Python/library behavior. Current helper files happen to match the accepted boundary, but the proposed verifier would accept a future modified helper while still presenting the frozen orchestration-file hash.

Define an immutable engine manifest at the accepted commit covering at least `orchestration.py`, `validate.py`, `data_integrity.py`, every schema used on the path, Python runtime identity and the JSON Schema implementation/version. Verification must load the accepted code closure from the verified frozen tree/artifact rather than importing mutable current modules and checking one file afterward.

Historical execution also needs a deterministic evaluation clock. The adapter may capture the actual aware UTC evaluation instant and rerun the accepted code in an isolated environment whose clock dependency is fixed to that instant; this wraps the function without changing its eligibility rules. If the project rejects controlled clock replay, then it cannot claim exact historical recomputation for clock-sensitive decisions and must narrow the evidence claim accordingly.

The recomputation environment must be specified. A verifier cannot simply point frozen M0.2 at an arbitrary temporary directory because `_validate_identity` requires that root to equal the imported module's `ROOT` and validates remote/ancestry. A workable plan is a verified isolated checkout/worktree based on the freeze tree, imported from that tree, with captured authoritative source bytes and inventories materialized, captured origin/HEAD/origin-main identities established, and the captured clock/environment applied. Equivalent approaches are acceptable, but Data cannot invent this boundary.

## Generation, verification and the three statuses

Generation has a HIGH TOCTOU gap. “Resolve sources, hash input, invoke M0.2” is not serialized with repository mutation. The adapter must acquire the accepted M0.3A runtime/checkout advisory lock, resolve and persist an immutable candidate source snapshot, invoke frozen M0.2 against exactly that snapshot, perform a final authoritative resolver comparison while the lock remains held, and store the immutable envelope bytes/digest in the same runtime transaction or an explicitly ordered atomic persistence step. A→B mixtures must deny/block rather than produce an envelope claiming A.

Verification must be two-phase:

1. **Historical validity:** validate the closed schema and content digest; verify freeze/engine manifest; reconstruct the captured historical environment solely from persisted evidence; rerun frozen M0.2 at the captured evaluation instant; compare the exact raw and normalized outputs, every field and `decision_id`. Failure is `INVALID`.
2. **Currentness:** under the common lock/final-check protocol, independently resolve the current authoritative source/inventory/Git bundle and compare it with the historically valid subject and bundle. Equality plus DISPATCH and matching runtime/task/attempt/generation is `VALID_CURRENT`; a current authoritative difference is `VALID_STALE`.

The current steps instead require every source reference to match the current repository before recomputation, then later call a changed source stale. That makes historical staleness impossible to distinguish from unverifiability. Current files are for currentness, not the source of historical bytes.

The revision must classify edge cases explicitly. Malformed/corrupted envelope, digest mismatch, incomplete captured bytes, wrong freeze/engine, failed historical recomputation, raw/normalized output mismatch, `decision_id` substitution, internally inconsistent task/attempt/assignment or unavailable accepted engine are `INVALID`. A historically reproducible envelope whose current source was changed, moved, deleted, superseded, gained a conflicting inventory entry, or whose project/STOP/dependency/capability/assignment/Git head/generation advanced is `VALID_STALE`. A different runtime/repository attachment cannot authorize and should be explicitly classified—normally `INVALID` for that runtime even if an origin-specific historical verifier can separately attest its prior validity.

## R gates, persistence and governance

V4's R-gated map is coherent with the accepted scheduler policy: CLAIM, START, CONTINUE and COMPLETE require a current DISPATCH envelope for the exact task/attempt/runtime generation; governance REVALIDATE requires a newly generated current envelope. Yield, failure, recovery, cancellation, supersession, review/remediation and routing remain non-R operations. Once authoritative input changes, the accepted governance transition fences ownership and records uncertainty; stale work cannot continue or complete. Evidence already captured remains historical evidence rather than a new effect authorization.

Envelope reuse while current is acceptable because M0.3-only tuple mutations are not M0.2 repository inputs. Reuse must still run currentness verification at each R-gated transaction under the common lock and final Git check; an envelope is neither one-use nor timeless authority. Repository generation, exact task/attempt and authoritative bundle must match every use.

SQLite as runtime authority is correct, but immutable persistence must include canonical envelope bytes plus every exact historical source artifact needed by phase-one replay, not only source digests. Task, event and idempotency records bind the envelope digest/reference; update/delete deny; replacement creates a new envelope. Backup/export and replay must carry the referenced envelope and source artifacts so event→envelope→historical inputs/output remains self-contained after Git changes.

Caller-supplied `receipt_digest`, arbitrary envelope IDs, caller `verified=true` flags and unverified digests must be removed from every authorization path. The additive migration may preserve legacy values only as non-authorizing historical data. No R-gated transition may fall back when the adapter is absent or invalid.

The security claim is appropriately narrow: deterministic local evidence binding, reproducibility, substitution detection and staleness detection. It provides no actor authentication, external authority, hostile-host integrity, external immutability, STOP clearance, Risk approval or capital permission.

## Data scope, STOP, and required acceptance additions

Existing Data scheduler work can remain. The narrow implementation should add the closed envelope/source-artifact persistence, adapter/verifier, event/envelope references, additive legacy-field migration, replay/export/backup integration and tests; replace the caller receipt path; and avoid unrelated scheduler rewrites.

`STOP-M0-3A-001` cannot be cleared by this planning review. It requires an accepted corrected contract, separate Director release, Data implementation, complete adapter and M0.3A acceptance runs, independent adversarial implementation review, and an evidence-linked resolution by authorized process. `STOP-M0-001` is unaffected.

In addition to the proposed cases, implementation acceptance must cover:

1. mutation of `validate.py`, `data_integrity.py`, each consumed schema and dependency version while `orchestration.py` stays unchanged;
2. a record timestamp crossing the captured evaluation-clock boundary;
3. changed `origin/main` ancestry, remote URL, root identity and directory inventory;
4. extra malformed task/assignment/handoff/capability/STOP filenames and unrelated malformed handoff content;
5. DISPATCH and each DENY branch's complete dependency set;
6. duplicate JSON keys, finite floats, Unicode variants, list-order changes and raw-property-order changes;
7. exact frozen raw output, DENY missing-operation normalization and an unexpected output field;
8. generation mutation between source resolution, invocation, final check and persistence;
9. historical replay after current source mutation, deletion, move and uncommitted working-tree capture;
10. explicit INVALID versus VALID_STALE edge cases, including unavailable engine and wrong runtime attachment;
11. currentness change between verification and each R-gated transaction;
12. removal of every arbitrary caller digest/ID/boolean fallback;
13. Stage 1 regression and byte preservation.

## Disposition

No project-wide BLOCKER is introduced. Five HIGH planning gaps prevent adapter release: incomplete transitive/branch-specific input capture; incomplete engine/environment identity and nondeterministic clock replay; open typed input/output schemas with ambiguous output normalization; absent immutable historical source bytes/recomputation environment; and generation/verifier ordering that leaves TOCTOU and collapses staleness into invalidity. MEDIUM notes cover explicit Unicode/float/list canonicalization, wrong-runtime classification, and exact evidence-only behavior after governance block. No LOW issue needs a separate cycle.

Director must publish a corrected envelope schema/specification and v4 amendment, then request focused Skeptic re-review. Data remains blocked. No adapter/runtime implementation, STOP resolution, M1, operational activity or capital action is authorized.
