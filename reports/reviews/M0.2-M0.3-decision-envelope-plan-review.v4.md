# M0.2 → M0.3A decision-evidence adapter planning review v4

**Verdict: `M0_2_M0_3_ADAPTER_PLAN_REQUIRES_REVISION`.** V4/v7 fixes the prior scheduler contradiction, accepts the real Stage 1 Git SHA-1, closes the basic DENY/DISPATCH shapes, defines bounded evidence-only payloads, and makes the semantic verifier mandatory. The package is still not implementation-ready. The closed envelope schema omits the canonical input, captured Git observations, runtime identity, and repository/runtime generation bindings that its prose and v7 require. Data therefore cannot reproduce or establish currentness from the purported authority record without inventing fields or an out-of-envelope evidence model.

## 1–3. Verdict, Stage 1 neutrality, and scheduler reconciliation

Frozen Stage 1 remains byte-identical at `bc3a40924ca580ca6eddc4c24e32ff99ddd95330`; the current `orchestration.py`, `validate.py`, `data_integrity.py`, and accepted orchestration tests match that commit. This review changes no production, contract, schema, scheduler, adapter, or runtime file.

V7 now preserves the accepted v3 scheduler semantics: claim `N0→N1` with `+S+D+F`; start `N1→N2` with `+S`; continue `N2→N2` with `+S`; completion `N2→C0/N3` with `+S+D+F`; revalidation `B0→N0` and `B1→N3` with `+S`; and accepted invalidation with close/revoke and `+S+D+F`. It introduces no `R0` and does not redefine terminal `C0`. Claim/fence, dispatch-generation, terminality, and governance behavior remain under v3.

## 4–6. Schema authority, outputs, and subject

The three-stage authority rule is clear in prose: schema validation, retained-content/digest verification, then mandatory `semantic_verify_v1`. No caller verification flag is accepted. The v4 schema rejects extra top-level fields, DENY with non-null operation, DISPATCH with null operation, malformed adapter values, and unsupported raw fields. Cross-field raw/normalized mutations remain schema-valid, but the named verifier explicitly must derive normalization, rerun Stage 1, and reject them; that division is acceptable.

The subject correction is conceptually sound: only output `task_id` is compared with the envelope, while attempt and heads come from canonical historical input. It is not implementable as written because the closed schema contains no `input` member. A schema-valid envelope has no place to store `input.source_ids`, canonical input bytes/digest, task/attempt intent, or the assignment/handoff source identities that the verifier is ordered to reconstruct. Since `additionalProperties:false` forbids adding that evidence, Data must either violate the schema or invent external semantics.

## 7–9. Artifact closure and complete inventories

The prose requires unique IDs, exact source sets, no dangling references, lexical inventories, root containment, equal member/file digests, absence contradiction checks, and complete handoff and recursively consumed inventories. That correctly covers `_current_handoff`, including unrelated valid, malformed, newer, and conflicting files, and it covers the frozen STOP, project, assignment, task, completion, capability, binding, dependency, schema, and denial-context reads.

The schema cannot represent all of the declared rules. It says ABSENT has “scope,” but the ABSENT variant has no scope field. DIRECTORY members have only path, artifact ID, and digest, with no entry kind, so the record cannot distinguish files from directories, symlinks, or other entries even though closure requires FILE-member linkage and fail-closed filesystem interpretation. The source manifest is only `{source_id,artifact_id}`, while the nonexistent `input.source_ids` exact-set check is central to completeness. A named semantic checker may validate references, but it cannot recover facts the closed data model does not carry.

## 10–11. Raw and normalized output

The raw contract is sufficient in principle: strict base64 decode, UTF-8 canonical JSON, exact raw mapping, bool/int distinction through canonical JSON, float and duplicate-key rejection, length and SHA-256 equality, and exact replay comparison. The schema deliberately leaves base64 and digest agreement to the mandatory verifier. Normalized output has no independent authority and must be recomputed; task, reason, decision ID, decision, adapter, and operation mutations are covered by the exact-equality rule.

The envelope’s own `envelope_sha256` is not similarly defined. Neither v4 nor its schema states which canonical envelope bytes are hashed or how the self-referential field is excluded or replaced. This is authority-bearing persistence and export identity, so Data cannot invent the digest procedure.

## 12–15. Engine graph, loader, clock, and Git shim

V4 materially improves the engine graph by using artifact IDs for entries, launcher, clock shim, Git shim, and a dependency-manifest artifact. The loader, module path, working root, environment allowlist, clock installation order and exact `edgelab.data_integrity.datetime` symbol are specified. Historical clock reads use one preserved UTC instant and remain separate from the currentness clock. The Git shim exactly matches the two frozen subprocess observations and denies all others.

The closed graph is still underspecified. No schema defines the dependency-manifest FILE’s content, closure algorithm, or sealed import-validation manifest. Distribution entries contain only name/version and do not resolve to retained immutable artifacts, despite the requirement that every decision-critical engine artifact and restored replay dependency remain available. More fundamentally, no envelope field captures the Git shim’s historical remote URL or ancestor result. The verifier therefore cannot configure the exact shim described by the contract from a schema-valid envelope.

## 16–18. Historical verification, currentness, and typed results

Historical/current separation is correct in concept: replay alone determines historical validity, then a common-lock current comparison determines currency, and wrong-runtime evidence remains historically valid but non-authorizing. The currentness checklist names the complete authority closure and exact task, attempt, repository, and runtime generations.

The schema omits repository identity, remote/origin-main observations, runtime identity, repository generation, and runtime generation. It consequently cannot bind the values that v7 requires at claim/start/continue/complete, cannot prove that restored replay uses the captured Git state, and cannot decide reuse after either required generation advances.

The verification-result schema separates the five requested dimensions syntactically but does not constrain their combinations. It accepts `INVALID/CURRENT/MATCH/ALLOW`, `HISTORICALLY_VALID/STALE/MATCH/ALLOW`, and `HISTORICALLY_VALID/CURRENT/WRONG_RUNTIME/ALLOW`, each with empty reason codes. V4 says the verifier checks result consistency, but a persisted or consumed result is itself an authority record; its closed schema must mechanically deny these combinations or the contract must specify that only a verifier-created result with a separately bound digest is consumable. V7’s aggregate `VALID_CURRENT` is also not explicitly mapped to the result fields.

## 19–20. Evidence payloads and event-only semantics

All four payload variants are closed. Extra command, executable, action, success, output, and escalation fields reject; digest counts and REPORT_BLOCKED note size are bounded. `RECORD_EVIDENCE` requires evidence. Duplicate or untyped generic digests are a bounded residual, because the event layer can content-address and type-check them; the contract should still require unique digest arrays.

V7 makes REPORT_BLOCKED, RECORD_EVIDENCE, REPORT_FAILURE, and SAFE_YIELD B0-only, event-only `NO_STATE_CHANGE` operations. They require the ledger-bound original actor fixture and already-closed claim/fence plus unique idempotency, advance no tuple/scheduler/dispatch/fence generation, open no claim, grant no retry or completion, and have `operational_effect=false`. SAFE_YIELD is coherent because governance already closed the claim. B1 and all other tuples deny. No route back to operational work was found.

## 30–33. Findings, required revisions, and readiness

Three BLOCKERs remain:

1. **Canonical input and historical observations are unrepresentable.** The closed schema has no input bundle and no captured remote/ancestor facts, while v4 requires both for subject binding and exact replay.
2. **Currentness generations are unbound.** The schema has no runtime/repository identity or generation fields, while v4/v7 require exact values for authorization and reuse.
3. **Envelope identity is undefined.** `envelope_sha256` has no canonical byte/self-field calculation rule.

Three HIGH ambiguities remain:

1. Git algorithm and length are independent: both `git-sha1` with 64 hex and `git-sha256` with 40 hex validate.
2. The verification-result schema accepts authorizing ALLOW for invalid, stale, and wrong-runtime results and does not mechanically define `VALID_CURRENT`.
3. Artifact/engine closure cannot encode ABSENT scope or filesystem member type, and the dependency-manifest format and immutable distribution-artifact closure are undefined.

MEDIUM residuals are duplicate/untyped evidence-only digest arrays and the absence of a unique/reason-code consistency constraint. No separate LOW item was found.

Required revision is narrow but structural: add a closed canonical input with exact source IDs/bytes/digest and subject derivation; capture historical Git observations; bind runtime/repository identities and generations; define the envelope digest algorithm; condition Git digest length on algorithm; make result authorization combinations impossible; encode absence/member kinds; and define the dependency/import manifest and immutable distribution closure. Preserve v7’s scheduler and evidence-only semantics.

Data cannot implement directly from v4/v7 without architectural invention. H-M0-041.v12 remains blocked. Neither STOP is cleared and Data is not released.
