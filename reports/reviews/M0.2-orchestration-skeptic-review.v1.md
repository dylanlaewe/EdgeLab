# M0.2 orchestration sandbox — independent Skeptic review v1

**Verdict: REJECTED AS A GOVERNANCE DECISION ENGINE; CONTAINED AS MOCK-ONLY CODE.** No BLOCKER was demonstrated because the module has no task executor and cannot cause the prohibited external or operational effects represented by its output. Seven HIGH findings demonstrate that caller-controlled combinations can nevertheless produce `DISPATCH`, completion, or approval routing for work that current governance does not permit. The implementation therefore fails its central decision invariant and must remain mock-only while Director-owned remediation is completed and independently reviewed.

## Findings

### M02-SK-01 — HIGH — caller-controlled classification and unvalidated task envelope

`decision()` never validates `orchestration-task.schema.json` and ignores every unknown field. A task missing required schema fields, carrying `operation: LIVE_EXECUTION` and external/network payload metadata, receives `DISPATCH` when its label is `SYNTHETIC_TEST`. The allowlist correctly denies missing, malformed, case/space/lookalike, deprecated, unknown and explicitly prohibited labels, but the label is only a caller assertion. There is no typed operation or resource envelope binding the label to permissible behavior.

No external effect occurs because the result is `MOCK_ONLY`. This is still a current HIGH decision-integrity defect: the engine says governance permits disguised work. Remediation must validate the full task schema and bind each allowlisted class to a closed, typed set of operations/resources/capabilities. Free-form executor payloads must not become reachable through an allowlisted label.

### M02-SK-02 — HIGH — stale assignment is the only accepted assignment

The code compares `handoff_ref` to the literal implementation claim `H-M0-027.v2`. It does not load or validate that handoff, resolve the latest version, bind a claim identity, or check task attempt/status. Consequently the superseded v2 dispatches while the current v4 request denies; attempt `0`/`-1`, `COMPLETED`/`REJECTED` tasks and unknown assignee labels dispatch. Completion has no handoff, attempt or supersession check.

Remediation must resolve the authoritative current assignment and claim from repository state, bind task/attempt/owner, and reject changed or superseded work at dispatch and completion.

### M02-SK-03 — HIGH — project and STOP validity/head selection is incomplete

Project state is reread on every call and phase/status changes are observed. Missing/read-error safety files deny. However, the engine validates neither safety record against its schema nor current authoritative history. Minimal objects containing only the two project fields and `{"status":"OPEN"}` pass. It always reads `STOP-M0-001.v1.json`, so a conflicting/superseding v2 head is ignored. Scope, affected components, dependencies, active STOP inventory, timestamps and action relationship are not checked.

Remediation must validate full records, select the authoritative STOP head/inventory, reconcile project state with it, and bind the specific allowlist exception. The safety snapshot must be revalidated at the final state-changing boundary when one exists.

### M02-SK-04 — HIGH — repository identity is cloneable

Wrong remote, missing markers and missing Git metadata deny. Alternate remote spelling also denies because equality is exact. A synthetic repository with copied marker files and the expected `origin` URL dispatches, as does a symlink alias to it. The check does not establish canonical workspace, trusted checkout identity, expected commit ancestry, branch, worktree registration or content provenance. It therefore does not prevent the historical wrong-repository failure class when markers/config are copied.

Remediation must define and verify the trusted workspace/checkout identity and expected remote ancestry. Path aliases may be allowed only after canonical resolution to that identity.

### M02-SK-05 — HIGH — writer and dependency truth is supplied by the caller

The optional `writer_task` detects a conflict only when the caller supplies one. Omitting it dispatches during an asserted conflict, and claiming the candidate task ID dispatches without repository evidence. Dependency status is an arbitrary `completed` set: a nonexistent, failed, blocked or self dependency dispatches when its ID is inserted. Cycles, versions, evidence, invalidation and status transitions are not resolved.

Remediation must derive writer ownership and dependency closure from one authoritative, validated state snapshot with atomic claim/compare-and-set semantics appropriate to the repository protocol. Caller assertions cannot be authority.

### M02-SK-06 — HIGH — completion and independent review are unauthenticated route strings

`completion()` checks only exact task-ID text and whether the evidence list is nonempty. `"human says done"`, another task's artifact or an unlanded reference advances a queued task. It does not verify claim freshness, task/attempt/status, artifact ownership, commit existence, expected remote ancestry, validation, clean/yielded writer state, reviewer identity, review subject/version or review evidence. Any caller can pass `REJECT` or `APPROVE`. Setting `review_required: false` bypasses review and returns `COMPLETED`; alias identities bypass the raw role-string self-review comparison.

Approval returns `READY_FOR_DIRECTOR_GATE` and does not mutate project state, which is the correct final routing boundary. Rejection returns bounded remediation. Those strings do not form an end-to-end state machine. Remediation must authenticate canonical actors, validate immutable transition evidence and make transitions conditional on authoritative current state.

### M02-SK-07 — HIGH — capability enforcement is optional and incomplete

Omitting `capability` bypasses all capability checks. A partial object marked approved, non-revoked and non-executable passes even when it says network and credentials are required, remains unreviewed/unknown, or accompanies an installation operation disguised as a synthetic task. The capability schema is not invoked and capability/task binding is absent. Explicit unapproved, revoked and executable flags do deny when the optional object is supplied.

Remediation must require schema-valid capability bindings for every operation that can use one, reject network/credential/install/activation semantics in M0.2, and resolve approved metadata from authoritative registry state rather than trusting a caller object.

## Requested attack dispositions

1. **Action classification:** exact known prohibited/unknown variations deny; a permitted label disguises arbitrary semantics and dispatches (M02-SK-01).
2. **Project state:** fixed path and per-call reread work; approved/M1/unknown/missing deny. Minimal malformed or stale records with the two expected fields pass (M02-SK-03).
3. **STOP:** missing/fake-cleared status denies; incomplete OPEN and stale v1 amid a conflicting v2 pass (M02-SK-03). OPEN is not a generic operational bypass only because the label allowlist and absent executor contain it.
4. **Repository preflight:** obvious wrong remote/markers/Git deny; copied identity and symlink alias pass (M02-SK-04). No NetworkPilot repository was accessed or changed.
5. **Stale assignment:** older v2 is required, current v4 is denied, and attempt/status/claim freshness is ignored (M02-SK-02).
6. **Writer coordination:** supplied conflicts deny, omitted or self-asserted state passes (M02-SK-05). There is no persistent scheduler consistency.
7. **Dependencies:** omitted dependencies pass; arbitrary caller-completed, nonexistent, failed, self/cyclic/versionless dependencies can pass (M02-SK-05).
8. **Completion:** empty evidence and mismatched ID deny; all other requested integrity properties are documentation-only (M02-SK-06).
9. **Independent review:** exact same role string denies at dispatch; aliases, omitted review and unauthenticated approval/rejection pass (M02-SK-06).
10. **Director release:** approval yields only `READY_FOR_DIRECTOR_GATE`; status manipulation does not release M0 or mutate project state. This narrow property passed.
11. **Synthetic-only:** explicit prohibited labels deny, but mislabeling succeeds at the decision layer (M02-SK-01/M02-SK-07). It is safe from real-world effects today solely because no executor consumes the decision.
12. **Execution adapter:** no task, Codex, network, plugin, credential or external-agent invocation exists. The only subprocess is fixed-argument local `git remote get-url origin` in repository preflight; task input cannot alter its command. No hidden execution adapter was found.
13. **Plugin/Skill registry:** schema metadata exists and explicit negative flags can deny, but registry validation/resolution/binding is absent and optional (M02-SK-07). No skill or plugin was installed or activated.
14. **Audit model:** returned decisions have no unique decision ID, persistence, ordering, conflict, deletion or dispatch-to-completion correlation. This was explicitly deferred and cannot cause effects in mock-only M0.2, but it is a FUTURE_GATE.
15. **Model routing:** there is no persisted policy. This has no current effect because no Codex/agent executor exists; it is a FUTURE_GATE.
16. **Synthetic workflow:** individual route strings reproduce dispatch → review route → rejection/remediation route → approval/Director-gate route. Claim, state transitions and remediation ownership are not implemented. Human-prose evidence can advance completion, so the reported end-to-end workflow is not independently reproduced as an enforced workflow (M02-SK-06).

## Severity summary

- **BLOCKER:** none; no current external/operational effect path exists.
- **HIGH:** seven findings, M02-SK-01 through M02-SK-07.
- **MEDIUM:** none separately; the meaningful integrity weaknesses are included in the HIGH findings.
- **LOW:** none.
- **FUTURE_GATE:** four grouped gates below.

## Mandatory gates before any real executor

1. **Typed semantic execution boundary:** closed operation/resource/capability envelopes, schema validation, policy-to-adapter binding, deny-on-unrepresented semantics and a separate independently reviewed adapter.
2. **Authoritative transactional scheduler state:** persistent task/attempt/claim/dependency/writer state, atomic claim and transition operations, current project/STOP-head resolution and invalidation immediately before effect.
3. **Authenticated evidence and audit:** canonical actor identities, independent-review subject binding, landed-commit/remote-ancestry validation, append-only uniquely identified decisions and completion correlation, replay/conflict/deletion defenses.
4. **Model and usage policy:** task complexity tier, allowed model tier, explicit escalation, budget/cost limits, no silent strongest-model escalation and durable routing evidence.

These gates do not authorize an executor after implementation; each requires independent review and the separate repository-defined release process.
