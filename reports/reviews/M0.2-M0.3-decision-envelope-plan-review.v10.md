# M0.2 → M0.3A decision-evidence adapter planning review v10

**Verdict: `M0_2_M0_3_ADAPTER_PLAN_REQUIRES_REVISION`.** V10 is structurally satisfiable as a complete root envelope, required root-component deletion fails, closure v4 authenticates and contains the pinned third-party runtime set, engine v4 closes working-directory/environment fields, and V11 adopts V10. The graph is not semantically satisfiable against frozen M0.2 without invention: canonical scheduler evidence requires facts the frozen record never contains; ABSENT cannot represent its required digest inputs; closure v4 is unreachable from the envelope; and the currentness, relationship, dependency, capability and artifact predicates remain incomplete.

## 1–4. Satisfiability and root graph

A complete synthetic DISPATCH envelope was constructed from the published schemas. It contains canonical task/scheduler/assignment/handoff/project/STOP/capability authority, source manifest, FILE/DIRECTORY artifacts, blobs, Git observation, engine distribution, import/validation manifests, raw bytes/mapping, normalized output, verification binding and self digest. It validates structurally. Removing source manifest, blobs, artifacts, Git observation, engine distribution, import manifest, validation manifest, raw evidence or verification binding makes it schema-invalid.

Structural success does not prove semantic coherence. Blob IDs may be duplicated with conflicting blob records, directory members may be duplicated and unsorted, artifact paths may escape the root, manifest digests may be arbitrary, and the envelope self digest is only shape-checked. V10 says to verify these objects but supplies no canonical formulas or ordering/uniqueness rules after superseding earlier plans.

Primary task records directly name ID, artifact, version and head. A verifier can follow those IDs through the source manifest, FILE artifact and blob, provided the missing cross-record algorithms are supplied. No path inference is structurally necessary.

## 5–10. Frozen authority semantics

The frozen M0.2 scheduler record contains `generation`, project/STOP refs, task refs, claims and completed tasks. It has no `workflow`, `execution`, `review`, `dispatch_generation` or `fence`. V10 requires all five as canonical historical scheduler fields. Populating them requires mapping M0.3A tuple semantics onto evidence frozen M0.2 never emitted. That is a BLOCKER under the no-competing-scheduler requirement.

V10 relationship contains task, assignment, handoff and claim IDs. Assignment/handoff heads exist in adjacent generic records, but writer role, assignment/handoff head equality and claim generation are absent from the relationship predicate. A mismatched writer or cross-record head has no published deterministic rejection rule.

Project fields correctly bind M0 phase, status and locked live state without inventing capital authority. STOPs have a directory artifact and generic record identities, but neither status/disposition nor the exact complete-inventory equality predicate is represented. Frozen replay can inspect retained bytes, yet currentness and source-manifest mismatch behavior still require a stated predicate.

Dependency entries add required/current heads and `completion_count:1`, closing zero/multiple count structurally. They do not bind frozen completion `content_sha256` to the exact dependency task bytes or state how scheduler task ref, numeric current head, task artifact/version and completion record must agree. This remains a HIGH frozen-predicate gap.

Capabilities are generic record references only. Canonical input omits disposition/effects and all frozen security fields such as trust, approval, revocation, roles, permissions and prohibited semantics. Replay can inspect retained bytes, but the canonical/currentness contract cannot compare the authority-bearing capability state V10 claims to bind.

## 11–17. Blob, artifact, source and Git graphs

Every root authority can carry an artifact ID and every FILE can carry a blob ID. V10 prose requires unique resolution, but the blob array’s `uniqueItems` compares whole objects rather than blob IDs; two conflicting records with the same `blob_id` validate. Malformed base64, length/digest disagreement and FILE/blob disagreement are semantic checks with clear intended rejection, so those are bounded once algorithms are specified.

Artifact v2 rejects OTHER, but FILE paths and DIRECTORY roots/member paths accept traversal. DIRECTORY does not require lexical ordering or path uniqueness and supplies no inventory-digest formula. V10’s two-paragraph authority does not define these security-critical inventory semantics.

ABSENT remains impossible to verify. Artifact v2 lacks `source_class` and `absence_context`, the two fields the prior formula required, and V10 supplies no replacement formula. A representative assertion cannot be recomputed from the published V10 authority.

Source manifest lists unique artifact, inventory and absence IDs and binds canonical/source-set digests. Canonical records, engine shims, import modules and validation schemas can name artifacts directly. The exact required source set, directory/inventory correspondence and digest formulas remain unstated.

Git observation carries repository identity, HEAD, origin/main, URL, ancestry operands/result and digest. V10 says historical replay uses preserved evidence and not current Git; the exact operand rule established in V9 is not restated after V10 superseded V9. Data would need the superseded plan to know that left must equal HEAD and right origin/main.

## 18–27. Engine, paths, packages and outputs

Engine v4 requires strict typed working directory and the exact four-key environment. Non-string, absolute, dot/traversal, empty segment, URI and drive paths reject. Missing/unknown/wrong environment values reject.

Import and validation manifest paths retain their older grammar and still accept `replay/./x` and `replay//x`, contradicting the engine grammar. Artifact and shim paths are less constrained. The inconsistency has a clear conservative resolution but needs schema/test alignment.

Package records have distribution IDs, exact versions, blob/digest, Python and platform. Import and validator IDs can resolve by exact ID. Engine v4 does not bind import/validation manifest IDs, local-module artifact IDs or a Python interpreter artifact; the envelope has one sibling manifest of each kind, but the engine distribution itself cannot authenticate which manifests/modules/interpreter constitute it.

Closure v4’s digest recomputes to `766c19…406c4`; mutation changes it. It includes jsonschema, jsonschema-specifications, attrs, referencing and rpds-py. It is not a root property, artifact, manifest reference, engine field or digest in V10, so historical replay cannot establish that this external fixture is the accepted closure without repository/path inference.

Import and validation manifests map local modules/schemas to artifacts/digests and external validation to distribution IDs. V10 does not define completeness comparison against closure v4, and validation completeness is not structurally tied to every schema in the fixture.

Raw DENY and DISPATCH retain exact frozen five/six-field shapes. Raw evidence adds base64, length and digest, and normalized DENY adds null operation. The schema merges output mapping and byte metadata into one object; V10 does not state the exact projection whose canonical JSON becomes raw bytes, nor its envelope self-digest exclusion formula. Stored normalization is declared non-authoritative and the intended replay/recompute flow is otherwise clear.
