# M0.3A closed-contract final planning review v1

**Verdict: `M0_3A_PLAN_REQUIRES_REVISION`.** The v2 contract closes the earlier tuple/terminality, idempotency-ordering, worker/reviewer fencing, governance blocking, event-field, replay-enumeration, Git final-check, copied-checkout intent, backup and acceptance-case gaps. Three implementation-critical contradictions remain: circular attachment/genesis digest construction; omission of the required SQLite operational configuration from the document that declares itself the complete superseding contract; and a one-event/single-task-sequence model that cannot represent the specified bidirectional remediation mutation without leaving one task history unsequenced. `H-M0-041.v3` remains queued and is not implementation-ready.

## Transition model and prior HIGH dispositions

The complete state tuple and closed tuple aliases now separate workflow, execution and review state coherently. `APPROVED` is review-terminal while N7→N8 changes only workflow to `DIRECTOR_GATE_READY`; the prior terminality contradiction is closed. Cancelled, superseded, closed and director-gated complete tuples do not resurrect. Retry creates a new attempt, remediation creates a linked task, and continuation remains on the same attempt.

The actual matrix now states source and target tuples, actors, claim/reviewer/receipt requirements, generation effects, evidence, events and claim effects. Unlisted tuples and operations deny. Worker transitions require **W**, reviewer transitions require **V**, and independent review requires both a different structural role and fixture identity. Fixture separation is structural only and does not claim authentication.

One matrix fact remains undefined: `repository_generation` is part of the complete tuple, but `IMPORT_REPOSITORY` says `+S` and returns a repository generation without stating its previous/next value or increment rule. `REVALIDATE_GOVERNANCE` similarly returns a new repository generation without an explicit mutation rule. Because repository generation is used to invalidate receipts and authorize later rows, Data must not infer this security-relevant CAS behavior. The final revision must state whether the generation is global or per-task, its exact increment, and its event before/after fields.

## Transaction and semantic idempotency

The committed-result-first order is now correct. After immutable runtime/attachment validation, the scheduler looks up `(runtime_id, operation_key)` before mutable tuple, CAS or fence checks. An exact request digest returns the canonical committed response; changed content rejects key reuse. A new operation alone proceeds through state/fence/receipt checks, final Git verification, one atomic event/state/result write and commit. This closes the prior lost-response HIGH finding.

Canonical request fields and serialization are sufficiently explicit. The acceptance cases now cover post-commit/pre-response failure, altered idempotency content, atomic failure injection and stale CAS after commit.

The process-level lock still has a safe availability ambiguity. `O_CREAT|O_EXCL` can leave a stale file after a crash, and the contract requires “separately recorded takeover” without defining its operation, authority, evidence destination or lock-safe ordering. A safe implementation can refuse service, so this is MEDIUM rather than a privilege bypass, but the recovery contract and acceptance case must be added before claiming restart recovery.

## Claim, reviewer, recovery and governance fencing

The matrix closes worker/reviewer fencing. Start, continue, yield, complete and fail require the current claim/fence; stale workers reject before evidence mutation. Recovery acts only on N1, uses liveness evidence, closes the claim, advances scheduler/dispatch/fence values and returns exactly N0. Lease expiry alone grants nothing. N2 recovery is prohibited because external effects cannot be disproved.

Governance invalidation now has exact targets: N1/N2→B0, N3/N4→B1, with claims/reviews closed or revoked and fences advanced. Revalidation never restores ownership. This covers STOP/project changes before start and during work without pretending M0.3A can cancel an executor.

The reviewer matrix requires both owner/reviewer role difference and fixture-ID difference. M0.3B remains responsible for authenticated identities.

## Events, sequencing, replay, and cross-task lineage

The expanded event fields, genesis sentinels, logical global/task sequences, canonical digests, and replay enumeration close most prior event/replay findings. Logical committed sequences are separate from SQLite row IDs, contiguous, and checked for gaps, reorder, duplicate, wrong predecessor and wrong task/attempt substitution. Materialized tuples, attempts, claims, fences, assignments, counters, links, evidence, receipts, idempotency results, heads and roots must match replay or startup/export fails closed.

`CREATE_REMEDIATION_TASK` remains contradictory under the “exactly one event” and singular `(task_id, task_sequence)` contract. It says the source remains state-immutable but gains a successor link, a new task is created at N0 with a predecessor link, and only the new task's scheduler generation changes. One event cannot simultaneously advance both per-task chains. If assigned to the source, the new task has no task-sequence-1 creation event; if assigned to the new task, the source link changes without advancing its task head. Global replay may see the mutation, but one per-task forensic history is incomplete. The revision must either emit two deterministically linked events atomically, define a multi-task event with sequence/head effects for every affected task, or make one side derived and immutable from a single authoritative link. Acceptance must assert both task heads and replay results.

Runtime-level events have a smaller representability gap. `SCHEMA_MIGRATED` is required, but the general event schema requires task/attempt and task sequence. Define a runtime-event namespace/sentinel with no task chain, or a separate runtime-event shape. This is MEDIUM and must not be improvised inconsistently.

## Git/SQLite serialization and attachment

The cooperative lock ordering plus a final Git re-resolution inside the SQLite transaction closes the cooperative A→B TOCTOU attack. All cooperative operations must use the same order: scheduler lock, then SQLite transaction. A process ignoring the lock is explicitly outside local proof.

The checkout attachment as written cannot be constructed. `attachment.json` contains `genesis_digest`; genesis contains `attachment-manifest digest`; each digest therefore depends on the other. Cryptographic fixed-point construction is neither defined nor practical. Data would have to invent which field is excluded or which object is sealed first. This is HIGH. Define an acyclic scheme, such as digesting an attachment core that omits `genesis_digest`, binding that core digest in genesis, then storing genesis digest as a non-core cross-reference; specify canonical bytes and startup verification in both directions. Preserve the stated local-only limitation.

## SQLite, backup, migrations, snapshots, and corruption

The v2 document calls itself the complete contract and says it supersedes the earlier implementation details, but it only says “verify required PRAGMAs.” It does not define `journal_mode=WAL`, `synchronous=FULL`, `foreign_keys=ON` on every connection, the five-second busy timeout, short `BEGIN IMMEDIATE` writer discipline, startup/export `integrity_check`, or owner-only permissions for directory, database, WAL and SHM files. Those values existed in the superseded planning document and cannot safely be inferred into the complete contract. This is HIGH because durability, foreign-key behavior and busy handling would otherwise be implementation choices. Restate them directly and require verification of returned PRAGMA values.

The SQLite backup API, prohibition on raw live `.db` copying, transactional migrations, failure rollback/unavailability, downgrade/newer-version refusal, coherent read snapshots and no-secret exports are otherwise suitable. Migration and snapshot operations must explicitly acquire the same scheduler lock before SQLite locks so lock ordering stays uniform and the Git bundle cannot change during export. This is a MEDIUM clarification.

Corruption behavior remains sound: integrity, foreign-key, sequence, chain, tuple, replay or malformed-row failure makes the runtime unavailable without destructive repair.
