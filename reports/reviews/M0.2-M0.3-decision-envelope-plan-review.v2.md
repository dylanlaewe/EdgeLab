# M0.2 → M0.3A decision-evidence adapter planning review v2

**Verdict: `M0_2_M0_3_ADAPTER_PLAN_REQUIRES_REVISION`.** Envelope v2 materially improves historical/current separation, blob retention, local security boundaries, lock ordering, and fake-receipt removal. It is still not implementation-ready. The published schema does not encode most of the claimed contract, the DISPATCH source set omits unrelated handoff files that frozen M0.2 actually parses, raw-output bytes are undefined for a Python mapping, deterministic frozen-clock/loader behavior remains an implementation choice, and v5 adds four operations without defining their scheduler transitions.

## Stage 1 and evidence closure

Frozen Stage 1 remains byte-identical at `bc3a40924ca580ca6eddc4c24e32ff99ddd95330`. The wrapper is evidence-only in intent and does not add permission, change classification, reinterpret STOP/capability logic, or strengthen `decision_id`. A conforming wrapper must return exactly the direct frozen result for equivalent authoritative inputs; no adapter exists yet, so implementation must prove this through the required equivalence matrix.

The source closure is almost complete but retains one HIGH omission. `_current_handoff` in `src/edgelab/orchestration.py` reads and parses every `docs/handoffs/*.json` before comparing the requested path. A malformed unrelated handoff therefore changes DISPATCH into DENY. V2 requires only the claimed handoff and the complete matching handoff-ID inventory on the DISPATCH path. Every handoff file parsed during that path, plus the full directory inventory, must be captured. A generic promise to capture every byte source does not cure a contradictory enumerated implementation list.

The successor must type content, absence and inventory evidence separately. Missing paths and malformed names cannot be represented solely by a blob-shaped item that requires `blob_sha256`; the closed manifest needs explicit tagged variants for file, absent path and directory entry/inventory evidence. DENY replay must preserve raw sources and the branch error while independently recomputing that error; stored error text cannot substitute for recomputation.

## Strict schema and canonical representations

The schema is not strict. Only the top-level object, `subject`, and `normalized_output` reject extra properties. `repository`, `runtime`, `evaluation`, `source_manifest`, `engine_manifest`, `input`, and `raw_output` are unrestricted objects with no required subfields. The schema contains no typed blob, manifest entry, engine entry, evaluation time, repository identity, runtime generation, canonical input, input/output digest, or raw-output byte representation. Four preserved probes demonstrate that it accepts empty authority objects, hidden caller authority, DENY with a non-null operational action, and DISPATCH with null operation.

The normalized shape also lacks the prose's conditional rules. It does not require DENY→`operation:null`, DISPATCH→a non-null frozen operation, normalized task equality with the subject, or normalized fields/digest equality with raw output. `decision_id`, heads and envelope ID accept arbitrary strings. These are security-critical omissions because Data would have to implement validation outside the claimed implementation-authoritative schema without a closed field contract.

Canonical JSON rules are otherwise coherent: UTF-8, duplicate-key denial, codepoint preservation, strict booleans/integers, no floats, explicit nulls, ordered arrays, canonical sets, normalized paths and UTC timestamps avoid the earlier collisions. Raw source bytes and canonical parsed bytes are correctly distinct. A changed raw file can be historically reconstructed from preserved bytes while current comparison becomes stale.

“Raw output is exactly the returned mapping bytes” is undefined because frozen M0.2 returns a Python mapping, not bytes. The contract must specify that raw output is, for example, the canonical JSON encoding of the exact unmodified returned mapping, store those bytes/base64 and digest in a closed shape, and require decoding to reproduce the exact key/value mapping. Property order should be explicitly non-semantic for the mapping while key presence and value types remain exact. Unexpected keys must remain preserved and make normalization fail.

## Engine, time and replay

The engine manifest improves on the single-file hash by naming the frozen modules, reached schemas, Python and jsonschema. Its schema is nevertheless empty, and its operational language leaves Data to choose the security mechanism. Frozen `decision()` has no clock parameter: `validate_record()` calls `clock_checks(record, now=None)`, which invokes `datetime.now()` on every validation. The contract must name one reproducible interception mechanism that freezes all of those reads to the captured instant without editing frozen modules, bind its artifact/version/configuration, and require direct-versus-wrapped equivalence at timestamp boundaries.

The loader rule likewise needs an exact construction. It must state whether the replay checkout HEAD is the historical source commit or freeze commit, how frozen engine modules are overlaid/loaded, how captured `origin/main` is established without consulting today's ref, and how `ROOT`, remote and ancestry checks are made identical to the historical call. “Rooted at the freeze” and “validates origin/HEAD/origin-main identities from the manifest” permit incompatible implementations. The environment manifest must close every required field and reject unavailable exact runtime/dependency versions.

Once these mechanics are closed, the two-phase algorithm is sound. `verify_historical` uses only preserved blobs, the accepted engine and captured time; current Git equality is irrelevant. `verify_currentness` then runs under the common lock and compares the target runtime's current complete bundle. Missing/corrupt historical evidence or replay mismatch is INVALID. A changed/deleted/moved current source with intact evidence is VALID_STALE. Wrong-runtime evidence may remain historically valid in its originating context but is `INVALID_CURRENT_STATE` for target-runtime authorization; the API should preserve the historical sub-result so this is not described as envelope corruption.

## Generation, runtime use and retention

The proposed generation order closes the earlier A→B race if candidate blobs are materialized before evaluation, the engine reads only that immutable materialization, and the final resolver comparison and SQLite commit remain under the common lock. Implementation tests must inject changes at each boundary. Envelope hashing is acyclic, but a closed schema must enumerate every hashed field and subordinate digest before that claim is testable.

The CLAIM/START/CONTINUE/COMPLETE/REVALIDATE rules remain conservative and coherent: exact current DISPATCH evidence, task/attempt/runtime and repository generation binding, currentness rechecked at every use, and a new envelope after governance revalidation. Reuse is permissible only under those checks. Legacy digest, arbitrary ID and caller verification fallbacks are explicitly non-authorizing.

V5's governance evidence amendment is not implementation-authoritative. `REPORT_BLOCKED`, `RECORD_EVIDENCE`, `REPORT_FAILURE`, and `SAFE_YIELD` do not exist in v3's closed transition matrix. V5 does not specify each operation's allowed source/target tuple, whether it closes a claim, which generations/fences advance, event/result schema, actor/fence requirement, idempotency material, or whether repeated evidence appends are allowed. “Non-operational, fence-bound, append-only” is a useful invariant but leaves Data to invent scheduler policy. Add exact rows that cannot reach C0/N3, cannot create output/completion authority, and cannot bypass a stale worker fence.

Immutable SQLite envelope/blob storage, event references, replay, backup and export direction is correct. The schema and database plan must make the evidence graph self-contained: canonical envelope bytes, every referenced blob, engine/environment manifest, raw and normalized outputs, evaluation time and event reference. Replacement creates a new object; mutation/deletion denies; restore verifies every reachable digest.

## Disposition and required correction

No project-wide BLOCKER is introduced. Five HIGH planning gaps remain:

1. the purported strict schema leaves nearly every authority-bearing section open and fails to enforce output conditionals and required digests;
2. the DISPATCH manifest omits all unrelated handoff files that frozen M0.2 parses;
3. exact raw-output bytes/digest and derivation of normalized output are undefined;
4. deterministic frozen clock, loader, checkout/ref construction and environment replay are not specified tightly enough for equivalent implementations;
5. four new evidence-only operations lack closed transition/event semantics.

MEDIUM residuals are explicit tagged absence/inventory forms, preservation of the historical-valid sub-result for wrong-runtime use, and exact mapping-property-order language. No LOW finding requires separate disposition.

Director should publish a genuinely closed schema with definitions and conditionals, correct the complete DISPATCH source list, specify canonical raw-output bytes and deterministic replay mechanics, and add exact v5 transition rows. Then request another focused planning acceptance. Data remains blocked. Planning correction cannot clear either STOP; implementation, full acceptance testing, independent implementation review and authorized resolution evidence remain required.
